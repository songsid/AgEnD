Everyday chat and core concepts

100 tips
tip-001

Instance = Agent = one AI CLI you can talk to, such as Kiro CLI, Claude Code, Codex, Antigravity, Grok, or OpenCode.

tip-002

Backend = the AI service that powers an Agent, such as Claude Code, Codex, or Kiro CLI. Different Backends provide different features and models.

tip-003

One Instance = one separate Agent conversation; another Instance does not automatically know what was discussed here.

tip-004

Fleet = all Instances managed by the same AgEnD; a fleet-wide restart affects every unpaused Instance, not just the current chat.

tip-005

General = the coordinator Agent; ask it to choose an Instance, split work, or collect results when a task crosses projects.

tip-006

A topic, thread, or channel = the chat location bound to an Instance; send the request there to reach that Agent.

tip-007

Working = the Agent is handling something; Idle = it is ready for the next message.

tip-008

Paused = the Instance is asleep but keeps its saved session; sending it a new message normally starts waking it.

tip-009

Stopped = the AI CLI exited normally; Crashed = it exited unexpectedly or repeated recovery did not succeed.

tip-010

Start a request with the result you want; add limits and output format after that so the Agent sees the main point first.

tip-011

A good request = goal + important constraints + what counts as done; this reduces extra clarification rounds.

tip-012

If wording matters, include one short example; an example usually communicates tone faster than a long explanation.

tip-013

When changing an earlier instruction, name exactly what is replaced; otherwise both old and new instructions may stay in play.

tip-014

`/steer <message>` = change the direction of work already running; it is supported by Claude Code, Codex, and Grok.

claude-codecodexgrok
tip-015

Use `/steer` for a correction to the current task, not for a separate job; unrelated work is clearer as a new message.

claude-codecodexgrok
tip-016

`/btw <question>` = ask Claude Code a side question without replacing the main task.

claude-code
tip-017

`/btw` and `/steer` are different: BTW opens a side question, while Steer changes the current work direction.

claude-code
tip-018

A busy Agent may queue a new message for later; delayed handling does not by itself mean the message was overwritten.

tip-019

Do not resend a queued request just because the reply is slow; two copies can make the Agent do the same work twice.

tip-020

Cancel button or `/cancel` = interrupt this run; the user message is already in conversation history, and how much work already happened depends on when cancellation occurred.

tip-021

AgEnD = the system that connects a Telegram or Discord chat to one or more Agents.

tip-022

Cancel also clears older deliveries still waiting for that Instance, so queued cross-Instance or scheduled work will not start immediately afterward.

tip-023

A message sent after Cancel is new work and will not be removed with the older queue.

tip-024

⏳ = queued, 👀 = delivered, ✅ = turn confirmed, ❌ = failed; these marks describe delivery, not answer quality.

tip-025

A delivery mark can appear before the Agent replies; it comes from AgEnD, not from the Agent's written answer.

tip-026

If a message stays on ⏳, wait before resending; it may be waiting for the Agent to become ready.

tip-027

If a message shows ❌, check the Instance status first; blind retries can hide the real startup, login, or connection problem.

tip-028

Reply to an earlier message when the Agent must know exactly which text, file, or image the new request refers to.

tip-029

A quoted reply includes the referenced text; add one sentence explaining what should be done with it.

tip-030

Related requests work best in one clear message; unrelated requests are easier to track as separate messages.

tip-031

Put the main request in the first few lines of a long message; details can follow without hiding the goal.

tip-032

For long work, ask for a short progress update instead of sending the whole request again.

tip-033

If the Agent asks a question, answer the missing point first; mixing in a new task can leave both requests unclear.

tip-034

If an answer is wrong, quote the exact sentence or value to change; a precise correction is faster than saying only redo it.

tip-035

At the end of a long discussion, ask for decisions + unfinished items; that summary is easier to hand to another Instance.

tip-036

Attach the file and instructions in the same message so the Agent receives them as one request.

tip-037

For an image, say what to inspect; sending only a picture forces the Agent to guess the question.

tip-038

For a document, name the page, section, or question that matters; this avoids reading unrelated parts first.

tip-039

Several attachments = explain each file's role; filenames alone may not reveal which one is input, reference, or expected result.

tip-040

A Telegram voice message is delivered as audio; if speech-to-text is enabled, the Agent also receives a transcript.

tip-041

Names, codes, and numbers in voice messages are easy to mishear; type the exact value once when accuracy matters.

tip-042

A Telegram sticker becomes its emoji when one exists; a sticker without an emoji becomes `[Sticker]`.

tip-043

A pasted image URL is still only a link; attach the actual image when the Agent must inspect the pixels.

tip-044

On supported Discord replies, replying to a message with an image also sends that quoted image to the Agent.

tip-045

Use text for important instructions; an emoji reaction alone may be recorded as feedback without starting work.

tip-046

In a chat with several bots, mention the intended bot; otherwise the wrong persona may answer or nobody may act.

tip-047

Tool progress = a short history of what the Agent is doing; when enabled, the button disappears after completion but the history remains.

tip-048

Verbose progress can include command previews; check screenshots for private paths or values before sharing them.

tip-049

An interactive prompt = the AI CLI is waiting for a password, permission, Y/N, or Enter; AgEnD will notify General instead of guessing.

tip-050

AgEnD never types a password automatically; review the prompt before approving anything.

tip-051

`/dashboard` = links to View, Settings, and Web UI; it is an admin command because the edit links contain an access token.

tip-052

View at `http://localhost:19280/view` = the live local dashboard by default; localhost means it normally opens only on the AgEnD machine.

tip-053

View shows Instance state, Context percentage when available, and live terminal output; use it to check whether work is actually moving.

tip-054

View's AI Usage panel = subscription usage for Backends that currently have an Instance; unused Backends stay hidden.

tip-055

`/usage` = show available AI subscription usage in the chat without opening View.

tip-056

No data in `/usage` does not always mean zero quota; the account may be signed out, refreshing a token, or not exposing usage data.

tip-057

Usage data is cached briefly to avoid provider limits; use Refresh in View when the latest number matters.

tip-058

Quota = the amount included with an account or subscription; a warning may allow the current answer but block later work.

tip-059

`/status` = the fleet overview, including Instance state and key health information.

tip-060

`/sysinfo` = AgEnD, operating-system, runtime, and process details; use it when reporting an environment problem.

tip-061

Context = how much of the current conversation the Agent can remember. When it fills up, use `/compact` to compress it or `/clear` to start over.

tip-062

Context near full = older details may be compacted or lost; ask for a handover summary before a long task reaches the limit.

tip-063

For a long Claude Code session, check `/ctx`; use `/compact` or write a handover summary before the limit to reduce lost details.

claude-code
tip-064

Codex normally manages conversation compaction itself, but important decisions should still be summarized instead of assuming every detail will survive.

codex
tip-065

`/compact` = shorten the current conversation while keeping useful Context where the Backend supports it; behavior differs by Backend.

tip-066

`/model` = show models discovered for the current Backend; choosing one changes that Instance's model and saves the choice for restart.

tip-067

The model list is probed when AgEnD starts; if a new model is missing, restart AgEnD, or use Discord's `/model refresh` to refresh it directly.

tip-068

`/effort` = reasoning strength for supported models; higher effort may improve hard work but usually takes more time and quota.

tip-069

`/save <name>` = export the current conversation for later reference; AgEnD supports it with Kiro CLI and Claude Code.

Claude Code `/save` exports a Markdown file for reference; there is no matching AgEnD `/load` that restores it as a Claude session.

claude-code

Kiro `/save` maps to `/chat save`; Discord `/load` works later only in the Kiro ClassicBot workflow.

tip-073

Admin `/update` = install the latest AgEnD release from the current stable or beta channel, then restart the fleet.

tip-074

Admin `/restart` = gracefully restart the whole Fleet, not only the current Instance.

tip-075

Restarting wakes every unpaused Instance; startup takes time, and later recovery or summary work may use extra tokens, so avoid repeated fleet restarts.

tip-076

Pause unused Instances before an update or restart if they do not need to come back immediately; paused Instances are skipped during fleet startup.

tip-077

Admin `/pause` = put an Instance to sleep; `/wake` = start it again. General itself cannot be paused.

tip-078

Settings can set automatic pause time; `0` means disabled, and sleeping unused Instances reduces background processes and restart load.

tip-079

Changing auto-pause, progress detail, display name, description, tags, or log level is hot-reloaded and does not restart the Instance.

tip-080

Backend, working-directory, or tool-set changes in Settings—and Backend options changed in config—are cold changes that restart the Instance.

tip-081

ClassicBot = an Agent living in an ordinary Discord server/channel or Telegram group, rather than a pre-created Fleet topic.

tip-082

ClassicBot does not interrupt every conversation by default; use `/chat`, while a bot mention also triggers it in Telegram groups or collaboration chats.

tip-083

ClassicBot includes recent chat-log context before the triggered message; the default is the latest five lines, not the entire channel history.

tip-084

To use ClassicBot, invite the bot to the Discord server or Telegram group, then an administrator runs `/start` in the target chat.

tip-085

ClassicBot `/start` creates or resumes the chat's Instance with the ClassicBot default Backend; Settings can change the Backend afterward.

tip-086

ClassicBot `/stop` removes that chat binding; use it only when the channel should no longer have its Agent.

tip-087

A ClassicBot chat and a Fleet topic are routed differently; always run commands in the chat that owns the intended Instance.

tip-088

Several bots in one collaboration chat = mention the right persona or use its slash command; each bot can own a different ClassicBot Instance.

tip-089

A login-expired message = sign in to that Backend again; retrying the same request before login is fixed usually repeats the failure.

tip-090

A model-not-supported message = the selected Backend or account rejected that model; choose another listed model instead of expecting a silent fallback.

tip-091

A password or Y/N prompt that sits still will trigger a General notification; AgEnD will not answer it automatically.

tip-092

For a bug report, include time + Instance name + what you sent + what happened; those four facts make logs much easier to match.

tip-093

A screenshot from the View page shows the live Agent screen; check it for project names, paths, or secrets before sharing.

tip-094

AI answers can be wrong; verify commands, prices, permissions, and other high-impact facts before acting.

tip-095

Sensitive work = share only the files and values needed for this request; chat exports and screenshots may contain more than expected.

tip-096

`/tips` = show another available Tip in the current chat; it does not have to be run in General.

tip-097

✅ I know this = keep the Tip text but remove its buttons and stop showing that Tip again.

tip-098

❓ I don't understand = keep the Tip text, record feedback, and allow that Tip to appear again later.

tip-099

`/clear` = erase the current Context after confirmation; it cannot be undone, but project files and AgEnD instructions remain.

tip-100

A useful Tip should tell you what changes for you; press I don't understand when the wording does not make the consequence clear.

Intermediate

Commands, Backends, and coordination

100 tips
tip-101

An Instance is one independent Agent. Each instance keeps its own conversation and can be assigned a different project.

tip-102

A Fleet is the group of instances managed together by AgEnD. Fleet-wide actions can affect every running Agent.

tip-103

General is the coordinator Agent that manages work. Ask General to choose a suitable instance, divide independent tasks, or manage the Fleet.

tip-104

A Backend determines which AI service an instance uses, such as Claude Code, Codex, Kiro CLI, Grok, Antigravity, or OpenCode.

tip-105

Context is the amount of information the AI can keep from the current conversation. It is limited and is not permanent project storage.

tip-106

MCP is the channel that lets an AI use reply, file, and collaboration tools. Users normally ask for an outcome rather than operate MCP directly.

tip-107

A Model is the particular AI selected inside a backend. Leaving it unset normally uses the fleet or account default.

tip-108

A Session is a backend's saved conversation state. Whether it resumes after a restart depends on that backend's session support.

tip-109

A working directory is the project folder an instance reads and edits. Separate instances may share one, but simultaneous edits can conflict.

tip-110

ClassicBot is the mode that creates an ongoing Agent in an ordinary Telegram or Discord conversation, rather than a preconfigured Fleet conversation.

tip-111

An Adapter is AgEnD's connection to one messaging bot account. In a multi-bot setup, an instance can be bound to a specific bot identity.

tip-112

Telegram separates fleet conversations with topics; Discord may use channels or threads. These spaces serve the same routing purpose in AgEnD.

tip-113

A Tool is an action an AI can call, such as reading a file or sending a reply. Tool availability depends on the backend and permissions.

tip-114

A delivery queue holds messages until they can safely enter a busy Agent. A queued message is delayed, not necessarily lost.

tip-115

Idle means an instance appears ready for input; Working means AgEnD sees it processing a turn. These states are observations, not guarantees about answer quality.

tip-116

Paused means AgEnD intentionally stopped the Agent's CLI process while preserving its configuration for a later wake.

tip-117

Stopped is an orderly exit; Crashed indicates an unexpected exit or repeated recovery failure. General can help inspect either state.

tip-118

Settings is the browser editor for common AgEnD options. Hot settings apply immediately; cold settings change startup behavior and restart the affected instance.

tip-119

View is the browser page that mirrors an instance's live terminal screen. It is useful when a prompt or progress display needs visual inspection.

tip-120

A CLI is an AI program that runs from a computer terminal, and a TUI is the text-based screen it displays there. AgEnD sends messages into that screen, which users can inspect through View or from a computer terminal.

tip-121

Use `/ctx` to check the current instance, backend, model, and available context estimate. Some backends cannot report a percentage.

tip-122

Use `/model` without an argument to open the model selector. Administrators can use `/model <name>` to request a specific model.

tip-123

AgEnD passes a safely formed model name to the backend even when its local pattern does not recognize it. The backend remains the authority and may reject it.

tip-124

Use `/effort` without an argument to inspect available reasoning levels. Administrators can use `/effort <level>` when the backend and model support that level.

tip-125

Reasoning effort changes how much work a supported model spends thinking; it does not change the backend or guarantee a better answer.

tip-126

Use `/compact` when the context is crowded but the conversation should continue. Backend behavior differs; Antigravity maps this action to a full clear.

tip-127

Use `/clear` to reset the conversation on a supported backend. It is administrator-only and asks for confirmation because prior context is removed.

tip-128

Use `/cancel` or the Cancel button to interrupt the current turn. It also discards messages queued before the cancellation, but keeps messages arriving afterward.

tip-129

Use `/pause` on an idle non-General instance to save resources. General cannot be paused because Fleet coordination must remain available.

tip-130

Use `/wake` to start a paused instance immediately. Sending a normal message to a paused instance can also begin its wake process.

tip-131

Use `/restart` only when the entire Fleet should restart. Ask General for an instance-specific restart when one Agent is unhealthy.

tip-132

Use `/update` after active work reaches a safe point. Updating installs the selected AgEnD release and then restarts the fleet.

tip-133

Use `/usage` to view available subscription metrics for backends used by running or paused instances. No data can mean unavailable telemetry, not zero usage.

tip-134

Use `/dashboard` to obtain current View and Settings links. Links containing an access token should be treated like a password and not shared publicly.

tip-135

Use `/status` for an administrator-only fleet summary, including running, paused, stopped, and crashed instances.

tip-136

Use `/sysinfo` to collect host and version details for an environment-specific problem report.

tip-137

Use `/doctor` in General to check configured Backends. Run `agend doctor` from a trusted computer terminal for broader service and connection checks.

tip-138

Use `/tips` to request another tip, `/tips off` to stop daily delivery, and `/tips on` to enable it again.

tip-139

Use `/steer <message>` to redirect an active turn on Claude Code, Codex, or Grok. Unsupported backends return an explicit message.

tip-140

Use `/btw <message>` for a side question on Claude Code without asking it to abandon the current task. Other backends report it as unsupported.

tip-141

From General, administrators can use `/pause <instance>` or `/wake <instance>` to target a named Agent instead of opening its conversation first.

tip-142

Use `/save <name>` only with Kiro CLI or Claude Code. Kiro saves a chat and Claude Code exports a Markdown file; other backends report unsupported.

tip-143

In a ClassicBot conversation, `/start` creates or resumes its Agent and `/stop` removes that channel binding. Both are administrator actions.

tip-144

Use `/collab` as an administrator to toggle whether bot messages may participate in a configured fleet conversation. Access rules still apply.

tip-145

Settings stages edits until Apply is pressed. Review the pending changes before applying them, especially when a cold field will restart an instance.

tip-146

Backend is a cold setting. Changing it in Settings selects a different Backend and restarts the affected instance.

tip-147

Working directory is a cold setting. Confirm the destination exists and contains the intended project before applying it in Settings.

tip-148

Model overrides can be changed with `/model` or Settings. If no override is needed, leave the field unset so normal defaults apply.

tip-149

Tool progress controls how much live tool history appears under the working message. Choose off, standard, or verbose in Settings; it applies without restarting.

tip-150

Display name changes how an instance is presented without changing its internal name. It is a hot setting in Settings.

tip-151

Description and tags document an instance's responsibility and help General choose it. Both can be edited in Settings without a restart.

tip-152

Auto-pause is an optional idle timer. It is disabled when set to zero and can be enabled or adjusted in Settings without restarting the instance.

tip-153

Warm cap limits how many non-General instances remain active. Ask General to adjust it, or change `defaults.warm_cap` in fleet.yaml under advanced configuration and reload; existing instances do not need to restart.

tip-154

Log level controls diagnostic detail. It is a hot setting, but more detailed logs may contain project or routing information.

tip-155

Channel binding selects which configured bot identity a fleet instance uses. Set it in Settings when several bot accounts share a server or group.

tip-156

Kiro UI controls whether Kiro starts with its interactive interface. It is backend-specific and changing it restarts the instance.

tip-157

Terminal columns and rows define the logical screen size seen by the Backend. Change them cautiously because narrow layouts can hide or wrap permission prompts.

tip-158

Settings reads effective values after defaults are applied, while saved instance entries can omit repeated defaults. Missing repeated fields are not necessarily lost settings.

tip-159

A Schedule is a message delivered later or repeatedly. Ask General to create it for the instance responsible for the work.

tip-160

A recurring schedule uses a cron expression, which describes a pattern such as every day at 09:00. A one-time schedule uses an ISO date and time, such as `2026-08-25T09:00:00+08:00`; use only one form per schedule.

tip-161

A timezone tells a recurring schedule which local clock to follow. For example, `Asia/Taipei` makes “every day at 09:00” mean 09:00 in Taiwan rather than the server's local time.

tip-162

A silent schedule hides the trigger message from the conversation, but the assigned Agent may still post a result when the task requires one.

tip-163

A Team is a reusable group of instances for recurring collaboration, such as implementation plus review. Ask General to manage team membership.

tip-164

A shared Decision records an agreed Fleet-wide choice so Agents can reuse it after restarts. Ask General to record durable architectural decisions.

tip-165

Instances can exchange selected questions and results, but their full conversation histories and working directories are not automatically shared.

tip-166

Ask General to parallelize only independent work. Two Agents editing the same files should coordinate ownership or work in separate copies.

tip-167

A sender-side timeout—a notice that waiting for a reply took too long—does not prove a cross-instance message failed. Avoid resending solely because the sender stopped waiting.

tip-168

When an Agent waits for a password or confirmation, AgEnD can notify General. Review the visible prompt before authorizing any manual input.

tip-169

Do not send passwords, access tokens, or private keys through chat. Enter secrets only in a trusted terminal when an authorized prompt requires them.

tip-170

Delivery-status reactions mean ⏳ queued, 👀 delivered, ✅ turn confirmed, and ❌ failed. They describe transport, not whether the answer is correct.

tip-171

Avoid using 👀, ⏳, ✅, or ❌ as ordinary reactions because AgEnD reserves them for delivery status.

tip-172

Replying to an earlier message gives the Agent quoted Context. Supported Discord replies can also include images from the referenced message.

tip-173

Attachments are copied to a local inbox before delivery. The Agent receives a local file path, so sensitive files should be shared only with an appropriate instance.

tip-174

A permission prompt is a safety boundary from the Backend. Read the requested file or command scope before approving it.

tip-175

After sixty intermediate tips are dismissed, AgEnD offers an Advanced Tips unlock button. An administrator can also enable them with `/tips advanced on`.

tip-176

Claude Code supports subagents, which are focused helper AIs inside the same CLI. They can research or review while the main agent coordinates the result.

tip-177

Claude Code permission modes decide whether file and command actions are allowed, denied, or require approval. Choose a mode that matches the project's risk.

tip-178

Claude Code can resume saved sessions, but continuity depends on the same project path and available session data.

tip-179

Claude model families usually trade capability, speed, and cost differently. Use the current account selector for exact availability rather than relying on a static list.

tip-180

Opus is generally aimed at demanding work, Sonnet at balanced work, and Haiku at lighter faster work. Current provider documentation remains authoritative.

tip-181

Codex uses a sandbox, which is a boundary around model-generated commands. Sandbox scope and approval policy are separate controls.

tip-182

Codex accepts queued input while it is working. Follow-up messages can enter its native queue instead of waiting for an idle gap.

tip-183

Codex Skills are reusable instruction packages discovered when relevant. They keep detailed workflows outside the always-loaded conversation.

tip-184

A custom provider is an alternate model service configured in Codex. AgEnD can select it, while its URL and credential environment variable remain in Codex configuration.

tip-185

Custom Codex models may show a metadata warning because built-in model details are absent. The provider's actual response determines whether the model works.

tip-186

Kiro Specs are project documents that organize requirements, design, tasks, and execution. They are useful when a feature benefits from an explicit plan.

tip-187

Kiro Steering files are persistent project guidance. They can keep conventions available without repeating them in every conversation.

tip-188

Kiro Skills use progressive disclosure: the CLI first sees a short description and loads detailed instructions only when relevant.

tip-189

Kiro's `auto` model mode lets the CLI choose dynamically. Set `model: auto` explicitly only when it should override a fleet-level model default.

tip-190

Grok can provide web search and page retrieval when enabled by the installed CLI, account, and policy. Availability should be checked in the current environment.

tip-191

Grok supports steering through `/steer`, but its available models and tools can vary by account. Treat the CLI's current list as authoritative.

tip-192

OpenCode distinguishes primary agents for main work from subagents for focused tasks. Project configuration can change which agents and permissions are available.

tip-193

OpenCode model names commonly use a provider/model form. Check OpenCode's current model list instead of assuming that a bare model name is accepted.

tip-194

OpenCode provider definitions belong in its own configuration. AgEnD selects a model from what OpenCode exposes rather than storing provider credentials.

tip-195

OpenCode does not currently expose an AgEnD `/effort` mapping. Use model or agent settings supported by OpenCode instead.

tip-196

Antigravity supports multi-step work and tool calls through its terminal interface. Its account and installed version determine available models and integrations.

tip-197

Antigravity has no separate summarizing compact command in AgEnD. Both `/compact` and `/clear` use its full conversation-clear action.

tip-198

Different GPT variants can target different capability, latency, and cost points. The names visible to the current CLI account are the source of truth.

tip-199

Automatic model selection may choose differently between turns. Pin a model only when repeatability matters more than flexibility.

tip-200

A model available to one account may be unavailable to another. Verify access with the target backend before changing several instances at once.

advanced

Advanced

Configuration, reliability, and troubleshooting

100 tips
tip-201

Before a migration or bulk edit, copy fleet.yaml and classicBot.yaml outside the working path. Keep the backup until a representative restart and message round trip succeed.

tip-202

Instance entries may omit values inherited from defaults. Compare effective configuration, not only raw YAML, when diagnosing what a daemon received.

tip-203

AgEnD removes redundant default-valued leaves when saving fleet.yaml, while retaining identity fields such as backend, model, working_directory, topic_id, and backend_options.

tip-204

Lossless YAML editing preserves unrelated structure and comments where possible, but a comment attached only to a removed node may have no node to remain on.

tip-205

Run `agend validate` after manual YAML edits and before reload. Validation catches schema errors without requiring a fleet restart.

tip-206

Hot fields are reconciled in place, while cold fields restart affected instances. Check the Settings change summary before applying a mixed patch.

tip-207

A SIGHUP reload updates the running fleet from validated configuration; it is not equivalent to restarting every CLI process.

tip-208

Backend, working_directory, tool_set, lightweight, and backend_options are cold instance fields. Changing them can recreate the affected CLI process.

tip-209

Tool progress, display name, description, tags, log level, and auto-pause settings are designed for hot reconciliation. Verify the daemon acknowledged the update when diagnosing stale behavior.

tip-210

Use per-instance overrides only when behavior must differ from defaults. Fewer duplicated values make later default changes and reviews easier to reason about.

tip-211

A backend option is interpreted only by its matching backend. For example, `backend_options.codex.provider` selects a provider but does not define that provider's endpoint or credentials.

tip-212

Codex custom-provider definitions belong in Codex config, and secrets should be referenced through environment variables available before the fleet service starts.

tip-213

OpenCode provider definitions belong in opencode.json, while AgEnD's model field should use the identifier exposed by OpenCode, commonly `provider/model`.

tip-214

Treat model-name compatibility checks as hints. The CLI remains the source of truth, so AgEnD passes configured model names through instead of silently falling back.

tip-215

An unset instance model first inherits defaults.model. To request a backend's own default while a fleet model default exists, configure the backend-specific default explicitly where supported.

tip-216

Kiro's `auto` is an explicit model choice. Set it on the instance when it must override a non-auto defaults.model value.

tip-217

Model failover reacts to supported usage telemetry and applies on a later rotation. It cannot replace a model safely in the middle of an active turn.

tip-218

Cost guards are limited by provider telemetry. Missing, cached, or delayed usage data reduces enforcement precision and should be visible in operational expectations.

tip-219

Usage results are cached to reduce provider calls. Use the View panel's Refresh control when an immediate post-login or post-renewal fetch is required.

tip-220

A provider absent from `/usage` may simply have no running or paused instance. Usage visibility follows effective backends, not every installed CLI.

tip-221

Keep bot tokens, dashboard tokens, provider keys, and exported sessions out of repositories and shared workspaces; each requires its own rotation procedure.

tip-222

When a CLI supports an environment-key reference, store the secret in the service environment rather than fleet.yaml or a provider config committed to source control.

tip-223

Files such as web.token and per-instance state should remain readable only by their owner. Copying them into a project can expose them through backups, diffs, or agents.

tip-224

The persistent web token keeps dashboard URLs valid across restarts. To invalidate existing links, remove the token file, restart the fleet, and request a new dashboard URL.

tip-225

A dashboard URL is usable only after the health server is listening. A port conflict should fail closed instead of publishing a URL backed by the wrong process.

tip-226

Channel allowlists are authorization boundaries, not display filters. After changing access rules, test both an allowed identity and a rejected identity.

tip-227

Before changing a locked channel's allowed_users, ensure at least one administrator remains. An empty locked allowlist can remove every administrative path.

tip-228

Nonce-bound confirmation buttons are tied to their adapter, chat, thread, message, and administrator identity. A copied callback should not authorize another context.

tip-229
