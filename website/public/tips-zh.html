入門

日常對話與核心概念

100 條提示
tip-001

instance = Agent = 一個可以對話的 AI CLI，例如 Kiro CLI、Claude Code、Codex、Antigravity、Grok 或 OpenCode。

tip-002

Backend = 背後驅動 Agent 的 AI 服務，例如 Claude Code、Codex、Kiro CLI。不同 Backend 有不同特性和模型。

tip-003

一個 Agent = 一份獨立對話；其他 Agent 不會自動知道這裡談過什麼。

tip-004

Fleet = 同一套 AgEnD 管理的全部 Agent；重啟 Fleet 會影響所有未暫停的 Agent，不只目前聊天室。

tip-005

General = 協調工作的 Agent；需求跨專案時，可請它挑選 Agent、拆工作或彙整結果。

tip-006

Topic、Thread 或 Channel = 綁定某個 Agent 的聊天室位置；在那裡發訊息就會交給該 Agent。

tip-007

工作中 = Agent 正在處理工作；閒置 = 已準備接下一則訊息。

tip-008

Paused = Agent 暫時休眠但保留已存 Session；再傳訊息通常會開始喚醒它。

tip-009

Stopped = AI CLI 正常結束；Crashed = 非預期退出，或多次恢復仍沒有成功。

tip-010

先講想要的結果，再補限制與輸出格式，Agent 會更快抓到重點。

tip-011

好需求 = 目標 + 重要限制 + 完成條件；寫清楚可以少來回確認。

tip-012

在意文風時，直接附一小段範例；範例通常比長篇解釋更快讓 Agent 抓到語氣。

tip-013

要改先前指示時，直接說哪一條被取代；不說清楚，舊指示與新指示可能同時被保留。

tip-014

`/steer <訊息>` = 改變正在執行中的方向；目前支援 Claude Code、Codex 與 Grok。

claude-codecodexgrok
tip-015

`/steer` 適合修正目前任務，不適合塞入另一件工作；無關需求另外發一則會更清楚。

claude-codecodexgrok
tip-016

`/btw <問題>` = 對 Claude Code 問題外話，不會取代正在做的主要任務。

claude-code
tip-017

`/btw` 和 `/steer` 不一樣：BTW 是題外問答，Steer 是改目前工作的方向。

claude-code
tip-018

Agent 忙碌時，新訊息可能先排隊；晚一點處理不代表訊息被蓋掉。

tip-019

回覆較慢時先不要重送排隊中的需求；送兩次可能讓 Agent 真的做兩次。

tip-020

取消按鈕或 `/cancel` = 中斷這次運行，並清掉按下前排隊的訊息（取消後才到的新訊息會保留）；訊息已進入 Context，已執行多少取決於取消時機。

tip-021

AgEnD = 把 Telegram 或 Discord 聊天室連到一個或多個 Agent 的系統。

tip-022

Cancel 也會清掉該 Agent 尚未送入的舊訊息，因此排隊中的跨 Agent 或排程工作不會立刻接著啟動。

tip-023

Cancel 之後才傳的新訊息 = 新工作，不會跟舊佇列一起被清掉。

tip-024

⏳ = 排隊、👀 = 已送達、✅ = 回合已確認、❌ = 失敗；這些符號只表示投遞狀態，不代表回答品質。

tip-025

投遞符號可能比 Agent 回覆更早出現；它是 AgEnD 的狀態，不是 Agent 寫的答案。

tip-026

訊息停在 ⏳ 時先等一下再重送；它可能只是在等 Agent 準備好。

tip-027

訊息顯示 ❌ 時先查 Agent 狀態；盲目重試可能把真正的啟動、登入或連線問題蓋掉。

tip-028

需要 Agent 確認新需求指的是哪段文字、檔案或圖片時，直接回覆原訊息。

tip-029

引用回覆會帶入原文字；再補一句要怎麼處理，Agent 比較不會猜錯。

tip-030

彼此相關的需求整理成一則最清楚；無關需求分開傳，之後比較好追蹤。

tip-031

長訊息先把主要需求放在前幾行；細節接著補，不要讓目標埋在最後。

tip-032

長工作想確認進度時，直接問一則簡短進度，不必把整份需求重貼。

tip-033

Agent 追問時先補缺少的資訊；同時插入新任務，兩件事都可能變得不清楚。

tip-034

回答有誤時，直接引用要改的句子或數值；只說重做通常會多繞一圈。

tip-035

長討論結束時，可請 Agent 整理決定事項 + 未完成項目；這份摘要也比較容易交給另一個 Agent。

tip-036

檔案和說明放在同一則訊息，Agent 才會把它們當成同一個需求。

tip-037

傳圖片時順便說要看什麼；只丟圖片會讓 Agent 猜問題。

tip-038

傳文件時指出頁面、段落或問題；可以避免 Agent 先讀一堆無關內容。

tip-039

一次附多個檔案 = 說明每個檔案的用途；只看檔名不一定分得出輸入、參考與預期結果。

tip-040

Telegram 語音會以音訊送入；若有啟用語音轉文字，Agent 也會收到逐字稿。

tip-041

語音裡的姓名、代碼與數字容易聽錯；需要精確時再打一遍文字。

tip-042

Telegram 貼圖有對應表情時會變成該 emoji；沒有對應表情時會變成 `[Sticker]`。

tip-043

貼圖片網址仍然只是連結；需要 Agent 看圖片內容時，請直接附上圖片檔。

tip-044

在支援的 Discord 回覆中，回覆一則帶圖訊息時，被引用的圖片也會送給 Agent。

tip-045

重要指示請用文字；只按 emoji 可能只會被記成回應，不會啟動工作。

tip-046

同一聊天室有多個 bot 時，要標記指定的 bot；不然可能由錯的身份回覆，也可能沒人處理。

tip-047

Tool progress = Agent 正在做什麼的簡短歷程；啟用後，完成時按鈕會消失，但歷程會保留。

tip-048

詳細進度可能包含指令預覽；分享截圖前先檢查私密路徑或數值。

tip-049

Interactive prompt = AI CLI 正在等密碼、權限、Y/N 或 Enter；AgEnD 會通知 General，不會自己猜答案。

tip-050

AgEnD 不會自動輸入密碼；任何確認都先看清楚再允許。

tip-051

`/dashboard` = View、Settings 與 Web UI 的網址；編輯網址帶有存取 token，所以這是管理員指令。

tip-052

`http://localhost:19280/view` 的 View = 預設本機即時畫面；localhost 代表通常只能在安裝 AgEnD 的電腦開啟。

tip-053

View 會顯示 Agent 狀態、可取得時的 Context 百分比與即時工作畫面；可用來確認工作是否真的有在跑。

tip-054

View 的 AI Usage 面板 = 目前有 Agent 使用中的 Backend 訂閱量；沒在用的 Backend 會隱藏。

tip-055

`/usage` = 不開 View，直接在聊天室查看可取得的 AI 訂閱用量。

tip-056

`/usage` 顯示 no data 不一定是額度歸零；也可能是帳號未登入、token 正在更新，或服務沒有提供用量資料。

tip-057

用量資料會短暫快取，避免頻繁查詢供應商；需要最新數字時，可按 View 裡的重新整理。

tip-058

Quota = 帳號或訂閱包含的可用量；出現警告時，本次回答可能仍會完成，但後續工作可能被擋。

tip-059

`/status` = Fleet 總覽，包含 Agent 狀態與重要健康資訊。

tip-060

`/sysinfo` = AgEnD、作業系統、執行環境與程序資訊；回報環境問題時很有用。

tip-061

Context = 這段對話目前能記住的內容量。滿了就需要壓縮（`/compact`）或重新開始（`/clear`）。

tip-062

Context 接近滿 = 舊細節可能被壓縮或遺失；長工作快到上限前先請 Agent 寫交接摘要。

tip-063

Claude Code 的長 Session 可用 `/ctx` 留意空間；接近上限前用 `/compact` 或寫交接摘要，可降低細節遺失。

claude-code
tip-064

Codex 通常會自行管理對話壓縮，但重要決定仍建議整理摘要，不要假設每個細節都會一直保留。

codex
tip-065

`/compact` = 在 Backend 支援時縮短目前 Context 並盡量保留重點；不同 Backend 的效果不完全相同。

tip-066

`/model` = 顯示目前 Backend 探測到的可選模型；選擇後會切換該 Agent 的模型，並保存供重啟後使用。

tip-067

模型清單會在 AgEnD 啟動時探測；新模型沒出現時可重啟 AgEnD，Discord 也可用 `/model refresh` 直接刷新。

tip-068

`/effort` = 支援模型的思考強度；強度較高可能更適合難題，但通常也更花時間與額度。

tip-069

`/save <名稱>` = 匯出目前對話供之後參考；AgEnD 目前支援 Kiro CLI 與 Claude Code。

claude-codekiro-cli
tip-070

Discord 的 Kiro ClassicBot 可用 `/load <名稱>` 載入先前由 Kiro 儲存的對話；這不是所有 Backend 都能用的通用還原指令。

kiro-cli
tip-071

Claude Code 的 `/save` 會匯出 Markdown 檔供參考；AgEnD 沒有對應的 `/load` 可把它還原成 Claude Session。

claude-code
tip-072

Kiro 的 `/save` 會轉成 `/chat save`；之後的 Discord `/load` 只適用 Kiro ClassicBot 流程。

kiro-cli
tip-073

管理員使用 `/update` = 從目前的穩定版或 Beta 更新通道安裝最新 AgEnD，完成後重啟 Fleet。

tip-074

管理員使用 `/restart` = 優雅重啟整個 Fleet，不是只重啟目前 Agent。

tip-075

每次重啟都會喚醒所有未暫停的 Agent；啟動需要時間，後續恢復或摘要也可能多用 token，因此不要頻繁重啟 Fleet。

tip-076

不需要立刻恢復的 Agent，可在 update 或 restart 前先 Pause；Fleet 啟動時會跳過已暫停的 Agent。

tip-077

管理員使用 `/pause` = 讓 Agent 休眠；`/wake` = 再次啟動。General 本身不能被暫停。

tip-078

Settings 可以設定自動暫停時間；`0` 代表停用，讓不用的 Agent 休眠可減少背景程序與重啟負擔。

tip-079

修改自動暫停、進度詳細度、顯示名稱、描述、標籤或 Log Level 會即時生效，不會重啟 Agent。

tip-080

在 Settings 修改 Backend、工作目錄或 Tool Set，以及在設定檔修改 Backend Options，都屬於冷設定，會重啟 Agent。

tip-081

ClassicBot = 常駐在一般 Discord Server/Channel 或 Telegram Group 裡的 Agent，不是預先建立的 Fleet Topic。

tip-082

ClassicBot 預設不會對每段聊天主動插話；可用 `/chat`，在 Telegram 群組或協作聊天室標記 bot 也會觸發。

tip-083

ClassicBot 觸發時會附上近期聊天紀錄；預設是最近 5 行，不是整個頻道歷史。

tip-084

要使用 ClassicBot，先把 bot 邀進 Discord Server 或 Telegram Group，再由管理員在目標聊天室執行 `/start`。

tip-085

ClassicBot 的 `/start` 會用 ClassicBot 預設 Backend 建立或恢復該聊天室的 Agent；之後可到 Settings 修改 Backend。

tip-086

ClassicBot 的 `/stop` 會移除該聊天室綁定；確定這個 Channel 不再需要 Agent 時才使用。

tip-087

ClassicBot 聊天室與 Fleet Topic 的路由不同；指令要在目標 Agent 所屬的聊天室執行。

tip-088

同一個協作聊天室有多個 bot = 標記正確 persona 或使用它的 slash command；每個 bot 可以各自擁有不同的 ClassicBot Agent。

tip-089

登入過期訊息 = 重新登入該 Backend；登入尚未修好前重送同一需求，通常只會再次失敗。

tip-090

模型不支援訊息 = 目前 Backend 或帳號拒絕該模型；請改選清單中的模型，不要期待系統默默換回預設。

tip-091

密碼或 Y/N 提示停住時會通知 General；AgEnD 不會自動代答。

tip-092

回報問題時附上時間 + instance 名稱 + 傳了什麼 + 發生什麼；這四項最容易對上 Log。

tip-093

View 頁面的截圖會顯示 Agent 即時畫面；分享前先檢查專案名稱、路徑或 Secret。

tip-094

AI 回答可能出錯；指令、價格、權限與其他高影響資訊都要確認後再執行。

tip-095

敏感工作 = 只提供本次需求必要的檔案與數值；聊天匯出與截圖可能比預期包含更多資訊。

tip-096

`/tips` = 在目前聊天室再顯示一則可用 Tip；不一定要到 General 執行。

tip-097

✅ 我知道了 = 保留 Tip 原文、收起按鈕，之後不再顯示同一則。

tip-098

❓ 看不懂 = 保留 Tip 原文、記錄回饋，之後仍可能再次出現同一則。

tip-099

`/clear` = 確認後清空目前 Context；這個動作不能復原，但專案檔案與 AgEnD 指示仍會保留。

tip-100

有用的 Tip 應該直接說明對你有什麼影響；看不出實際後果時就按「看不懂」。

intermediate

中階

指令、Backend 與協作

100 條提示
tip-101

instance（單一且獨立的 Agent）各自保有自己的對話，也可以分別負責不同專案。

tip-102

Fleet（由 AgEnD 一起管理的一組 Agent）可統一執行管理操作；整體操作可能影響所有運行中的 Agent。

tip-103

General（協調工作的 Agent）可協助選擇合適的 Agent、拆分互不相依的任務，或管理整個 Fleet。

tip-104

Backend（決定 Agent 使用哪種 AI 服務）可以是 Claude Code、Codex、Kiro CLI、Grok、Antigravity 或 OpenCode。

tip-105

Context（目前對話可保留的資訊量）有容量限制，也不是永久的專案儲存空間。

tip-106

MCP（讓 AI 使用回覆、檔案與協作工具的通道）通常不需由使用者直接操作，只要說明預期結果即可。

tip-107

Model（Backend 內實際選用的 AI 模型）若未指定，通常會沿用 Fleet 或帳號的預設值。

tip-108

Session（Backend 保存的對話狀態）能否在重啟後延續，取決於該 Backend 的支援方式。

tip-109

工作目錄（Agent 讀取與修改專案時使用的目錄）可以共用，但多個 Agent 同時修改時可能產生衝突。

tip-110

ClassicBot（在一般 Telegram 或 Discord 對話中建立持續 Agent 的模式）不需要預先配置 Fleet 對話。

tip-111

Adapter（AgEnD 與某個訊息 Bot 帳號的連線）在多 Bot 環境中可讓 Agent 固定使用指定身分回覆。

tip-112

Telegram 以 Topic 分隔 Fleet 對話，Discord 則可能使用 Channel 或 Thread；這些空間在 AgEnD 中都用來把訊息送到正確的 Agent。

tip-113

Tool（AI 可呼叫的操作，例如讀取檔案或發送回覆）是否可用，取決於 Backend 與權限設定。

tip-114

Delivery queue（等待安全時機送入忙碌 Agent 的訊息佇列）代表訊息延後處理，不一定是遺失。

tip-115

閒置（看起來可接收輸入）與工作中（偵測到正在處理工作）是 AgEnD 觀察到的狀態，不代表回答品質。

tip-116

Paused（暫停）表示 AgEnD 刻意停止 Agent 的 CLI 程序，但保留設定，之後仍可喚醒。

tip-117

Stopped（正常停止）與 Crashed（非預期退出或多次恢復失敗）原因不同，可請 General 協助檢查。

tip-118

Settings（常用設定的網頁編輯器）會即時套用 Hot 設定；Cold 設定會改變啟動方式，因此會重啟受影響的 Agent。

tip-119

View（在瀏覽器顯示 Agent 即時終端畫面的頁面）適合查看互動提示或工作進度。

tip-120

CLI（在電腦終端中運行的 AI 程式）會顯示 TUI（以文字構成的操作畫面）；AgEnD 會把訊息送進該畫面，使用者可透過 View 或電腦終端查看。

tip-121

使用 `/ctx` 可查看目前的 instance、Backend、Model 與可取得的 Context 估計值；部分 Backend 無法提供百分比。

tip-122

不帶參數的 `/model` 會開啟模型選單；管理員可用 `/model <名稱>` 指定模型。

tip-123

即使 AgEnD 的本機規則不認得某個格式安全的模型名稱，仍會交給 Backend 判斷；Backend 可能接受，也可能回報不可用。

tip-124

不帶參數的 `/effort` 可查看推理強度選項；管理員可在 Backend 與 Model 支援時使用 `/effort <等級>`。

tip-125

Reasoning effort（推理強度）會調整支援模型投入思考的程度，不會切換 Backend，也不保證答案一定更好。

tip-126

Context 擁擠但仍要延續對話時可用 `/compact`；各 Backend 行為不同，Antigravity 會改為完整清除。

tip-127

支援的 Backend 可用 `/clear` 重設對話；此指令限管理員使用，且因先前 Context 會被移除而需要再次確認。

tip-128

使用 `/cancel` 或取消按鈕可中斷目前回合；按下前排隊的訊息會被丟棄，之後到達的新訊息則會保留。

tip-129

可對閒置且非 General 的 Agent 使用 `/pause` 以節省資源；General 必須維持協調能力，因此不能暫停。

tip-130

使用 `/wake` 可立即啟動 Paused Agent；傳送一般訊息也能觸發喚醒流程。

tip-131

只有整個 Fleet 都需要重啟時才使用 `/restart`；若只有一個 Agent 異常，應請 General 單獨重啟該 Agent。

tip-132

應等進行中的工作到達安全點後再用 `/update`；更新會安裝選定的 AgEnD 版本，接著重啟整個 Fleet。

tip-133

使用 `/usage` 可查看 Running 或 Paused Agent 所用 Backend 的訂閱資料；無資料可能代表無法取得統計，不等於用量為零。

tip-134

使用 `/dashboard` 可取得目前的 View 與 Settings 連結；含存取 Token 的連結應視同密碼，不要公開分享。

tip-135

管理員可用 `/status` 查看 Fleet 摘要，包括 Running、Paused、Stopped 與 Crashed Agent。

tip-136

問題可能與執行環境有關時，可用 `/sysinfo` 收集主機與版本資訊。

tip-137

在 General 使用 `/doctor` 可檢查已設定的 Backend；更完整的服務與連線檢查需從可信任的電腦終端執行 `agend doctor`。

tip-138

使用 `/tips` 可立即查看另一則提示；`/tips off` 可停止每日投遞，`/tips on` 可重新開啟。

tip-139

使用 `/steer <訊息>` 可在 Claude Code、Codex 或 Grok 工作途中調整方向；不支援的 Backend 會明確回報。

tip-140

tip-201

進行 migration 或大量修改前，應把 fleet.yaml 與 classicBot.yaml 備份到工作路徑之外；直到代表性 instance 完成重啟與訊息往返測試後再移除備份。

tip-202

instance entry 可以省略從 defaults 繼承的值；診斷 daemon 實際收到的設定時，應比對 effective configuration，而不只查看原始 YAML。

tip-203

AgEnD 儲存 fleet.yaml 時會移除與 defaults 重複的 leaf values，但會保留 backend、model、working_directory、topic_id 與 backend_options 等識別欄位。

tip-204

Lossless YAML 編輯會盡量保留無關結構與註解；若註解只附著在被移除的節點上，該註解可能無法保留。

tip-205

手動修改 YAML 後、reload 前應先執行 `agend validate`；它可在不重啟 Fleet 的情況下找出 schema 錯誤。

tip-206

Hot fields 會原地 reconcile，cold fields 則會重啟受影響的 instance；套用混合變更前，應先查看 Settings 的變更摘要。

tip-207

SIGHUP reload 會以通過驗證的設定更新執行中 Fleet，並不等同於重啟所有 CLI process。

tip-208

Backend、working_directory、tool_set、lightweight 與 backend_options 屬於 cold instance fields；變更後可能重建受影響的 CLI process。

tip-209

Tool progress、display name、description、tags、log level 與 auto-pause 設定可 hot reconcile；若行為未更新，應確認 daemon 是否已接收變更。

tip-210

只有在 instance 行為確實需要不同於 defaults 時才設定 override；減少重複值可讓後續 default 變更與 review 更容易判讀。

tip-211

Backend option 只由對應 Backend 解讀；例如 `backend_options.codex.provider` 只負責選擇 provider，不會定義 endpoint 或 credentials。

tip-212

Codex custom provider 應在 Codex config 中定義；密鑰宜透過 Fleet service 啟動前已存在的環境變數提供。

tip-213

OpenCode provider 應在 opencode.json 中定義；AgEnD 的 model 欄位應使用 OpenCode 提供的識別字，通常是 `provider/model`。

tip-214

Model name compatibility check 只應視為提示；CLI 才是最終依據，因此 AgEnD 會傳遞已設定的 model name，而不會靜默退回預設值。

tip-215

instance 未設定 model 時會先繼承 defaults.model；若 Fleet 已有 model default，而某 instance 要使用 Backend 自己的預設，應在支援時明確設定該 Backend 的預設值。

tip-216

Kiro 的 `auto` 是明確的 model 選擇；若要覆寫非 auto 的 defaults.model，應在該 instance 設定 `model: auto`。

tip-217

Model failover 依賴支援的 usage telemetry，並在後續 rotation 套用；它不會在進行中的回合中途安全替換 model。

tip-218

Cost guard 受 provider telemetry 限制；usage data 缺失、快取或延遲時，執行精度會下降，營運預期應納入這項限制。

tip-219

Usage 結果會快取以減少 provider calls；登入或更新 token 後需要立即重取時，可使用 View 面板的 Refresh。

tip-220

Provider 未出現在 `/usage` 時，可能只是目前沒有 running 或 paused instance 使用它；用量顯示依 effective Backend，而不是所有已安裝 CLI。

tip-221

Bot token、dashboard token、provider key 與匯出的 session 都不應放入 repository 或共用 workspace，且各自需要不同的 rotation 程序。

tip-222

CLI 支援 environment-key reference 時，應把 secret 放在 service environment，而不是 fleet.yaml 或會提交到版控的 provider config。

tip-223

web.token 與 per-instance state 等檔案應只允許 owner 讀取；複製到 project 後，可能經由備份、diff 或 agent 暴露。

tip-224

Persistent web token 會讓 dashboard URL 在重啟後仍有效；若要使既有連結失效，應移除 token file、重啟 Fleet，再取得新的 dashboard URL。

tip-225

Dashboard URL 只有在 health server 開始 listening 後才可使用；遇到 port conflict 時應 fail closed，避免發布指向錯誤 process 的 URL。

tip-226

Channel allowlist 是 authorization boundary，不是顯示篩選器；變更 access rules 後，應同時測試允許與拒絕的 identity。

tip-227

修改 locked channel 的 allowed_users 前，應確認至少保留一位管理員；空的 locked allowlist 可能移除所有管理操作路徑。

tip-228

使用 nonce 的確認按鈕會綁定 adapter、chat、thread、message 與管理員 identity；複製 callback 不應能授權另一個情境。

tip-229

Multi-world Fleet 中，若第一個 adapter 不是預期 persona，應為 General 與 fleet-topic instance 明確設定 channel_id。

tip-230

ClassicBot routing 依自身 channel records 決定；在多 bot 協作頻道中，不應把 fleet-topic 的 adapter canonicalization 套用到 ClassicBot reply。

tip-231

Terminal columns 與 rows 同時影響 TUI layout 和 capture wrapping；修改 geometry 後，應用真實 pane sample 驗證 ready、permission 與 error detection。

tip-232

Terminal validator 會限制保守的 geometry 範圍，因為過窄 pane 可能使 permission prompt 換行到無法辨識。

tip-233

AgEnD 會固定 tmux window size，並讓 control client 忽略尺寸；兩層保護都需要，才能讓 logical geometry 在 reconnect 後保持穩定。

tip-234

Mouse mode 只在 AgEnD 的 tmux session 啟用；attach 後可捲動 scrollback，且不影響使用者其他 session。

tip-235

`capture-pane` 未合併 wrapping 時會讀取畫面實際行；因此即使邏輯文字相同，width 變更仍可能改變 parser input。

tip-236

Ready、busy 與 error pattern 都是針對 terminal text 的 heuristic；修改前應保留去識別化的真實 sample，並加入 production-path test。

tip-237

閒置誤判可能提早收回控制項或過早投遞 input；工作中誤判則可能延遲訊息並觸發 hang notification。

tip-238

週期性 statusline redraw 不一定代表工作；各 Backend 的 pane handling 應區分純顯示重繪與任務內容變化。

tip-239

hang_detector 應依實際 silent-work interval 調整，而不是任意設定很短的 timeout；重啟前先檢查 pane 與 process evidence。

tip-240

Interactive-prompt alert 會同時要求 prompt-like pattern 與穩定 output 時間，以降低 agent 只是討論密碼或確認操作時的誤報。

tip-241

限管理員使用的 `/raw <文字>` 會略過 AgEnD 的一般訊息包裝，直接送給 Backend；只有包裝會改變刻意輸入的 CLI 指令時才應使用。

tip-242

Special-key delivery 需要可寫入的 tmux control client；Enter 或 interrupt command 失敗時，應直接視為 command failure，而不是等後續 timeout。

tip-243

即使 Backend 有 native input queue，pasteLock 仍需序列化 terminal writes；native queue 不代表重疊 PTY paste 是安全的。

tip-244

Codex 可把 busy-time input 放入自身 queue，因此 AgEnD 對 Codex 略過閒置門檻，但仍保留首次投遞的 startup settle。

tip-245

Cancel 會透過 delivery epoch 使取消前已排隊的訊息失效；取消後抵達的新訊息使用新的 epoch，仍可正常投遞。

tip-246

tip-247

被替換的 IPC client 必須移除 listeners 並 destroy socket；只刪除 map entry 可能留下仍在處理 outbound message 的 orphan。

tip-248

Disconnect、overflow 與 close event 應在每個 client lifecycle 收斂成一次 disconnect，且 reconnect 應依 instance 序列化。

tip-249

若簡單訊息也持續出現重複回覆，應先檢查 client 與 socket 數量，再判斷是否與 rich-message rendering 或 model 有關。

tip-250

Schedule trigger metadata 必須包含 instance 設定的 adapter identity；否則重啟後的 reply 可能 fallback 到錯誤的 bot persona。

tip-251

Fleet singleton lock 保護的是 manager startup，不是單一 instance restart；per-instance restart serialization 仍是另一項必要保護。

tip-252

出現兩個 Fleet process 時，終止前應先收集 PID、parent PID、command line、lock owner、service state 與 listening ports。

tip-253

Service-managed Fleet 在 user service manager 無法連線時應 fail closed，而不是啟動未追蹤的 detached duplicate。

tip-254

透過 SSH 使用 Linux 時，缺少 D-Bus session 可能使 `systemctl --user` 無法使用，即使 unit file 已存在。

tip-255

`active` 與 `activating` 都應視為 service 已被占用；service query 結果不確定時，不應允許第二次 startup。

tip-256

Health-port conflict 可能代表 stale manager 或其他 service；更換 port 或停止 process 前，應先識別 listener。

tip-257

Recovery path 應依 instance 序列化，避免 health check、MCP recovery、manual restart 與 config reconcile 建立互相競爭的 replacement。

tip-258

Crash-loop protection 會在有限次重複失敗後停止自動恢復，並顯示 crashed 而非閒置；成功恢復後則必須清除 stale crash marker。

tip-259

Restart backoff 可限制 CLI 反覆 startup failure 時的資源消耗；診斷確定性的設定錯誤時，暫時停用 retries 可能較合適。

tip-260

MCP auto-restart 會等待符合條件的閒置狀態，並去除重複 restart request；由於 MCP child connection 由 CLI 掌握，因此需要重啟 instance。

tip-261

只有在 pane 可見文字適合轉送時才啟用 mcp_proxy_reply；regex redaction 無法保證移除所有專案特有 secret。

tip-262

Proxy reply 是 MCP 中斷後的最後備援 channel path，不是 source-of-truth transcript；應留意 terminal chrome 或不完整輸出。

tip-263

Session resume 由 Backend 掌控；AgEnD 可保留 identifier、workspace path 與 marker，但無法保證 CLI 升級後仍維持語意 continuity。

tip-264

OpenCode resume 應使用已記錄的 session identifier；global `--continue` 可能選到其他 directory 的最新 session。

tip-265

Claude Code project-session lookup 依賴編碼後的 workspace path；重新命名或移動 workspace 可能使既有 session 看起來不存在。

tip-266

Per-instance Codex home 會隔離 MCP configuration 與 instance decisions；把這些項目寫入共用 Codex config 會造成 cross-instance authorization risk。

tip-267

SQLite database file 不應與 active WAL、SHM 或 rollback-journal sidecar 分離；從其他 home 連入 sidecar 可能使 private database 無法使用。

tip-268

tip-269

tip-279

tip-280

tip-281

tip-282

tip-285

tip-286

tip-287

Silent schedule 會注入工作但不要求 channel reply；只有在刻意不需要 user-visible output 時才應使用。

tip-288

tip-289

Restart 後觸發的 schedule 仍需帶入 target instance 的 effective adapter 與 delivery epoch，才能維持 routing 與 cancellation 正確。

tip-290

Fleet decision 可保存持久的架構脈絡；過時 decision 應 supersede 或 retire，避免後續 agent 收到衝突指示。

tip-291

tip-292

tip-295

tip-296

tip-297

tip-298

安全 rollback 應同時恢復相容的 code 與 configuration；只 revert 一側可能留下 schema 或 behavior mismatch。

tip-299

tip-300
