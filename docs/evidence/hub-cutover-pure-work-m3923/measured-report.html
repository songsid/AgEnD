Less pure-work CPU; the 100 ms target remains out of reach

P+S reduced mean gross Hub CPU by 19.2% with one tab and 16.4% with three tabs versus a fresh #4614 baseline. It still costs 3,672.6 ms and 8,101.8 ms per send plus final answer, VM-normalized. Both capacity ramps pass only the tested one-user level. These are synthetic measurements, not a production capacity guarantee.

What changed, and what did not

P is one memo slot per role clock, keyed by the exact full raw marker and Hub id. A miss runs the full parser; only six frozen primitives are retained after success. Close clears the slot. Failures and policy/transport graphs are never memoized. Both passes retain every fresh SQL, registry, marker confirmation, independent floor, owner, currentness, time and live check.

S changes only audit() and the composed group-version callback to readVersion(). Both still execute the same checkedImage and uncertain/sticky-failure behavior; no production fallback, permit reuse, other version callback or owning reader was changed. The prototype is private; shipping remains the Leader’s decision.

Workload and budget

Fresh full native Hub source builds for #4614, P and P+S, with the same HTTP/TLS/SQL/signing/audit/private-floor and real link-currentness path. Synthetic directory returns immediately and completely; a controlled member receive seam avoids real Fleet/provider/native CLI traffic. Thirty people, eight Fleets, nine shares and thirty direct rooms with seventy answered turns each. One send plus a locally produced 20-second/40-chunk mock reply uses the supported whole final-answer frame; no per-token Hub frame was invented. Working/idle presence is coalesced at the existing five-second cadence. One versus three SSE subscribers verify exact final content, unread projection and eventual idle.

Each container: pins 0 and 2, aggregate quota 0.758 CPU, 1 GiB RAM/swap, Node heap 512 MiB, 128 PIDs, read-only root/code, internal-only network and no published ports. One container at a time, no host Fleet or frequency changes; guards stop above load 8 or below 8 GiB MemAvailable. CPU uses the supplied current VM factor 1.32; wall latency is not multiplied again. This is a calibrated budget approximation, not a physical GHz claim. Generator CPU is recorded separately but competes in the same cgroup. Setup/login and profile collection are excluded from primary/ramp measurement intervals.
