# Opted-in Fleet update receiver, M-3144

The Fleet independently admits the Hub's fixed request, persists consent against the exact pairing, checks the npm version/install permission/service mode/no-downgrade, tells the owner durably, and uses the existing updater only after the durable idle queue claims one launch. The launcher is stubbed in every test. No live updater, vendor, user Fleet or real install was driven.

Validation scopes:

- The receiver began with inert fail-first controls (no owner notice / no launch); startup reconciliation was then pinned separately. The final receiver and owner suites contain 29 distinct cases, passed across the affected runs: initial 27, boot-marker and held-consent additions. The receiver-only final run is recorded separately.
- One owned pinned TLS/WSS factory journey covers the real member factory, capability offer, consent report, request/waiting notice, one injected launch, terminal status and ACK, then fence/detach. Its Hub peer, directory and registry are inert. It first caught the actual missing consent report: fleet-info-v1 is Hub-only, so it cannot be looked up in the member's intersection. The final journey passes 1/1. This is not a live updater rehearsal or a combined production Hub-service journey.
- The existing member factory suite passes 9/9. The three adjacent recommendation/web-update/notices files have 51 cases; all passed across the saved runs after fixing the recommendation test's clock baseline. That pre-existing test compared a 7-day boundary against a timestamp sampled before an async notice write; pinning Date.now at the initial sample removes the timing gap, without sleeps.
- Three isolated reversals are caught: ignoring the owner session during an immediate claim, skipping startup settlement, and removing the chat callback's administrator gate. Each original was restored.

Startup settles claimed updating rows from the running version and exact local marker, retaining this boot's marker if ordinary startup clears it before the optional Hub mount. It never re-launches a claimed request. An independent launcher exiting zero does not prove completion: the bounded existing marker remains authoritative until completion/failure/startup. Accepted waiting work expires after 24h. Turning consent off is possible while the selected pairing is held. A 7-day request that expires before admission is reported without falsely telling the owner its agents were busy for 24h.

Owner endpoints are local signed-in administrator routes with ordinary CSRF. Header tokens, guest/read sessions and public gateways cannot grant consent. Request-bound Update now retains the existing explicit confirmation, resolves the frozen verified version server-side, and rechecks the current person/profile at launch. An expired request's explicit Update now is a new local update; its old Hub result remains expired. The chat button is checked against the current Fleet-admin namespace. Notice metadata is presentation; actions resolve the retained request again.

Rollback: withdraw the fleet-update-v1 offer / update host hooks to disable remote admission, retaining consent/request/status journals and accepted work. No existing updater or rollback engine is replaced. Actual service update / automatic rollback / beta.3-Hub fallback are proven in the later single phase-3 rehearsal, not here. Companion UI PR #3958 owns the consolidated Hub skill instructions and notice rendering.

Review delta: the runtime is unchanged since 6f818bd0. Three new receiver cases pin withdrawal after acceptance and local candidate refusal after unsuccessful registry checks. An additional owner HTTP case exercises the unverified expired-request button through /ui/update/start. These four affected cases pass. The startup-settlement reversal was changed to remove the completion call while retaining TypeScript narrowing: the original always-false condition was assertion-red but did not compile and is not counted. All three corrected reversals compile together and the replacement settlement reversal is assertion-red. No network/native-platform/updater campaign was repeated.

The readiness follow-up changes only two runtime paths: HubMemberUpdates keeps a startup recovery ID and retries a composed host's unknown outcome on later ticks; FleetManager withholds the outcome until its normal startupComplete boundary. Fresh launches are not mistaken for startup recovery. Two new/extended regressions fail against the original compiled 6f818bd0 runtime blobs because they report done before readiness; the final receiver/owner suites pass 34/34. This delta requires source review; it is not described as an unchanged-source sync. The prior TLS/factory scope remains its original stage; no duplicate network campaign.
