# Chrome password-manager DOM contract — scoped follow-up

Before this change the page already had a real form/submit handler, stable hubLogin/name=username/autocomplete=username and hubPassword/name=password/autocomplete=current-password. Ordinary successful sign-in calls setSession and replaces HubSignIn, removing its form and inputs; it is not a fetch-only success that leaves the form mounted. The combined Sign in-and-connect action waits for its approval stage before removing the form, including terminal connection failure. The existing Credential Management API offer is optional and never blocks successful sign-in when unavailable.

Two small gaps: submit read framework state rather than native field values, and the offered identifier was trimmed. A password manager may fill native values without a framework input event. The submit handler now snapshots the actual controls, synchronizes state so pending rerenders do not blank them, submits the normalized account to the API, and offers the exact typed identifier/password to PasswordCredential. A returned canonical account name never replaces that offer. Failure still clears the password; success removes the form. No visible copy/style/layout or backend/directory/budget change.

The actual mounted component/client regression fills native fields without input events and submits the real form. Corrected baseline failed an assertion (no POST) on f70's handler; candidate passes. It pins native FORM, stable ids/names/autocomplete, submitted full email, exact credential offer including surrounding whitespace, populated fields until the offer, and absent form/input nodes after success. All59 Hub page/join-approval UI cases across2files pass. Types and runtime assets are checked separately. Baseline source/candidate hashes and a zero-context reverse patch are retained; check/apply with --unidiff-zero and select the M-3795 DOM test. Initial harness errors (missing calls binding, then treating the helper result as an array) were excluded and preserved locally; the accepted baseline rerun is assertion-red, not those harness failures.

This is DOM-contract proof, not native Chrome save/update-bubble proof. No real credentials/browser account was used.
