# Interrupted work, staged delivery (#2473)

The approved design is [issue comment 6352248250](https://github.com/songsid/AgEnD/issues/2473#issuecomment-6352248250).
The leader requires four independently reviewed PRs in a later 2.3.x release:

1. Observational journal, structured logs and Log tab. No recovery behavior changes.
2. Durable session-OOM terminal blocker, including automatic startup/retry/wake.
3. Stable, pressure-paced recovery coordinator, deduplicated continuation/General summary and opt-out.
4. Consolidate #1209/#926 restart paths and import the legacy marker.

The restart/OOM/crash-loop harness is required for stages 3/4; a packaged rehearsal is required before stage 3 ships in a beta. This is not a 2.3.0 GA blocker.

## Stage 1 contract

`working_state_journal` is a lazy extension of `delivery-outbox.db`, using its existing WAL transaction and process-crash durability. It adds no separate database and does not change SQLite's existing power-loss policy. Each instance has one latest metadata snapshot and at most one first prior interruption observation. Each JSON snapshot is at most 8 KiB, with at most 16 references; the row therefore has a fixed maximum of two snapshots. Duplicate heartbeat observations do not write. A pre-stop/pre-spawn boundary is recorded even when the observed values otherwise match. The prior observation survives further boots and is not consumed in this stage.

The snapshot whitelists launch ownership, backend, a workspace/profile digest, cached activity time, execution/process state and background work observed from an already-captured pane, turn IDs/generation/cancellation/completion evidence, task UUID/version/status, and open incoming/outgoing reply-obligation references. Reference totals expose overflow. Missing stores are explicitly unavailable rather than treated as proof there is no work. The current session/backend turn IDs remain null: this path must not discover a session through a backend method, walk transcript directories or query a CLI. Claimed/review/blocked card references are observations, not permission to execute those cards. A later coordinator must revalidate direct ownership, status, permissions and completion.

Observation hooks run on published daemon state edges, accepted pause/wake transitions, confirmed human delivery, cancellation, guard closure, delivered completion, process/supervision transitions and before guard retirement during stop/spawn. Board mutations refresh both old/new owners; reply-reference changes are observed after the owning delivery transaction. A replaced daemon or stale launch observation cannot overwrite the current owner's row. Identical hooks are attached once per daemon. Journal writes use a zero busy wait and restore the delivery connection’s timeout, so a diagnostic cannot stall every stop behind an external SQLite writer. Observer/store failures are contained and do not change delivery, cancellation, task mutation, startup or shutdown results.

Observation begins when the managed daemon is published after startup, including ClassicBot daemons; the initial snapshot records its resulting state. Transient events before publication are outside this stage's history. A startup failure before publication leaves the existing journal untouched.

No original message, task title, pane output, transcript/config path, full config, tool arguments or credential value is copied. Identifiers are bounded without prefix truncation, so an oversized ID cannot alias another reference. Structured daemon and Log events expose only state/reason/revision/reference counts. The existing Log authorization, masking and enable switch still apply; observational entries are visible in All but excluded from Errors.

This is a record, not a resume decision. A prior snapshot can be stale, cancelled, completed or reassigned; it must never authorize recovery on its own. This stage leaves `in-flight-turn.json`, #1209's consume-before-gate logic, #926 reminders, crash-loop recovery and #2446 supervision unchanged. No new prompt, automatic start, queue item or General summary is produced. The next stages add terminal authority and recovery reconciliation separately.

Rollback is a normal revert. Unused additive rows can remain in the outbox; ordinary delivery tables retain their previous schema/semantics. Do not reuse this stage's rollback statement for the later durable OOM blockers, which must not be bypassed by a downgrade.

The data-downgrade compatibility workflow populates both journal snapshots, checks their exact stored JSON bytes after the published 2.1.12/Node 20 outbox opens, recovers and writes deliveries, then checks that the current build can read and update the retained row while preserving its prior snapshot.

## Stage 2: durable session-OOM stop

#2446's second confirmed same-session CLI OOM ends supervision, but its decision originally lived only on the Daemon. A new fleet process, a configuration reconcile or a queued-work wake could therefore resume the stopped session. Stage 2 records terminal authority separately from the observational journal and from the auto-wakeable `paused` marker. It does not change native OOM attribution, the two-death threshold or the in-memory first-death counter. It does not add a continuation, recovery coordinator, General summary or fresh-session policy; #1209 and #926 remain unchanged.

`instances/<name>/session-oom-stop.json` is an atomic, fsynced 0600 file of at most 4 KiB. The final health owner/session check precedes the synchronous write; supervision-ended publication follows it. The record whitelists a random decision ID, captured boot/spawn/launch owner, bounded owned session identity, configuration digest, timestamp, count and victim PID/time. No message, pane, path, credential or transcript is copied. Directory fsync uses the existing best-effort atomic-write policy; this is process-crash persistence, not a new power-loss guarantee.

Automatic cold starts, startup retries, wakes, low-level physical CLI admission and recovery restarts consult this authority. Admission is checked again after backend preparation and immediately before native spawn following awaited tmux preparation. A distinct thrown error prevents an OOM stop from entering the ordinary `false`-result resume retry/fresh fallback. Incoming work stays queued with attempt zero and a named waiting reason; it cannot auto-wake this instance. A full fleet restart, update, session-ID getter change or configuration edit does not clear the stop. The block is instance-level until explicitly acknowledged: boot-time provider getters may be null or select by cwd and cannot prove a new session is safe.

Only an existing authorized per-instance Start, Restart or Wake action can acknowledge the stop. These actions use the shared serialized stop → start transition. They capture the stop's file identity at the command boundary and clear only that same decision in the stopped gap, before session/carry mutation. A queued action cannot clear a newer stop, and joining an in-flight automatic restart does not confer that authority. Existing tool/route authorization remains in force; this stage adds no confirmation dialog. Explicit retry preserves the session and transcript and starts a new Daemon with the existing empty OOM streak. Starting a new session remains an explicit choice through the existing controls.

Malformed, oversized, unreadable, symlinked or foreign-owned stop evidence is held rather than treated as absence. An owned regular damaged marker can be acknowledged by an explicit retry; a symlink or foreign owner cannot. If writing fails, the current Daemon remains held and the notice explicitly says to repair storage before a fleet restart. If every durable write fails, cross-process persistence cannot be guaranteed.

For upgrades from #2446, the bounded final structured `crash-history.jsonl` record is the only legacy evidence read. A terminal `reason: session_oom` has no recorded launch/session owner, so it is held as ambiguous rather than assigned a guessed identity. A valid ordinary crash is not OOM proof. Malformed or unreadable legacy evidence also holds. An explicit retry leaves a small cleared receipt bound to the acknowledged history revision, without deleting history; newer terminal history invalidates that acknowledgment. The true final record is located by scanning backward in 16 KiB chunks, capped at 1 MiB, and cached by file identity, with at most 512 cache entries. Wide or CJK pane output can make a valid single record larger than 64 KiB; that alone is not evidence of an OOM. Unreadable, incomplete or over-cap evidence is named as an unsafe history/stop-record read, not a verified session OOM. Only a valid stop record or complete structured legacy session_oom record uses OOM wording. This is not the #1209/#926 legacy-marker import reserved for stage 4.

Verification uses scratch directories, fake OOM children/procfs/journals and forbidden native process/network boundaries. Tests pin persistence before notice, replacement-process and delayed-preparation refusal, queued work, explicit retry, stale retry identity, legacy upgrade and corrupt/foreign evidence. Existing turn-resume tests remain controls. Reversal mutations must fail semantic assertions after source typecheck; a setup/build failure does not count.

**Rollback:** older binaries ignore this additive file and may restart a stopped session. Before downgrading, stop the affected instance with an independent operator policy and keep it excluded from automatic startup; do not assume a retained tombstone enforces anything in old code. Session IDs, transcripts and structured crash history are never deleted. The stage 1 data-downgrade byte-preservation proof establishes observational-row compatibility only, not old-version enforcement of this stage's authority.

## Stage 3: task-only automatic continuation

This stage leaves #1209's interrupted-turn marker and #926's restart reminder in control of their existing turns and reply obligations. A mixed task/owed-reply episode, an observed turn or a legacy-covered launch is excluded from this coordinator. Stage 4 will consolidate them; stage 3 must not send a second prompt alongside either existing path.

`defaults.resume_interrupted_work` defaults to `true`; an instance's `resume_interrupted_work: false` overrides it immediately. This disables automatic continuation, including the background-unknown advisory, without disabling the journal, task board or ordinary deliveries. An opted-out candidate remains deferred rather than being discarded.

Recovery starts only after the existing final service READY, two continuous minutes in that run, and thirty continuous seconds of sampled normal memory pressure. Unknown/stale memory readings, pressure, an active spawn storm and a new full restart reset or hold admission. A failed boot does not consume work. New admissions and physical writes are both paced at five-second intervals, with one recovery writer at a time; recovered queued rows do not bypass this pace. No recovery entry wakes or spawns an instance.

Every candidate rereads the actual task UUID, version, status and assignee, configuration digest, cached owned session identity, cancellation, OOM stop, native activity, idle state and pending ordinary work. An unavailable task store or unknown session ownership defers; a completed, cancelled, reassigned or changed task cannot authorize continuation. Only Claude's existing instance-specific statusline checkpoint currently supplies owned session identity. Cwd-selected transcript discovery is deliberately insufficient. A confirmed crash-loop fresh fallback may inspect unfinished task state; an explicit fresh-session choice does not authorize it.

When that existing checkpoint first learns or changes an owned ID, it publishes the cached metadata immediately. It does not add a lookup or wait for another idle/state edge; an otherwise quiet instance can OOM before such an edge. Repeated unchanged checkpoints do not write. This does not assign an owner to a genuinely unknown older snapshot.

The leader's decision of 2026-10-23 permits a narrower advisory when background inventory is unknown. Known running background work still blocks. The informational prompt explicitly says background state is unknown and tells the instance to inspect existing jobs, processes, worktrees, receipts and current cards first; continue only unfinished work still assigned to it; never blindly restart a command, replay the original request or resend a delegation; and report normally. A backend with a real inventory retains the strict known-idle path. The per-instance opt-out applies to both paths. Structured logs identify every advisory admission as `advisory_background_unknown`; the single informational General summary names the advisory instances in its paced admission sweep and lists how many other candidates remain deferred. Deferred candidates whose background inventory is unknown are also named with their current blocking reason; this does not claim they resumed or relax ownership. If General has an admitted continuation of its own, its summary waits until that delivery reaches a terminal state, so the coordinator does not cancel its own prompt by introducing an unrelated pending notice.

Admission, the episode receipt and its local outbox row commit on the same SQLite connection. The episode key describes work rather than the current boot, so another failed boot cannot generate a new copy. A confirmed delivered continuation records its delivery ID in the bounded journal observation: interruption of that demonstrably resumed interval can form a new episode even if the claimed card has not changed. Uncertain or merely admitted input never creates that marker, so a continuation that itself crashes the process before confirmation cannot create an automatic replay loop. Each new interval still waits for the full stability and memory gates; there is no lifetime cap on a genuinely confirmed, later interrupted task. The local writer holds the existing pane lock and rechecks launch/delivery ownership, current admission, empty composer, queued/collapsed input, authoritative idle state and background work after awaited prerequisites. Before paste it durably records possible input. Once input might have occurred, an uncertain attempt is never replayed. A pre-input draft or unavailable prerequisite can defer indefinitely without consuming the ordinary submission-attempt budget; ordinary delivery TTLs remain unchanged. An unchanged deferred decision does not open a write transaction or update its row on each tick.

Requested actions are persisted on the paths actually used: a completed SIGTERM/SIGINT shutdown records a manual restart (or an update when the active update marker is at activation), and SIGUSR2 enters the real in-process restart path and refreshes the current interval's cause label. A completed in-process restart clears the durable intent so a later unrelated process crash does not inherit it. The legacy SIGUSR1 path remains supported. Failed shutdown and fatal-exception cleanup never manufacture a manual intent; unknown interruption is not asserted to be an OOM. Logs and prompts distinguish the observed unknown interruption from the explicit prior requested action.

The data-downgrade check populates all five recovery metadata tables (episodes, receipts, run, summaries and cancellations), compares every stored field after the published old outbox opens, recovers and writes ordinary deliveries, then verifies episode/summary deduplication, cancellation and the prior requested-action read after return. This proves metadata compatibility only: older code does not implement this coordinator's admission, opt-out or pacing policy, and this check never runs an old fleet or dispatches a recovery prompt.

The restart cause is evidence, not a guess: absent an explicit persisted requested action the summary says `unknown_interruption`, including an unproven SIGKILL. A prior requested restart is labelled a requested action and is not claimed as proof of why the process died. No OOM attribution is inferred from an exit code alone. Main-process OOM proof belongs in the capped systemd rehearsal receipt, with cgroup memory events and the manager journal.

Full shutdown observes the interruption boundary synchronously before its first await, while the scheduler and reply stores remain open. The later daemon stop happens after scheduler shutdown; using only that observation loses task references and can retain `tasks` as unavailable forever. The packaged pressure/restart probe exposed this case; a real manager/daemon/SQLite regression and a typed reversal pin the early capture. Missing references from genuinely incomplete older snapshots remain deferred rather than being replaced with guessed work.

The owned write has a launch-bound input scope after durable begin. Its own paste generates PTY activity and can publish `working` before Enter; that expected activity is not evidence of unrelated native work. The scope applies only to recovery admission, keeps actual journal/UI execution state, and retains queue/cancellation/background/configuration/launch guards. Finishing the write marks native engagement for later episodes. Activity before begin or from a replacement owner still blocks. The packaged probe exposed this self-cancellation race; manager and daemon controls pin owned activity versus a queued request and earlier unrelated work.

**Rollback:** first disable automatic continuation fleet-wide or on affected instances, then revert stage 3. The retained observational journal and task cards are unchanged, and #1209/#926 retain their original ownership. Do not requeue a recovery delivery that has crossed the possible-input fence. Stage 2's independent OOM stop downgrade precautions still apply.


## Real-update check, 2026-10-25

The beta.5 read-only check found ten candidate rows although only two instances were working at the shutdown boundary. The regressions use synthetic copies of those shapes, with no live startup, provider or tmux calls.

- **Idle ownership is metadata.** Claimed, blocked and review cards remain in the journal, but an `idle`, paused or unknown execution observation cannot form a task-recovery episode. Only `working` or `stuck` execution without a terminal turn qualifies. Previously retained idle no-input rows are pruned rather than leaving receipts that suppress a later genuine interruption of the same task version. Admitted/uncertain delivery fences and continuation-marker inheritance are preserved. An idle prior without a legacy-owned turn cannot mask a later working boundary. Conversely, a later graceful idle stop supersedes an older task-only working candidate; admitted/uncertain delivery ownership is never retired by this rule.
- **Choose current claimed cards independently.** A working instance with one unchanged claimed card and an older review/blocked/completed card can continue the claimed card. Non-claimed references are skipped before version checks; they never authorize work themselves. Missing stores, changed claimed-card versions, reassignment and legacy ownership still hold or exclude recovery.
- **Cause and intent differ.** Every 13:06 decision in the checked logs already carried `requestedAction: update`. `observedCause: unknown_interruption` does not deny that request: intent alone cannot prove how a process died. `beginRun` consumes the preceding `requested_cause`, clears it for the new process, and returns it to the coordinator; a NULL current-run field is therefore expected. The host CLI can also write a generic update marker without a chat target; shutdown now recognizes that unexpired marker instead of requiring chat progress. Tracked full-restart, failed and completed progress keep their existing meanings.
- **Summaries belong to the recovering start interval.** The old implementation grouped by the interrupted manager's boot ID. A summary delivered earlier in that manager's lifetime consumed the key, hiding the later full-update summary. Discovery now assigns the current manager/start group, with a fresh group for an explicit in-process restart. Deferred episodes can move to the new group without changing their work key or receipts; admitted deliveries keep their ownership. Only a newly committed General notice emits the summary's daemon-log line and `working_state` Log event. Metadata-only rows do not inflate the summary.
- **A backend label is not session proof.** In the sampled idle Claude row the old snapshot had a session ID, but the replacement's cached `ownedWorkingSession` was NULL. `beginSpawn` clears it; Claude learns it through the existing session checkpoint/status-update path, while the guardian watches file changes rather than reading an unchanged status file at subscription time. Queries never discover sessions, and the cache remains unknown until that path supplies an ID. The fix does not copy the old session file or relax this fence. Excluding idle candidates removes the misleading deferral in this case. Codex, Grok and Kiro do not currently publish this Claude-specific ownership cache, so NULL is expected for them. Classic mode itself does not identify a backend: the sampled Classic row actually recorded `claude-code`.

Local proof uses the five directly related working-state/recovery suites, with native CLI/network boundaries forbidden and private SQLite/task-board fixtures. The operator will validate on the next real update; no live fleet restart is part of this proof. No new tables or data rewrite on the running host are required. Rollback is a code revert or the existing `resume_interrupted_work: false` opt-out; never requeue an admitted/uncertain continuation.
