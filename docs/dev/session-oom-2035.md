# Session OOM recovery (#2035)

Design before implementation: [issue comment](https://github.com/songsid/AgEnD/issues/2035#issuecomment-6272832619).

A health-monitored CLI can reach ready, then be OOM-killed while using a conversation. The ordinary crash path checkpoints its session marker and tries resume again. Successful startup clears `skipResume`; it does not prove the resumed conversation will fit in memory. The generic three-crashes-in-five-minutes and max-retry policies bound ordinary failures but do not diagnose OOM. Startup failures before a CLI can be identified still use the existing bounded, session-preserving startup policy.

This guard changes only recovery after death. It never kills a CLI because of memory usage. It does not claim that transcript size caused an OOM: two confirmed victim records show that continuing the same session marker is unsafe to repeat.

On Linux, the daemon observes a uniquely identifiable backend process through a short recognized shell/env launcher chain while the pane is alive. It does not search through an unknown primary to find a tool or subagent whose name happens to match the backend. Only its exact kernel OOM **victim** record qualifies, in the current boot and observed lifetime. A matching process name, process start identity and host PID namespace are required. Shell/helper/MCP victims, old records, PID reuse, an unreadable procfs/journal or a truncated/timed-out query are unknown. Status 137, pressure, transcript size and the shared fleet cgroup's `oom_kill` counter cannot qualify. One asynchronous journal reader is shared during a burst; it is limited to one second, 256 records and 256 KiB, looking back five minutes. Permissions that hide kernel records lead to ordinary crash handling. Generic `node` processes or wrappers without an identifiable backend name also remain unknown. This first implementation adds no macOS jetsam classifier.

Two consecutive confirmed deaths using the same backend/session marker cause the next existing crash recovery to skip resume. An ordinary crash or a different session breaks the count; a ready prompt alone does not. Counts belong to the resident daemon's recovery run, rather than a new cross-fleet history service. The old session ID is kept in `session-id.oom-*`; provider transcripts are never read in full, edited or deleted. A fresh-start intent uses the existing `crash-state.json` mechanism so a daemon interruption before launch cannot silently resume the suspect session. If that write fails, recovery stops. A successful fresh launch consumes only its own intent and receives the existing bounded ring-buffer snapshot, when available. Existing retry/backoff and rapid-crash limits still apply.

If that fresh recovery is itself a confirmed OOM victim, automatic recovery stops. The crashed instance stays in the existing Needs-you list. The instance and General receive the cause and remedy; the web Log records `session_oom` with the action, reason and previous session. A person can free memory and explicitly restart. No additional permission layer, per-instance cgroup architecture or privileged collector is introduced.

Evidence and tests use a fake child, private procfs fixtures, kernel JSON records and inert tmux/process boundaries. No host memory exhaustion, provider CLI or live tmux fleet is required. The dependency install, native rebuild, type checks and focused tests are capped by a private `systemd-run --user` unit with `MemoryMax=4G` and `MemorySwapMax=0`; full tests run in CI. Initial fixture failures and missing-dependency logs are retained with the local evidence.

Rollback is a revert. There is no persisted schema migration. Existing `session-id.oom-*` files can be kept as recovery references; `crash-state.json` remains the ordinary one-shot fresh-start marker. Removing the guard restores the old repeated-resume behavior.
