# Codex exhausted HTTP429 recovery (#2282)

## Root cause and current behavior

Issue: https://github.com/songsid/AgEnD/issues/2282 . Reporter versions are unknown. The exact screenshot row was
reproduced on a real Codex0.163.0 against a local Responses mock:

```
■ exceeded retry limit, last status: 429 Too Many Requests
```

Codex exhausted its HTTP retry budget, ended the turn and returned to the empty composer. A separate20-second quiet
window produced no new HTTP requests. The user request remained in the retained conversation: after the mock
recovered, a conditional continuation generated a successful new request carrying the original context.

Before this change, both main (`feacd62a2`) and release/2.2.x (`30c19ba3`) matched this as rate_limit/failover.
Their Codex backend, lifecycle and daemon files were identical. Lifecycle sends the standard rate-limit incident
(`OpenAI rate limit reached`, action failover), emits the event/webhook, clears Cancel, and calls
`checkModelFailover(name,100)`. No fallback or a one-entry list makes that method return immediately. Even a configured
fallback only sets a model override for the next spawn; it neither starts a new turn nor replays this one. Delivery was
already acknowledged, so it is not automatically requeued. The request is not physically erased, but remains unanswered.

## Change and safeguards

The exact decorated exhausted429 row now selects nudge_continue ahead of generic rate-limit detection. The generic
pattern excludes that row so a later poll cannot report the same row again as failover. Ordinary429 behavior remains.
Configured next-spawn failover bookkeeping is preserved only for a fresh, live error episode.

The existing daemon-owned continuation sends: “Continue only if the last request is unfinished; if it is done, reply
that it is done.” It keeps session context and avoids replaying the complete original message, which could repeat tool
side effects. The model still decides whether work remains; this cannot guarantee that an external side effect will
never be repeated, so recovery is limited and cancellation is conservative.

Transient429 has a separate lifecycle budget: delays30/60/120seconds, at most three continuations within30minutes,
then pause+notify. Capacity keeps its prior independent budget. Counters survive a daemon replacement within the fleet;
a fleet restart resets them, while resumed-history baselines prevent automatic replay of its old rows.

Every recovery requires the same daemon owner, a new occurrence beyond the first live composer’s history baseline,
the last live status row, and a running/idle/empty composer. Cosmetic redraws do not cancel it (#2543).
New output after the error, a draft, busy status, queued delivery, user cancel,
pause or launch change cancels it. Monotonic due time and the existing pane-write lock/rechecks apply. The history
baseline also suppresses old exhausted429 notifications and failover, not merely the paste. After rows scroll away,
a subsequent new error can recover normally.

Budget exhaustion must validate the fresh episode before pausing too. The existing arming method records only a due
time; on the fourth error it is synchronously cancelled before any monitor tick can submit a fourth continuation.
Exhaustion additionally captures the current empty composer under the pane-write lock, requiring no queued delivery,
working turn or background work. The real pause rechecks this admission after its own pane capture. A delayed pause
completion revalidates the live failed turn and captured boot/spawn/launch/delivery/episode owner before deferring. It cannot
pause a replacement launch even on the same Daemon object; pause's own monitor-freeze fence advance remains allowed.

The quota control exposed a separate gap: Codex renders insufficient_quota as
`■ Quota exceeded. Check your plan and billing details.` The preceding quota/pause pattern now includes that precise
sentence. Existing structured insufficient_quota, usage-limit and workspace-credit rules remain separate. A quota
failure does not arm a transient continuation or consume its budget.

## Evidence, tests and limits

[Fixture provenance](../../tests/fixtures/codex-429-2282/SOURCES.md) records the real binary hash, mock responses,
launch flags, isolated container/private socket, commands and normalization. Tests execute real Daemon/Lifecycle logic
with inert tmux/paste/pause/probe boundaries. No real memory exhaustion, account, provider call, fleet or host tmux.

Focused suite: new429 recovery27 plus existing capacity nudge/detection/backoff and backend tests,199PASS;
quota verification/audit-rig compatibility25PASS. Pause/precheck compatibility132PASS. Build/postbuild and test
TypeScript PASS. Six semantic reversals were caught independently: remove history suppression; bypass the retry
ceiling; remove rendered-quota detection; remove generic/specific dedup; remove exhausted-pause launch ownership;
remove exhausted-pause input/work admission. Sources were restored before final checks. The upstream detector
manifest is regenerated, with the exhausted429 literal mapped to the error surface.
Existing capacity fixtures only narrow their selector from “first nudge_continue” to “model_error nudge_continue”;
their original semantic assertions remain.

The reporter’s installed versions and exact incident route are unconfirmed. This fixes an evidenced shared mechanism,
not a claim that every429 has the same cause. Unknown/changed screen shapes deliberately cancel recovery. The retry
budget is not durable across fleet restart. No CLI restart or credential migration is introduced.

Release decision: no separate2.2.x backport. The leader relayed the user decision that2.2.7 will use the tested
beta.17/18 main SHA, so this main fix is carried by that release. No backport PR is opened. Rollback: revert this change; configuration, transcripts and credentials
are untouched, and the previous notification/failover behavior returns.
