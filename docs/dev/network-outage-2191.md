# Network outage, 2026-10-19 (#2191)

All incident times below are UTC+8. Historical evidence was supplied by the operator in issue #2191; no production fleet was restarted or disconnected for this investigation.

The fleet ran `node dist/cli.js fleet start` on beta.11, bundled Node 22.23.3, discord.js 14.27.0 and ws 8.22.0. During the network outage, each Discord bot's gateway watchdog saw a shard connecting for about 210 seconds and rebuilt its client. `fleet.log` then records two uncaught `Opening handshake has timed out` exceptions from `ws/lib/websocket.js:904`, followed by failed gateway rebuild attempts. The CLI's uncaught-exception handler stopped every daemon and exited 1. Systemd recorded `code=exited,status=1` and restarted it. An earlier run has the same pair after a watchdog rebuild.

The systemd template appends stdout and stderr to `fleet.log`. Those exception stacks therefore did not appear in `daemon.log` or the journal. No user-requested restart was recorded. The 72-second gap in `daemon.log` alone does not establish an event-loop stall or a systemd watchdog termination.

The dependency's shard destroy path removes its WebSocket `onerror` while a CONNECTING socket can still have its HTTP handshake timer armed. A later timeout emits an unhandled EventEmitter error. The adapter now owns error containment throughout retirement, awaits destruction, terminates unfinished sockets and prevents the retired shard from creating another connection. Tests exercise the local checkout's actual `@discordjs/ws` 1.2.3 destroy logic with an inert WebSocket transport (local discord.js 14.26.4 and ws 8.20.0, distinct from the incident versions); they reproduce the bare timeout error before containment. This is a dependency-sensitive boundary and must be rechecked on Discord library upgrades.

After the restart, both Discord connections failed their startup. `scheduleAdapterRetry` stopped scheduling at ten failed attempts, leaving them down permanently after the network recovered. Background retries now continue with a five-minute cap. **Settings → Connections → Retry now** bypasses a pending delay and reuses a running attempt; it is restricted to local administrators. Recovery uses the normal primary/additional adapter wiring and the connection lease, rechecks configuration through login and stops scheduling on fleet shutdown.

Fleet MCP outbound calls previously resolved a reply adapter before dispatching local operations. A missing primary or persisted Discord world consequently blocked `send_to_instance`, `describe_instance` and `delivery_status`, even with another platform running. Fleet handler dispatch now follows the same tool-permission gate but precedes reply routing. Channel operations retain their original context requirements. Task Board operations already use separate typed IPC and are covered as a control.

The reported MCP notices mostly say **never connected after the CLI started**. They do not prove that a previously connected MCP process died. The MCP server uses local Unix IPC, retries that connection indefinitely and performs no Discord/Telegram network requests. Fleet shutdown ends CLIs and their MCP children; later startup and parent/stdio failures need per-instance stderr and PID chronology to distinguish. We do not attribute every historical MCP notice directly to the network outage.

A separate recovery defect was reproducible: the daemon consumed its pending restart request before the lifecycle rejected it for being inside the 15-minute cooldown. Same-PID death deduplication then prevented reconsideration. Deferred recovery now returns through the daemon's normal liveness, idle, queued-work and pause gates after the cooldown, and is cancelled when the instance recovers or stops.

Unknown uncaught exceptions remain fatal. A local, synchronous fatal record is written before shutdown; normal startup and reload share that policy. Unhandled promise rejections are reported without taking the whole fleet down. Rollback is a revert of this change; there is no data migration. Existing fatal records are diagnostic artifacts only.

Retirement containment covers sockets and native recovery already present when a Client is retired. Prism also reproduced a pre-existing race in both the old destroy path and this change: if a pending `GET gateway/bot` resolves only after retirement, `Client.login()` can still create a new shard/socket. The completed retirement promise does not clean up that late socket. This PR does not claim to solve that separate pending-login race. Manual retry uses the same current connection evidence as Settings, including Telegram polling readiness after startup has resolved.
