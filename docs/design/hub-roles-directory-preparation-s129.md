# Directory preparation and fresh commit authority

This follows #3827. The private proof engine now accepts an optional operation-preparation handle. No production route, mounted-source producer, controller/session adapter or singleton-writer provider creates it yet. This is not mounted auxiliary Directory Save or full S-129 acceptance.

The ordinary named management proof lasts five seconds. Passing it through candidate LDAP checks would reject an otherwise valid slow Save. Extending that proof would also extend effect authority. The new preparation instead retains the original actor, session, request methods, canonical policy bytes, authorization version, directory method, configured root and operation clock basis. It has no writer capability and cannot be passed as an administration witness.

An actual `hub.admin` acquisition starts the preparation. Its provisional checks can continue for at most five minutes of wall or monotonic elapsed time, on the exact original basis. Role loss, assignment expiry, sign-out, a replaced method/provider, changed policy/version, clock rollback or an observed failure permanently retires it. An observed A-to-B-to-A change does not revive the operation. Preparation does not renew an old permit. The management authority keeps its existing twenty-second acquisition budget and five-second effect-proof deadline.

The opaque directory handle additionally binds that actual authority's directory and configured root, the exact actor/session/request, full source image, directory epoch and decision-proof getter. Source checks around awaits prevent another mount or request from supplying the final proof. Request bodies never decode either handle. Host/D3 cannot consume a browser handle, and mixed preparation/administration contexts refuse. Only explicit preparation boundaries accept this handle; ordinary read controls still require an administration proof.

After old-directory authentication and all candidate checks, including candidate close, the proof engine consumes the preparation with a new actual management acquisition. It revalidates the same session and reads current eligibility through the existing shared physical-read pool. No result from the earlier candidate check supplies management authority. Unknown or changed eligibility refuses. One acquisition runs at a time; cancellation or a source change while it is held prevents publication after physical settlement. A successful exchange is single-use.

Only the resulting new opaque administration witness reaches both writer preparation and commit. It retains the existing callback-local SQL decision behavior. A root's role-prepared directory draft cannot switch to a bare legacy Save. The final five-second proof is still checked by the normal writer path; a slow precommit callback does not extend it. Bare root and D3 preparation retain their existing behavior.

The five-minute limit is checked at operation boundaries; it is not a new timeout that releases physical LDAP ownership early. Existing directory operation timeouts and pool settlement still apply. The preparation's identity checks authorize continued preparation only; every effect/disclosure still needs the normal route's current authority. No timer grants or refreshes authority.

Validation uses actual memory SQLite, HubSessions, canonical roles, transport/floor and the real shared pool with fictional directory answers. The engine tests use an inert candidate and writer that checks the actual opaque final witness. Existing sealed-writer and root session suites are regression evidence, not a new mounted auxiliary recovery claim. No live AD/account/Fleet/pane, native platform, browser, container or startup migration is involved.

Next work must compose the exact mounted source and per-request preparation producer, recent-authentication/rotation adapters, singleton writer and new-generation response handoff, then exercise real mounted Save and its recovery. The producer must additionally retain its owning Core/provider identity and obtain a fresh proof before any result disclosure; the bare preparation guard is insufficient there. Member/SSE retirement, issued code/invitation recovery, root self-use and cold startup acceptance remain open. Parent-first plain alpha merges, conflict review, exact-head CI/readiness and the alpha.3 freeze remain. Before activation, rollback means leaving the optional path uncomposed; committed settings continue forward recovery.
