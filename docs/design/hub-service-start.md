# Hub service setup and restart

The Hub uses AgEnD's existing `com.agend.fleet` service and `fleet start` entry. It introduces no separate service identity or restart worker. The existing local-owner setup confirmation, fleet-agent `--yes` gate and verified-install restart guards retain their authority boundaries.

Hub init passes its exact `AGEND_HOME`, working directory and log path into both service templates. A fresh Hub's launchd plist uses `LimitLoadToSessionType=Background`, loaded in `user/<uid>` so it does not require a GUI session. Existing GUI fleet services remain in `gui/<uid>`. Refresh/install preserves an existing Background choice. All start/stop/inspect/restart/update-plan paths and the installer's recovery use the same selected domain; TypeScript and the standalone installer share a small parser that considers only the root plist field, ignores comments/nested environment fields and refuses duplicate choices. An unreadable installed definition refuses domain selection.

The service manager still owns stop/start sequencing. Existing launchd reload waits for confirmed job absence before bootstrap; systemd owns its ordered restart job. An agent-launched client therefore need not survive a stop to issue a separate start command.

Before the replacement claims the fleet singleton or constructs `FleetManager`, an enabled Hub waits for the recorded old process identity to exit and for its two listener endpoints to be free. It compares process births: a reused PID is no longer the old process, and unreadable identity never proves exit. A process born after the PID file was written cannot be its writer; a self-PID cannot be the previous fleet. Those stale claims do not block startup or installation. With no recorded PID, existing manager ordering and the singleton lock still apply. It then reuses the init check, including daemon loopback reservations, holding both temporary binds together and closing them before returning. A concurrent configuration edit refuses admission. Waiting uses the existing outer stop grace and an asynchronous, monotonic poll; it sends no signal, deletes no PID record and contacts no directory or model.

Hub installation refuses an active or unverifiable manual PID before writing a service definition. Its activation preserves any old PID record for the replacement's check instead of using the installer's legacy signal/short-wait/unlink path. An idle or positively gone old record can remain. The owner receives EN/zh-TW guidance to stop through the existing owner command or inspect a stale record. Existing initialized configuration is retained if service setup fails.

Non-Hub starts do not load the new Hub module. No access policy, config schema, key material, database migration, model version or subscription state changes. Systemd's template directives and loaded-value guards are unchanged; the Hub now supplies the existing explicit-home field. Rollback is a feature revert; preserve an installed Background definition's user-domain placement when operating it with an older CLI.

Limits: these are local process/bind checks, not remote reachability or full Hub readiness. Probes release their sockets before the actual server binds; runtime bind failure remains authoritative. Acceptance distinguishes real Linux loopback/PID observations, inert compiled-CLI routing and fake manager sequences from native service-manager acceptance. The running pilot is not used or redeployed by this work.
