# Group policy composition

This completes the server-side wiring for [#3298](https://github.com/songsid/AgEnD/issues/3298). The reviewed confirmation control, actual pairing enrollment, catalog publication enrollment and message-effect permits are composed together with the Hub editor and welcome routes. All are prerequisites; none is substituted by a preview or a UI capability mark.

The server factory owns one lazy policy store, one immutable directory/configuration binding, one authorization adapter and one configured-administrator confirmation control. All share the same private database and required audit writer. Policy/provenance/suspensions and the global authorization version change in the same owning transaction. The transport version writer is synchronous, validates that exact database and runs before commit; the listener refresh happens only after commit. Closing or fencing the service invalidates every captured control, session and action continuation. No admin role comes from group membership.

New installations remain `never-enabled`. Eligible directory users may sign in regardless of group membership. The configured Hub administrator can resolve groups, inspect the complete impact and save that exact short-lived preview; there is no additional fleet confirmation or authority handoff. A confirmed enable is the only transition into group enforcement. Unknown membership is listed separately as HELD and cannot grant new access or suspend an existing resource. Confirmed narrowing and explicit denies can suspend; a later positive save never resumes. Resume authenticates the configured administrator and binds the exact current resource, policy and lifecycle revisions.

The welcome uses the same policy binding, but is display only: no audit, permit or enrollment. An intact never-enabled legacy binding may keep the legacy welcome during a directory-generation repair. A previously enabled, corrupt or foreign binding answers unavailable without constructing a mismatched strict store; sign-in and the administrator's repair view remain available. Own fleets include their exact lifecycle projection: suspended is Paused, unknown is unavailable rather than Active. No other person's fleets, group GUIDs or DNs enter the welcome. Chat still needs an owner's existing grant; pairing still needs its one-time proof and both ordinary fingerprint confirmations. Quick pairing is a separate S-90 change.

The HTTP/session capability is present only with the complete control and welcome. Retained clients or panels without their own matching mark omit the new UI; they do not acquire authority from a newer session response. Discovery remains on the Hub's Administration page and the fleet host's Settings → Hub link. The editor's authentication completes on the Hub, not the fleet dashboard.

Acceptance uses a sealed scratch initializer and actual server factory, real SQLite/hash-chain audit, verified loopback HTTPS and inert directory people/facts. It covers real preview/apply/resume routes, ordinary and group enrollment, current sessions and CSRF, repair, HELD and service lifetime. A real browser performs group resolve/preview/save without API response stubs, then reads no-actions, ask-only and full welcomes. Desktop/phone, English/Traditional Chinese and retained-module cases are recorded separately from the fake-LDAPS driver and real WSS publication receipts. No real directory, account, native manager or pilot is touched.

The manual-pairing correction adds transport metadata version 2 for the persisted approving identity; see [the manual path](hub-manual-pairing.md). Before deploying or rolling back a binary, back up state and use a binary that understands every stored component and enforcement rule. Reverting this composition hides its editor; the already-landed pairing, publication and message gates must remain with any enabled policy. Restoring a pre-enforcement binary against enabled state is not a supported rollback.
