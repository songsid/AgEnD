# 保留 Hub 身分的搬遷手冊

這是設計與本機演練，依據 `e05fb8189698dd4bf804e3993a914e8e03a911d9`。沒有讀取或變更正式安裝。完整來源與細節見 [English runbook](hub-host-move-runbook.md)；測試結果見[演練證據](../evidence/hub-host-move-m3792/verification.json)。

## 先回答兩個問題

**金鑰、資料庫與已簽署的設定清單可以一起搬。不要重新初始化 Hub。** Hub 身分不綁電腦序號、作業系統主機名稱或資料夾的絕對位置；但設定、憑證名稱、金鑰、資料庫與版本紀錄必須彼此相符。先用完全相同的 AgEnD 版本與來源建置搬遷，再另排升級。

**新電腦的名稱，不一定要變成新的 Hub 網址。** 最穩妥的 A 路線是保留大家使用的兩個網址，把 DNS／路由改到新主機。Fleet 原來的配對仍有效，搬遷時離線的 Fleet 之後也能用原本的憑證連回來。單純換主機不要求重新分享；既有分享同意、授權期限等檢查仍然有效。

如果 Fleet 連接位址也必須換，採 B 路線：舊 Hub 還在執行時，先把已簽署的新位址送給線上的 Fleet。只有支援這個功能、成功回覆、而且連線一直有效到變更完成的 Fleet，才能保留配對。離線、舊版或中途斷線的 Fleet 會被撤銷連接，必須由擁有者按「重新連接」並登入公司帳號；之後還要檢查分享與誰可以提問，**不能保證都不用重新分享**。先停機、複製後才改網址，無法取得「線上自動跟過去」的效果。

這是停機搬遷，不是兩台同步運作。程式沒有跨主機的共同鎖；把同一份資料複製到兩台後，不能讓兩台 Hub 同時接收工作。

## 哪些要帶、哪些要重設

以下路徑都相對於選定的 AgEnD 資料目錄，不是作業系統的家目錄。只在私有操作紀錄記檔案路徑、大小、權限、版本、Hub id 與公開指紋；不要把金鑰、密碼、資料庫內容或備份貼到聊天或 GitHub。

| 項目 | 搬遷方式與限制 |
|---|---|
| `fleet.yaml` 的 Hub 設定 | 與資料一起帶走。Hub id、網址、監聽位址、憑證路徑、目錄服務、管理員、保留期限與共用模式都受已簽署設定約束；不要隨手改 YAML。 |
| `hub/init-manifest.json` | 保留與設定相符的原始簽章。改網址、監聽位址或憑證路徑可能使它失效，應透過既有設定流程更新。不要用 `hub init`「修復」。 |
| `hub/keys/` | 整個目錄帶走，包含 Hub 身分、簽署金鑰、Fleet TLS 私鑰／憑證與 `content.key`。不能產生新 Hub id、新簽署金鑰或新 Fleet TLS 金鑰；否則原本的信任會失效。 |
| `hub/hub.sqlite`、`hub/floors/transport` | 與內容金鑰取自同一次停機備份。資料庫包含連接憑證與世代、分享與授權、房間與歷史、登入狀態、稽核、設定決定、搬遷版本及加密附件片段。缺一部分會拒絕啟動。不可只還原資料庫或重設版本紀錄。 |
| SQLite `-wal`／`-shm` | 所有寫入者停止後才做最終備份，優先完成 checkpoint 並正常關閉。若仍有附檔，連同已停止的資料庫整組保存。不可刪 WAL 讓備份看起來乾淨，也不可只複製執行中的 `.sqlite`。 |
| `hub/secrets/` | 原有目錄服務密碼、加入碼與交付金鑰等一起帶走。搬遷不順便更換密碼。相對資料目錄的參照可保留。 |
| 其餘整個 `hub/` | 網頁／Fleet 位址版本、憑證版本與選擇紀錄、設定收據、journal、初始化狀態等都保留。搬前先在唯一正式來源完成或復原尚未結束的設定變更，不能自行刪 journal。 |
| `hub/install-inventory.json` | 帶走作為歷史安裝紀錄，保留當時的網址與路徑。它不是目前設定，也不能授權刪檔；`agend hub handoff` 只是說明紀錄。 |
| `hub-assistant/assistant-state.json` | 在 `hub/` 外。若保留 Hub 助理設定，要另列入搬遷。助理使用的帳號／profile 與憑證需分別驗證。 |
| Hub 外的 Fleet／瀏覽器／憑證檔 | 若與個人 Fleet 共用帳號，先逐項分類。`web.token`、Fleet 網頁登入／驗證資料、憑證庫與其解密金鑰、profile 等不是 Hub 配對本體；不要為了搬 Hub 把所有 Agent 與私人 Fleet 都帶過去，也不能漏掉助理需要的檔案。 |
| 瀏覽器憑證 | 必須符合人員開啟的網頁主機名稱，並受瀏覽器／AI App 信任。它與 Fleet 固定信任的 TLS 金鑰不同。換網頁網址應走正式設定流程與可信憑證規畫。 |
| 服務、程式與程序檔 | 在目的地安裝對應作業系統／架構的相同建置，重新產生服務設定、資料目錄、PATH 與日誌路徑。不要複製 launchd／systemd 定義、PID、鎖、socket、macOS 執行檔或 `node_modules`。舊服務定義私下保留供復原參考。 |

目的地檔案必須屬於執行服務的使用者，不能經過符號連結，目錄用 0700、檔案用 0600。不能只照抄來源的數字 UID。本機演練的第一次複製就被正式的私有檔案檢查擋下；修正目的地權限後才通過，因此這是實際必要步驟。

macOS Keychain 的登入不能直接當成 Linux 憑證檔。助理 profile 搬過去不代表已登入；有使用受管理憑證庫時，金鑰與資料庫必須成對保留，但仍要依該 CLI 支援方式另驗 Linux 登入。這份手冊不授權匯出 Keychain 密碼。Hub 核心搬遷不要依賴尚未驗證的助理登入。

## 開始前，先填操作表

操作表要有：來源／目的地資料目錄與服務帳號、版本與來源建置、網頁與 Fleet 兩個網址及 DNS 管理人、網路／目錄服務可達性、憑證方案、備份大小與傳輸方式、是否使用助理、舊服務是否同時執行個人 Fleet。IP／DNS 尚未確定時，只能準備。

1. **每一次 SSH 或其他 Server 連線前，都要取得使用者當次明確同意**，包含唯讀查詢、跳板與重用連線；依決策 `cab89340`。這份設計沒有授權登入、停機或啟動。正式搬遷與影響範圍也要另外確認。
2. 目的地先裝相同建置，驗證平台相依套件；不初始化 Hub、不啟動服務，自動啟動與入口維持關閉。套件版本字串一樣，不代表來源與 schema 一定相同。
3. 優先使用專用服務帳號。如果來源與個人 Fleet 共用服務，停服務會一起停其他 Agent，需告知影響。不要為了目的地改成專用帳號就手改 sealed 的 coexistence／目錄欄位；保留既有設定，或另排有支援、審過的變更。搬 Hub 不代表搬 Agent 工作資料夾，也不會延長原來的分享同意。
4. 讓同一組受簽章保護的監聽設定能在兩邊使用。可用明確的 loopback 監聽加各主機前端；Fleet 前端必須原樣轉送 TLS，不能改用代理自己的金鑰。網頁 TLS 與預覽端點各自規畫。如果來源綁的是舊主機專屬 IP，先在來源用支援的「只改監聽」操作處理並演練；目的地才有的 IP 無法通過來源的綁定檢查。
5. 事先準備 DNS、防火牆、目錄服務信任與網頁憑證。兩個 Hub origin 保持分開。新機器可使用新名稱、舊公開名稱保留為別名；但必須確認做得到，不能假設區域電腦名稱也能直接移轉。
6. 暫停使用者操作，等目前問題／助理工作結束，暫停新加入並等設定頁的近期加入保護結束，最久可能到十分鐘。私下記要檢查的 Fleet、分享與期限，不倒出對話。尚未確認的答案不能自動重送。

## A 路線：保留原來兩個網址（建議）

1. 保留 Hub 設定、身分與公開網址，安排 DNS／路由可改到目的地。必要的「只改監聽」先在來源用正式流程完成；這不撤銷 Fleet 配對。
2. 公告維護。停止來源服務及所有寫入者，停用／隔離來源自動重啟。確認服務狀態、真正的程序、網頁／Fleet／預覽監聽及助理背景寫入都停止；不能只看到 stop 指令成功。如果個人 Fleet 必須繼續跑，要先另設計 Hub-only 停用方式，不能假設共用服務只停 Hub。
3. 先審目的地設定：若來源還有 Fleet instances、bot channels 或 Hub-member 角色，**不可整份盲目複製後直接啟動**。需審查只執行 Hub 的目的地設定，保留 sealed 的 `hub` 區塊不動與所需全域設定／相依檔，排除無關 Agent 與傳輸，不變更來源。先做不啟動的設定驗證並審查差異；做不到就停止，另開安裝拆分工作。
4. **此時才做最終一致備份**：設定、整個 `hub/`、所需助理狀態與明確列出的外部相依檔。保留私有檔數／大小／checksum 紀錄，關閉後用不啟動服務的方式檢查 SQLite 完整性。可以預拷縮短時間，但只有停機後的最後一份才是正式來源。
5. 私下傳到仍隔離的目的地，先修正擁有者與權限，再讀取驗證。比對 checksum、完整檔案組、Hub id／金鑰指紋、設定簽章、schema 與外部路徑。不能把啟動 Fleet 假裝成唯讀驗證；備份與私有清單不可公開。
6. 依目的地套件與資料目錄重建 Linux systemd 服務，可使用支援的 `agend install --no-activate` 並檢查產物；確認該帳號的 user service manager 與開機持續執行安排。不要跑 `hub init`，也不要複製舊 launchd 檔。
7. 來源保持停止／隔離後，才切 DNS／路由並按正式授權啟動唯一的目的地。驗證目錄登入、Hub 狀態、原 Fleet、既有分享 Agent、房間歷史及附件。逐項處理 pending／held 工作；資料庫還在不等於可以重做不確定的操作。
8. 復原觀察期內保持舊主機不能自動啟動，驗證成功再恢復使用。原 Fleet（包含當時離線者）可用原網址與儲存的配對連回；授權過期、Agent 改變後需重新分享等規則不變。

## B 路線：Fleet 連接位址也要換

先完成準備，暫時保留網頁網址，減少同時改動。必須由仍在執行的來源 Hub 發出搬遷；停機副本無法繼承舊程序的即時連線回覆。

1. 要免重新連接／分享的 Fleet 全部在線且狀態正常，支援 `member-relocation-v1` 與 `welcome-caps-v1`。舊版／離線者先與擁有者說好處理方式；沒有有效回覆就不能保證保留。
2. 在來源電腦自己的「設定 → Hub → Fleet 連接位址」用「變更連接位址」，填新公開網址與**兩台都可用、而且不同於舊 listener 的後端埠**，正常確認。A 的前端仍指向舊後端埠，重掛後該埠必須關閉；B 的前端則指向目的地新埠。不要手改 YAML／身分檔。檢查的是來源的本地監聽，不是目的地能否連到。換主機名稱會重發符合新名稱的憑證，但保留相同 Fleet TLS 私鑰與 SPKI。
3. 來源配置新的遞增版本，向各 Fleet 發送分別簽署的搬遷說明；Fleet 先存下才回覆。共同等候回覆上限五秒，主機確認提案五分鐘到期。已保存的 pending 搬遷沒有時間到期限制；已確認的搬遷鏈最多八次。
4. 看結果「已跟隨／需要重新連接」清單，私下記錄最後狀態。只有相符的連線一直有效到 SQL 決定完成者才保留憑證與世代；其餘被撤銷、世代增加。若必須保留的 Fleet 被排除，**暫停下一步**，不要以為取消複製就恢復原憑證；位址變更已經提交，應選擇經審查的向前復原或正常重新連接。
5. 先確認新連到 A 只會暫時連線失敗，不會拿到 B 的憑證。換名稱卻沿用相同後端埠，可能讓 A 提供只符合 B 的 SAN；Fleet 先試 B 再試 A 時會變成停止重試的 `key-changed`。「立刻停機」不能消除這個競態。沒有分埠或等效入口隔離時，先停止此手冊、審查拓樸，不承諾自動跟隨。接著按 A 路線停機／隔離、取變更後的最後備份、傳輸與驗證，再只啟動目的地。複製期間新網址可能尚不可用，pending Fleet 先試 B 再試 A，重啟後仍保留 pending。但現行流程會關掉舊 Fleet listener，沒有自動轉址寬限入口；不能啟動過時副本補這個入口。
6. 確認 Fleet 在 B 通過固定信任的 TLS、welcome 與 reconciliation，才會正式把 B 當作新起點。之後只試 B，重啟也不回 A，原配對檔保持不變。檢查原分享／授權，搬遷時不要順便改 Agent 的 CLI、資料夾或 runtime；分享同意不能跨 Agent incarnation。
7. 被排除者由擁有者在「設定 → Hub」按「重新連接」，登入公司帳號，再確認分享與誰能提問。Hub 還有舊資料列，不代表新連接世代的同意仍然有效；需要時由擁有者走原本重新分享流程。

換人員開啟的網頁網址是另一個「Hub 位址」變更。它可能結束瀏覽器登入，需要可信的新網頁憑證，也要檢查 AI App 授權／redirect 與預覽網址。優先等主機搬穩後再做；若舊網頁網址無法保留，就先把兩個正式位址變更都演練好，再做最後停機複製，不能手工補簽章。

## 搬回去：不能把舊權限一起復活

- **還沒改位址、目的地也沒寫入：** 目的地繼續隔離，原來源可從未變更的正式資料恢復；必要時改回路由，驗證後再開放。
- **目的地已有人使用，即使採 A：** 先停／隔離目的地，把它最新且一致的完整狀態搬回來源、修權限，用相同建置與網址驗證後，只啟動來源。不能例行還原搬前舊備份，否則會遺失新工作或復活已撤銷的狀態。
- **B 位址變更已提交：** 保留最新資料及 B 網址。必要時可把 B 路由到舊機器，讓舊機器執行最新狀態；換回機器不等於必須把網址換回 A。不要還原舊資料庫、版本或搬遷檔來偽裝回到 A。
- **公開網址一定要回 A：** B 仍是唯一正式來源、必要 Fleet 都連在 B 時，先正常做一個更高版本的 B→A 簽署搬遷。再停／隔離 B，取最新的變更後資料搬回。未回覆者仍要重新連接；先前撤銷的憑證不會因為網址回來就復活。
- B 已無法啟動，已確認 B 的 Fleet 收不到新搬遷說明時，不能保證自動回 A。應恢復最新狀態並繼續提供 B，或安排明確重新連接；確認 B 後，Fleet 不會再自動試 A。

緊急還原更舊備份是可能遺失資料的安全復原事件，不是本手冊的例行 rollback；需另做決定，檢查版本下限與已接受／不確定的工作。搬遷時不要順便降版。

## 停多久、怎麼算成功

準備完成後，先預留 **30–60 分鐘**作為操作安排，不是測量保證。核心停機時間包括等工作結束、停機、最後備份／檢查、傳輸、目的地啟動／驗證及 DNS 收斂。資料量、網速、目錄服務／憑證問題與重新連接可能更久；五秒搬遷回覆不是總停機時間。排時段前要先用實際大小的靜態副本測速。本機演練不代表跨作業系統或 VM 的效能，小型 VM 與助理負載仍需實測；初次核心 Hub 驗收先排除助理 provider 負載。

成功條件：只有一個正式程序；Hub id、簽署金鑰與 Fleet SPKI 不變；設定／簽章／資料庫／版本檔相符；沒有未完成的設定 journal；Fleet 憑證世代符合預期；TLS／DNS／目錄可用；原分享／房間／附件正常；沒有重做不確定答案；舊機器自動啟動仍關閉；最新資料的搬回路徑已確認。

## 演練做到哪裡

[保留的測試](../../tests/hub-host-move-m3792.test.ts)使用私有來源、目的地與會員資料目錄，實際驗證金鑰、憑證、設定簽章、SQLite／版本下限／內容加密、搬遷簽章與會員起點；關閉來源 DB 才複製。目的地可解密內容、驗證原 seal；手改主機名稱或缺內容金鑰會被拒絕。已回覆會員保留配對位元組與憑證世代，離線會員被撤銷，返回原網址必須有新版本。
