# Hub S4: member execution design

This implements the restricted member boundary in [hub.md](hub.md#s4-restricted-member-execution), on the experimental alpha line. Both Hub switches remain off by default.

An exposure is usable only when the member has exact, current local consent for its owner, revision, data view and tool policy, and a trusted execution adapter can enforce isolation. A provider name, a read-only CLI flag or an instruction is not evidence of isolation. Ordinary Claude/Codex conversations, including idle, busy and resumed conversations, are unavailable for Hub execution. The initial implementation installs **no production execution adapter**: publication and execution refuse until a separately reviewed adapter supplies the required isolation. It does not start a CLI, paste into a pane or reuse a fleet conversation.

The execution service owns opaque context handles. Remote DTOs, copied handles and imported human receipts cannot create them. Each context belongs to one immutable question, asker, owner, exposure, grant and room. Local policy is resolved again after waits and at every effect. Disabling membership, replacing the link or changing policy permanently fences that context; restoring a switch cannot revive it.

The gateway exposes only member-installed read connectors, scoped to the approved data view. There is no shell, SQL string, filesystem path, URL, arbitrary network client or ordinary fleet-tool passthrough. Arguments are validated, canonicalized and copied before hashing; actual dispatch uses those same bytes. A trusted adapter is part of the member's security boundary, must not expose native/child tools or ambient credentials, and cannot be installed from a Hub frame or prompt. Test adapters are inert fixtures, not production isolation evidence.

Admission uses S1's signed-question and restricted-outbox boundary. S4 persists context and exact operation intents before authorization, consumes each intent before dispatch, and never retries an applied or uncertain intent after restart. Leases must match the actual phase, operation, policy revision, link and revocation generation. Tool results and answers are checked again before disclosure. Final answer bytes and ID are fixed before requesting their release lease; retransmission belongs to the journal and never regenerates a response.

High-risk requests create a durable local proposal containing the exact action, canonical arguments digest and consequences. They appear in the destination owner's local Needs-you through the member composition adapter. The restricted service has no approval or execution method for proposals. Any subsequent local action is a separate ordinary local operation with its own human receipt and replay checks; Hub identity and foreign receipt references supply no local authority.

Required persistence, audit, local Needs-you and online authorization adapters are mandatory. Missing dependencies, unavailable authority, corrupt/rolled-back state and unknown operation outcomes fail closed. Composition must use private member storage and an independent monotonic version floor; a failed save must not report success. No route, store, timer, provider or data connector starts merely by importing this module.

Acceptance covers enforced refusal of unisolated providers; forged/cross-context handles; policy and mode changes across awaits; unapproved data/tools and argument substitution; exact leases at begin/tool/answer boundaries; durable replay and uncertain holds; owner-local proposals without remote approval; and audit/persistence failure before effects. Positive gateway tests use inert adapters and private SQLite databases. Native delivery acceptance is required before adding a real Claude/Codex adapter; this slice advertises neither and invokes neither.
