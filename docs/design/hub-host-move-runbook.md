# Preserving a Hub identity during a host move

Design and rehearsal only, at `e05fb8189698dd4bf804e3993a914e8e03a911d9`. No running installation was inspected or changed. See [中文操作手冊](hub-host-move-runbook.zh-TW.md) and [scratch evidence](../evidence/hub-host-move-m3792/verification.json).

## Decision in plain words

**The Hub can move with its identity, database and signed setup manifest. Do not initialize a new Hub.** Move the complete, stopped state together, using the same AgEnD build first. Its identity is not tied to a machine serial number, OS hostname or absolute home path. Its configuration, keys, certificate names and database revision floors must still agree.

**A new computer name does not require a new Hub URL.** Preferred route A keeps both public Hub URLs and routes them to the destination. This preserves existing Fleet pairing, including Fleets that were offline during the move. They reconnect using the same saved credentials. No re-sharing is caused by the host move; existing grants, expiry and sharing-consent checks still apply.

If the public Fleet connection URL must change, use route B. Online, compatible Fleets that acknowledge the signed relocation and keep that exact live link through the commit retain their pairing. Offline, old or dropped-link Fleets are revoked by the current implementation: their owners must use **Reconnect** and company sign-in. Do not promise automatic re-sharing for that group; verify each existing share and permission after reconnect. Changing the URL only after the source is stopped does not provide the online-follow guarantee.

This is a single-writer cold move, not replication or high availability. There is no cross-host lock that makes two copied Hub homes safe to run together.

## What to inventory, without displaying secrets

`HOME_DIR` below means the selected AgEnD data home, not the OS home. Record paths, sizes, permissions, build/source version, Hub id and public fingerprints in a private operator checklist. Never paste credentials, PEMs, database content or a transfer archive into chat or GitHub.

| State | Carry / host binding |
|---|---|
| `fleet.yaml` | Carry the Hub configuration with the state. Hub id, public origins, listener addresses, browser TLS references, directory settings, administrator, coexistence and retention participate in the signed plan. Do not casually edit the sealed block. |
| `hub/init-manifest.json` | Carry unchanged with its matching configuration; it is the issuer-signed initialization seal. Hostname, bind or path edits can invalidate it. Supported settings writers reseal changes. Never run `hub init` to repair a copied seal. |
| `hub/keys/` | Carry all files, including identity metadata, issuer private/public keys, member TLS private key and certificates, and `content.key`. Preserve Hub UUID, issuer id and member SPKI. A fresh member key breaks existing pins. |
| `hub/hub.sqlite`, `hub/floors/transport` | Carry one consistent stopped set with the content key. SQLite contains transport credentials/generations, sharing/grants, rooms/history, sessions, audit, settings decisions, relocation revisions and encrypted attachment segments. Missing companion state fails closed. Do not restore the DB alone or reset a floor. |
| SQLite `-wal` / `-shm` | After every writer closes, take the final complete snapshot. A checkpoint plus clean close is preferred; check return/result. If sidecars remain, preserve the stopped database set together. Never delete a WAL to make a backup look clean or copy only a live `.sqlite`. |
| `hub/secrets/` | Carry private directory-bind, enrollment-code and join-delivery keys and other existing files. Secret rotation is a separate operation. The stored bind reference is relative to this data home. |
| All other `hub/` material | Carry address/certificate versions and selectors (`web-tls`, `web-address`, `member-address`), settings receipts/journal, init operation and revision evidence. SQL decisions and file images must match. Complete/recover any pending settings/setup operation on the authoritative source first. |
| `hub/install-inventory.json` | Carry as historical setup evidence. Its addresses and paths may describe the old setup. It is not a live config, permission or deletion manifest; do not rewrite it to authorize the move. `agend hub handoff` explains it. |
| `hub-assistant/assistant-state.json` | Outside `hub/`; carry if preserving Hub-assistant selection/settings. Account profiles and provider credentials require a separate supported transfer/re-login check. |
| Fleet dashboard/session/vault files outside `hub/` | Classify separately if the installation shares an account with a Fleet. `web.token`, web sessions/TOTP, managed credential vault/key pairs and profile directories are not Hub pairing state. Do not copy all agent/fleet identity just to move the Hub. Do not silently discard files required by the chosen Hub assistant. |
| Browser TLS | Certificate SAN must cover the public browser hostname; users/apps must trust its issuer. Preserve usable material for an unchanged URL, or provision trusted destination browser TLS via supported settings. This is distinct from the pinned member certificate. |
| OS service, binaries, sockets, PIDs and paths | Recreate the destination's native service using the destination package, account, `AGEND_HOME`, PATH and log path. Do not copy launchd/systemd units, process locks/PID files, IPC sockets, macOS binaries or `node_modules` across platforms. Retain old service definitions privately for rollback. |

Every Hub directory/file must be owned by the destination service user, non-symlink and private (directories 0700, files 0600). Matching numeric UIDs across systems is not sufficient. The scratch copy initially failed the real private-file check until destination modes were repaired, confirming this is an actual prerequisite.

macOS Keychain login is not a portable Linux credential file. A copied assistant profile may not be signed in. Preserve a managed vault with its key as a pair where used, and verify the selected backend's supported Linux login separately; never export a Keychain secret through this runbook. Core Hub migration must not depend on an untested assistant login.

## Before scheduling the move

The operator fills in: approved source/destination data homes and service accounts, installed build/source, browser/member URLs and DNS owner, destination reachability, certificate plan, directory reachability, backup size and safe transfer method, assistant use, and whether the source coexists with a personal Fleet. IP or DNS pending means **preparation only**.

1. Obtain a fresh, explicit user OK before each SSH/server-access session, including a reused connection or read-only remote check (decision `cab89340`). This design grants no server access and no live stop/start. Obtain the move window and service-impact approval separately.
2. Install the same AgEnD build for the destination OS/architecture without initializing a Hub or starting its service. Validate its native dependencies. Keep destination auto-start disabled and deny ingress until cutover. A package version label alone is not proof of the same source/schema.
3. Prefer a dedicated destination service account. If the source uses `same-user-pilot`, its service also controls other agents. The stop window affects them; migrating the Hub does not migrate their folders or grant new sharing consent. Do not change coexistence or directory fields by editing YAML merely to make the destination look dedicated; preserve the sealed plan or schedule a supported, reviewed change.
4. Make both hosts able to use the same sealed listener configuration. Prefer explicit loopback binds with a separately provisioned front end on each host; the member front end must pass TLS through unchanged because Fleets pin the Hub's member SPKI. Do not terminate member TLS with a proxy's unrelated key. Browser proxy/TLS and the optional preview endpoint need their own plan. Any member-TLS identity mismatch can stop automatic retries with `key-changed`, even with an unchanged URL: a TLS-terminating proxy, a front end serving its own certificate/502 page while the backend is down, or partial/fresh keys can trigger it. Correct the endpoint first, then affected owners must use **Reconnect**; waiting for another retry is insufficient. When its backend is down, the member front end must refuse connections, never answer TLS with its own certificate. If source binds a source-only IP, use a supported listener-only settings change while it is still authoritative, then rehearse. A target-only IP cannot pass the source's bind probe.
5. Provision DNS, firewall, directory trust and browser TLS before the outage. Browser and member origins remain distinct. A destination OS hostname can differ while old public DNS names remain aliases. Verify this is possible; do not assume an old local-only name can be moved by DNS.
6. Drain user activity and in-flight Hub questions/assistant work. Ask people to avoid changes during the window. Stop new joins; wait out the UI's recent-join fence (up to ten minutes). Record current shares/grant expiry and Fleets to check, without dumping private chat content. Do not retry or replay unanswered work automatically.

Before public DNS/routing switches, include an isolated destination member-TLS check in the cutover preflight: after the source is fenced and the copied destination listener is started, dial the actual destination front end by its destination IP with the expected member hostname/SNI. Use an inert TLS handshake with **no Fleet credential**; verify the certificate SAN, validity and exact existing member SPKI, not just a successful TCP/HTTPS response. Keep public member traffic blocked until this passes. Verify the backend-down behavior separately: connection refusal, no alternate certificate or TLS error page. This is server access and still needs that session’s user OK.

## Route A — keep the public URLs (recommended)

1. Keep the original Hub configuration, identity and both public origins. Arrange that DNS/routing can point those names at the destination. If necessary, first make a supported listener-only change on the source; it does not revoke Fleet bindings.
2. Announce maintenance. Positively stop the source service and its writers, then disable/fence its automatic restart. Check the service state, exact process ownership, browser/member/preview listeners and background assistant writers. An exit command alone is not proof. If a coexisting Fleet must keep running, first design an explicit Hub-only stop/isolation procedure; do not assume the service stops only the Hub.
3. Before the final snapshot, inspect the destination configuration plan. If the source config includes Fleet instances, bot channels or a Hub-member role, **do not start a blind full-config clone**. Review a Hub-only destination config that preserves the sealed `hub` block exactly and retains required globals/dependencies; exclude unrelated agents/transports without changing the source. Use inert config validation and review the exact diff before any destination start. If this cannot be established, stop and split the installation as a separate task.

4. Only now make the final private snapshot: matching config, entire `hub/`, relevant assistant settings and deliberately selected external dependencies. Record file counts/sizes and a private checksum manifest. Check SQLite integrity after clean shutdown with a read-only/inert tool. Retain that snapshot and the stopped source as rollback material. Pre-copying bytes is allowed for speed, but the post-stop image is authoritative.
5. Transfer privately to the fenced destination; restore ownership/modes before any Hub opener. Verify checksums, complete state set, keys/Hub id/SPKI, initialization seal, schema compatibility and external file references. Use only an inert verifier during preflight, not a Fleet start disguised as a check. Never publish private checksum manifests or archives.
6. Recreate the destination's systemd service, explicitly pointing to its data home and installed executable. Use `agend install --no-activate` where supported and inspect the generated definition. Ensure the user service manager/session and boot persistence work for the selected account. Do not run `hub init` or copy the source launchd file.
7. With the source still stopped/fenced, keep public member traffic blocked and start **only** the destination under the agreed live go-ahead. Until its Hub listener is up, the destination member front end must refuse connections rather than return any TLS response with its own certificate. Perform the credential-free SPKI/SAN check through that actual front end described above; only then switch public DNS/routing and admit Fleet traffic. Verify directory sign-in, Hub health, current Fleet links, one existing shared agent, original room/history and an attachment. Check pending/held work explicitly; a restored database is not permission to repeat uncertain operations.
8. Keep the old host fenced for the rollback window. Restore normal use only after checks pass. Fleets, including previously offline ones, can reconnect to the same URL with their saved bindings; normal consent expiry/lapse still applies.

## Route B — change the Fleet connection URL

Do steps 1–6 of preparation first. Keep the browser URL unchanged initially to reduce simultaneous changes. Route B requires the live source to publish the move; an inactive copied Hub cannot inherit its socket acknowledgments.

1. Bring every Fleet that must avoid reconnect/re-share online and current. Check it supports `member-relocation-v1` and `welcome-caps-v1`. Resolve legacy/offline Fleets with their owners beforehand. No unacknowledged Fleet is guaranteed to survive this change.
2. On the source's own Settings → Hub → **Fleet connection address**, use **Change connection address**, the new public member URL, and a **new portable backend port** valid on both hosts. Keep A’s front end mapped to the old backend port; after remount that old port must be closed. Point B’s destination front end at the new backend port. Commit through the supported control. Do not edit YAML/identity metadata manually. The source probes a local bind, not the destination. A new hostname gets a certificate with a new SAN under the **same member private key/SPKI**.
3. The running source reserves a new revision and sends per-Fleet, issuer-signed statements. Members durably save them, then acknowledge on their current links. The shared acknowledgment deadline is five seconds; the host's prepared confirmation expires after five minutes. Pending relocation itself has no time expiry, but the confirmed chain is limited to eight hops. Count the confirmed hops on **each member** before the change (the owner-held `hub-member/<hub-id>/member-origin.json` history, without copying credentials). A move and a later return consume **two confirmed hops**. To reserve transparent rollback, a member must have at most six confirmed hops beforehand; at eight, its next promotion is denied and its owner must Reconnect. Do not reset the history to create headroom.
4. Read the result's **followed / must reconnect** list and capture the post-commit state privately. Only exact live acknowledgments retained through the SQL boundary keep the credential and generation. All other active Fleets are revoked and their generations advance. If any required Fleet is excluded, **pause**: do not pretend cancelling the transfer restores its old credential. The address decision has already committed; choose a reviewed forward recovery or explicit reconnect.
5. Verify that a fresh connection to A now gets a temporary connection failure, never B’s certificate. Reusing the same backend port for a hostname change can present a B-only SAN at A; a member trying B then A can enter terminal `key-changed` and stop retrying. “Stop immediately” does not eliminate that race. If separate ports/ingress isolation are unavailable, stop this runbook and review the topology first; do not promise automatic following. Then carry out route A's stop/fence, final post-commit snapshot, transfer, verify and single-destination start. The new endpoint may be unavailable while copying; members with pending B try B then A and retain that pending statement across restart. The current remount closes the old member listener—there is no built-in old-address grace redirect. Do not run a stale source clone to provide one.
6. Verify the moved Fleets complete pinned TLS/welcome/reconciliation at B; only then does each member promote B as its anchor. After promotion it tries **B only**, including after member restart. Its original pairing file remains unchanged. Validate existing sharing/grants without changing agent backend/folder/runtime; no consent may carry across an agent incarnation change.
7. For excluded Fleets, owners use Settings → Hub → **Reconnect**, company sign-in, then check sharing and who-may-ask. Existing rows in the Hub do not prove that new-generation consent is valid. Re-share only where required through the ordinary owner flow.

A new browser URL is a separate supported **Hub address** change. It can end browser sessions and requires a trusted browser certificate; people should expect to sign in again. AI-app consent/redirect origins and preview URL must be checked separately. Do this as a second change after the host move is stable, unless the old public browser URL cannot be retained. If it cannot, rehearse both supported address changes before the final stopped copy; no manual resealing.

## Both public origins change: IP to DNS

When the old bare-IP URLs cannot follow the host, route A is unavailable. Use route B, changing **both** origins through supported controls on the running source. The following is a generic template; real endpoints belong only in the private annex.

| Channel | Public destination | Hub listener / TLS |
|---|---|---|
| Browser | `https://hub.example.test` (443) | 8443; public CA certificate for this DNS name, imported through **Hub address** settings. A kernel 443→8443 redirect changes only the TCP port; it does not terminate TLS. |
| Fleet member | `https://hub.example.test:9443` | 9443; **existing member private key**, with the self-signed DNS-SAN certificate generated by **Fleet connection address**. Self-signed is intentional: Fleets trust the pinned key, not the public CA. |

A self-signed IP certificate can become a self-signed DNS certificate without changing the member SPKI. The signed statement supplies the new origin, and the generated certificate supplies its new DNS SAN. A public wildcard certificate normally has a different private key and must **not** replace the member certificate. CA/key rotation of the member channel is outside this move; current member-address settings have no CA-import option. A later member-key rotation requires each owner to Reconnect and needs a separate card if ever requested. A different CA alone does not define the pin: the decisive checks are the retained SPKI, correct SAN and validity; this runbook does not implement alternative same-key CA issuance/import either.

Before the move, take a **private manual list from Administration → Connected fleets**: Fleet label/owner, connected/offline state, reported version/unknown/update warning, whether current relocation capability is actually established, confirmed-hop count and two-hop rollback headroom where owners can supply it, and an owner contact for recovery. Mark offline, too old, unknown capability, insufficient hop headroom and unstable links as at risk. A version number alone does not prove a currently negotiated capability. No export button is assumed. Recheck immediately before confirmation; only the final followed/reconnect result decides who was kept.

From the source's **own AgEnD dashboard → Settings → Hub** (not a Hub browser session that the address change may end):

1. While the source is the only writer, change **Hub address** to the new browser DNS origin. In **Advanced**, choose a source-valid portable listener on 8443; import the browser CA certificate/key through that control. Keep the old member listener available for the subsequent signed relocation. Browser users may need to sign in at the new address after cutover. Let the web-address remount finish, then explicitly wait for every required Fleet to reconnect/current at the **old member origin** before proceeding: the web remount also drains the member listener. Do the signed member relocation last.
2. Change **Fleet connection address** to the new member DNS origin on 9443. Its **Advanced** listener must be portable on the source (for example explicit loopback), with a port distinct from the old member endpoint. Let the supported flow reissue the DNS-SAN certificate under the retained key. Collect live acknowledgments and the final at-risk list, then stop/fence and copy the post-commit state.
3. Start the destination only after the source is fenced, with public ingress blocked. If portable loopback binds were used during the source decisions, use the destination's own Settings → Hub **Advanced** listener-only changes to select its actual local interface IP: browser 8443 and member 9443, keeping both public origins and certificate selections unchanged. Do not hand-edit the sealed fields. Listener-only edits preserve Fleet bindings even if no Fleet can connect yet. The destination is now the sole authoritative writer. The web listener-only edit can also end Hub browser sessions; keep using the host dashboard for management.
4. For a kernel/nftables 443→8443 redirect, verify which destination interface address the redirected packets reach. It does **not** make an interface-directed packet reach a loopback-only listener. Choose the matching explicit local bind or a separately reviewed forwarder; do not use an unsupported wildcard bind or silently add routing/sysctl changes. The exact rule, persistent rule ownership, existing rules and firewall permissions must be reviewed once the VM IP exists; this document installs none.
5. With the source still fenced, perform the real-ingress credential-free probes: browser hostname/SAN, valid CA chain and HTTPS application; member hostname/SAN and **original** SPKI on 9443. Probe from a path that actually traverses the redirect; a local connection may use different nftables hooks. Verify backend-down refusal. Only then admit public traffic/switch DNS and check the exact kept Fleets, existing shares and rooms. Offline/old Fleets use Reconnect as above.

The private annex holds the chosen old/new ports, real DNS name, pending destination IP and any confirmed rule details. No concrete nftables command or live connection is authorized by this design.

## Rollback without restoring stale authority

- **Before any address decision or destination write:** leave the destination fenced and resume the stopped source from the unchanged authoritative image. Return DNS/routing if needed. Verify it before reopening use.
- **After destination use, even on route A:** stop/fence the destination first. Copy its **latest** consistent complete state back to the source account, normalize ownership, preserve the same build and URLs, verify, then start only the source. The old pre-move image would discard accepted work or revive older revocations; do not use it as a routine rollback.
- **After route B commits:** keep the latest state and the new URL reachable even if the process must temporarily run on the old machine. Changing the machine back does not require changing B back to A; route B to that machine where possible. Do not restore old database/floor/relocation files to make the previous name reappear.
- **To return the public URL to A:** while B is still the sole authoritative running Hub and required Fleets are connected, perform a new supported, higher-revision **B→A** relocation. Then fence B, take the latest post-decision image and cold-move it back. Budget another confirmed hop for the return. A member already at the eight-hop limit cannot promote the return and must Reconnect; count both outbound and return hops before promising transparent rollback. Any non-acknowledging Fleet needs reconnect again. Already revoked credentials never become valid merely by returning to an earlier address.
- If B cannot run and confirmed Fleets cannot receive a new statement, there is no guaranteed transparent return to A. Restore the latest state serving **B**, or plan explicit member reconnects. After a member confirms B it no longer falls back to A.

An emergency old backup restore is a data-loss/security-recovery event, not this rollback path. It requires a separate operator decision and review of all anti-rollback floors and accepted/uncertain work. Do not downgrade the binary and schema during the move.

## Downtime and acceptance sheet

Reserve **30–60 minutes** as an operator planning allowance after preflight, not a measured promise. Core unavailability is source drain/stop + final snapshot/checks + transfer + destination start/checks + DNS/routing convergence. Data volume, transfer rate, directory/certificate issues and reconnects may dominate; the five-second relocation wait is not the downtime. Measure a real-size inert copy before choosing the window. The local scratch timing is not a Linux VM or cross-OS capacity benchmark. A small VM's headroom, storage, CPU and assistant capacity remain unproven until it exists; exclude assistant provider load from the initial core-Hub acceptance.

Success requires: exactly one authoritative process; same Hub id, issuer id, SPKI and required keys; matching config/seal/DB/floors; no incomplete settings journal; expected member credential generations; current TLS/DNS/directory; existing eligible share/room/attachment checks; no replay of uncertain answers; source auto-start still fenced; and a tested latest-state rollback location.

## Rehearsal evidence and limits

[The retained scratch test](../../tests/hub-host-move-m3792.test.ts) creates source, destination and member homes privately. It uses real keys/certificates, sealed settings writer, SQLite/floor/content encryption, relocation signature verification, member pending/anchor state and decision retention/revocation. It closes the source database before copying, reads encrypted content on the destination, proves a manual hostname edit and a partial key set are rejected, preserves an acknowledged Fleet's pairing bytes and binding, revokes an offline Fleet, and prepares a higher-revision return move.

A separate loopback transport case pairs a real pinned member, closes the source listener and database, copies to another private home, and successfully reconnects to the destination at the unchanged origin with unchanged pairing bytes. The address-change case’s live-link currentness and remount callbacks are fixture ports, not proof of an OS service/DNS move. Existing `hub-relocation-network-3429` tests separately exercise the actual TLS/WebSocket acknowledgment/reconciliation path. The scratch does **not** start a Fleet, contact a directory/provider, prove launchd/systemd behavior, move a real account credential, measure VM capacity, demonstrate a real shared-agent answer on both OSes, or guarantee that a human will fence two hosts. Those checks remain gates in the live runbook. No production implementation changed.
