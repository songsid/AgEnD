# Room directory selections

This slice follows #3864. It completes the room pickers and snapshot people expansion from Lumen's section6 at aafd4ae2c. It adds no role-policy activation or review gate.

Room creators and current room managers can search the existing bounded directory person/group prefix helpers. Searches share the mount's physical directory admission, retain the current browser and creator/manager checks across the read, and return at most20 suggestion rows. Suggestions create no Hub person, session or room membership. The optional C-owned roomTeamCandidates(db,prefix) callback projects Team suggestions; Team SQL stays C-owned.

GET /hub/v1/rooms/candidates/group/:id returns {kind:'group',id,name,people:count} for a selected group. The server resolves its GUID, reads every eligible direct member under the configured user filter/base, then rechecks the group's GUID and DN. It does not follow nested groups. The operation has a five-second connection/search deadline,100-entry pages and a4096-entry defensive cap. Any referral, partial/size-limit error, invalid/duplicate identity, changed group or cap breach refuses as group-unavailable. The chosen-group preview returns only a count and label; room creation/addition reads a fresh roster. The CLI library's locked source accepts SizeLimitExceeded only when sizeLimit is nonzero, so this complete read explicitly uses sizeLimit:0; the cap/deadline still bound it.

Room creation and POST /rooms/:id/members accept person, Team, group and assistant selections. People are the deduplicated union, including the creator and existing members for adds. More than100 returns409 {code:'people-limit',people:<union count>,limit:100}, with no room/member write. An incomplete chosen group returns503 {code:'group-unavailable',group:<GUID>}; the UI preserves the rest of the draft selection. The group/Team expansion is a snapshot; later source changes do not rewrite membership. Team revisions/expansion are rechecked in the write transaction. Each person's eligibility is checked before commit.

hub_people remains the permanent successful-Hub-sign-in witness used by catalog.subjectSignedIn and session initialization. Pre-sign-in names/login feedback therefore live in the additive s3-room-directory component's hub_room_people table, written only with the final room/member transaction. Room projections prefer actual signed-in names, then this directory feedback, and report signedIn:false until a real Hub sign-in. Selecting someone never manufactures a session, approval or sign-in record. They discover the retained membership on first sign-in.

Archived rooms remain readable; their detail skips the live invitation manager port because its actions require an unarchived room. Normal membership/history floors and owner consent remain unchanged.

Acceptance uses production local HTTP/SQLite and the exact directory adapter with inert LDAP/TLS peers. It is not a real AD/Fleet/browser or joined-UI walkthrough. UI wording/selection handling and concrete C/A composition remain cross-track follow-ups under S142. Older binaries refuse s3-room-directory: retain DB/content keys and deploy a compatible correction rather than dropping labels or input history.

The published shared client consumes object envelopes: candidate searches answer `{candidates:[...]}` and an owner's exposure-room projection answers `{rooms:[...]}`. Creator-policy GETs include named person records and Team name/head counts; PUT remains an ID-only selection. These are display projections and do not change eligibility, consent or creator authority. The real-server browser checkpoint found and pins these response shapes. The group snapshot is complete for direct members only; nested groups are intentionally outside it. Sequential per-person eligibility rechecks can be slow for the largest selections, as noted in ordinary review; that cost is not presented as a measured live-directory result.
