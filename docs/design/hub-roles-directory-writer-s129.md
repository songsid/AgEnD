# Role administration at the sealed directory writer

This slice follows #3821. The internal sealed-settings writer can consume an opaque administration witness from its own trusted dependency. The production singleton does not yet provide that dependency, so this does not activate auxiliary Directory Save or roles at startup.

The existing failure was in the writer's prepare method: it accepted a browser administrator only when that person was the configured root. A valid auxiliary administrator therefore passed the earlier proof engine but still received `denied` at the actual writer. A successful `current()` callback alone remains insufficient.

The optional `directoryAdministration` provider returns the writer's exact mounted decision and its source binding. The writer captures the provider and decision-reader functions, checks the sealed Hub and configured root, and requires the source's getter to be that decision's own administration-proof getter. Inside the decision callback, an actual opaque frame is mandatory. The preparation retains the decision identity; a replacement mount or omission of the witness cannot turn the prepared operation into a legacy root operation. Actor, session, request and source are still proved by the retained witness. Host/D3 calls never consume a browser witness.

The proof engine forwards that same opaque witness to prepare and commit. The writer checks it through material preparation and both SQL proof callbacks. A last writer-clock callback could itself retire the browser, so the final role assertion runs afterward. Its existing explicit permit method returns the wall-clock sample from that assertion, carried through HubCore and the witness. The writer validates the scalar against its creation/deadline and the preceding writer sample without invoking another clock callback. It does not renew the five-second permit or extend any recovery deadline. Normal assertions and legacy root/D3 sampling remain unchanged.

Before SQL commits, an authority failure rolls back the decision and leaves staged material for the existing recovery path to discard. After the SQL commit, installation and recovery complete the exact recorded operation without consulting the old browser permit. The configured root, canonical role graph, consent and recorded actor are not rewritten; the existing generation/revision rebind remains the decision kernel's work. Compensation still uses the original bounded SQL intent.

Validation uses real private identity/seal/files and actual SQLite, session, audit, role cutover, transport and decision code. SQLite is in memory and the external floor is a fixture; directory answers and the mounted source projection are synthetic. Six step-hook interruptions model recovery at staged/decision/secret/manifest/config/done boundaries. They are not SIGKILL, WAL durability, mounted-route, browser, container or live-directory evidence. The existing root directory-decision, writer and session-transition suites retain their own scopes.

Remaining S-129 work includes the production source/provider, a fresh permit near the effect after potentially slow directory work, actual successor-session authorization and release, mounted Directory Save, startup cutover and the member/SSE/issued-recovery acceptance. No new public route, token or session is introduced here. A user-facing UI and PNG round do not apply to this internal slice.

Rollback before activation is to leave the optional provider uncomposed. Do not restore an older database, floor or committed settings journal. Parent-first plain alpha sync, conflict review, exact-head CI/readiness, full-S129 and alpha.3 release holds remain in force.
