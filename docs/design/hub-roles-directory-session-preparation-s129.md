# Preparation can attest a session and stage its handoff

This follows #3832. A directory preparation may spend up to five minutes in TLS and directory checks, while its final effect proof lasts five seconds. Reusing the effect proof at the session attestation and rotation-preparation boundary would make a valid slow operation fail before it could acquire fresh publication authority. The mounted session projection also discarded the optional opaque proof, which left an auxiliary administrator on the configured-root-only helper path.

The internal session proof is now exactly one of an opaque effect witness or an opaque preparation, together with its bound source. Only recent-authentication lookup and staging a token-bound rotation accept preparation. The helpers retain the actual Core's directory identity, immutable configured root and directory epoch, and prove the same actor/session/request/source through the opaque handle. Mixed envelopes refuse. Method and packet-reference checks retain defensive validation of this internal typed contract; individual necessity is not claimed for every repeated identity check.

Preparation does not renew authentication, extend ordinary effect authority, grant self-use, install files or publish a directory decision. The existing attestation must still be current for that exact real session. Rotation still proves the exact token hash and active session. A preparation-marked rotation retains the role-required bit: after slow checks, the actual SQL decision needs a newly acquired effect witness, and releasing its successor needs fresh authority in the new directory generation. Legacy root-only helpers remain unchanged when no proof is supplied; bare auxiliary callers still receive no attestation or rotation.

HubSessions and the mounted HTTP session projection forward the optional proof without interpreting it. The directory HTTP route and host-lifetime controller do not yet produce or consume this new preparation input. No automatic role cutover is registered. Complete mounted auxiliary Save and full S-129 acceptance remain later work.

Verification uses actual Core, HubSessions, role preparation, canonical policy, persisted clock and SQLite with fictional directory responses. The mounted projection tests use an initialized sealed Hub and loopback HTTPS sign-in, then call the private session projection. Private SQL handoff tests use synthetic file-image hashes and the real decision kernel; they do not prove file installation, a mounted Save response or crash recovery. Root and auxiliary cases preserve recorded actor, assignments and denies and retire the old session. Foreign-source tests use genuinely issued opaque preparations with deliberately different private constructor bindings, to exercise the Core boundary rather than only a malformed handle.

No browser, container, real directory/account/Fleet, backend CLI, native-platform or pilot acceptance is claimed. No user-facing behavior or built-in Hub skill changes in this slice. Parent-first plain alpha synchronization, conflict-resolution review and exact-head readiness remain mandatory; the coordinator alone merges. Before controller activation, leave its later preparation integration uncomposed. After any committed directory change, retain forward recovery and never restore an old policy, database or floor.
