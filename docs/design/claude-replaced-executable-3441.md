# Claude Code executable replacement (#3441)

AgEnD's updater and postinstall install/verify AgEnD, synchronously before service activation. They do not upgrade an existing Claude Code installation. The same is true at the two reported release tags. The field evidence supports an independently replaced executable whose old inode kept running; it does not identify the installer or prove a partially written image.

On Linux/WSL, after a Claude pane becomes ready, AgEnD inspects only its exact tmux pane PID and a bounded, unbranched shell/env wrapper chain. A filesystem worker reads `/proc` and package metadata; it never invokes Claude, including for `--version`. The shared pool retains at most two physical workers until they exit, and each caller has a two-second deadline including queueing. Unknown metadata is not evidence of a bad executable.

A positive deleted or npm-temporary Claude image claims one repair budget for that daemon. Under the pane-write lock, an authoritative idle capture and current launch owner are required. Delivery remains held while a temporarily missing stable launcher is checked for up to ten seconds, the session is checkpointed, the installed launcher is resolved again, and PID/start-time/image plus launch ownership are revalidated. The replacement uses the exact saved Claude UUID (unless this was an explicit fresh start). A missing, invalid or unreadable UUID holds rather than selecting a different conversation. It must pass ordinary startup readiness and a fresh executable inspection. Stop/pause/replacement fences apply across awaits and immediately before the tmux respawn. No user message is replayed.

There is **no global or model-specific Claude minimum table**. When Claude itself prints `Claude Code A does not support this model; version B or newer is required`, AgEnD checks the currently resolved installed package, not the old running executable's path. If the disk version meets B, the same single repair budget applies. If it is below B or unknown, there is no restart: one plain notice asks for a Claude update and points to `/login`. A process already proven compatible ignores a restored older error line.

A successful repair logs and posts one plain notice. A failed runtime repair blocks delivery and automatic supervision, preserving the session and posting one failure notice. A failed startup repair throws the existing terminal `UnsupportedCliError`; it cannot enter startup's failed-resume/fresh-session fallback. The ordinary lifecycle surfaces that terminal failure. The budget does not renew on natural spawns; an explicit operator restart creates a new daemon.

Limits: this is a Linux/WSL tmux guard, not native Windows support or an updater lock with a third-party installer. A second external replacement can still occur after the final proof. Inaccessible/ambiguous process metadata remains unknown. Loaded JS cannot borrow the current package's version as proof of its already-loaded code; an unverifiable replacement fails closed after the one attempt. There is no account/vendor probe, automatic CLI installation, host command in the notices, or automatic resubmission.

Rollback: revert the guard commits to restore the prior launch behavior. No schema, durable state or configuration is added. Session markers remain backward compatible.
