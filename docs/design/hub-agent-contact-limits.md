# Hub question contact limit

M-3160 implements setting B from Lumen's design at `673782a40`, approved by the owner. Per-agent contact allowlists, Hub General and MCP agents are outside this change.

In Fleet **Settings → Hub → Shared agents**, **While it answers a Hub question, this agent may not contact other agents** defaults on. Existing shares also default on. A persistent Settings notice names the setting and where to turn it off; the owner acknowledges it once per Hub membership. Publishing or revising the choice uses the existing sharing confirmation and revision check. The choice is local Fleet policy, not a new Hub wire field.

Each direct or room question opens an independent window when the agent's daemon writes it into the idle pane (M-3660; originally at the connected input handoff). It lasts for that answer turn, with 30 minutes as a safety cap. This duration was confirmed by Lumen. Retries do not extend it. A malformed answer does not close it. Questions are answered one turn at a time, so at most one answer turn restricts an agent. The Fleet persists windows separately from the member service, so disconnecting, disabling Hub membership or restarting cannot silently remove them; the agent's daemon re-tells its current turn on every connection, which ends windows it is not answering. No question is resent.

The shared outbound send handler refuses `send_to_instance`, `delegate_task`, `request_information` and peer-directed `report_result`; the broadcast handler refuses the entire broadcast before admission. This covers MCP, agent CLI and direct IPC calls. `agend-hub` remains reachable for answers. `hub_room_post` has its own limits and is unchanged. The refusal says why, names the question, and says contact works again from the next turn.

This closes a direct contact path, not all access to the Fleet's information. The agent keeps its own tools/folder, may remember earlier information, and can contact other agents after the answer turn ends (including after 30 minutes even if still answering). The owner's and other agents' turns are never refused (M-3660). No backend launch/tool catalog is changed.

The local window file contains agent names, opaque correlation IDs and deadlines only, with private permissions and atomic writes. Missing file means no windows; malformed/unreadable state refuses contact and new Hub input until repaired. The setting remains on by default when an older Settings client omits the new field.


## M-3660: only the answer turn (2026-11-24)

The live m365 case on beta.21: an answer refused as "no longer open" held its question, but the window stayed for its 30 minutes and refused every agent message in every turn, the owner's included. The user's direction:

- **A Hub question is a turn of its own.** The agent's daemon writes it only into an idle pane: never into a running turn through the CLI's native queue, a busy composer or a steer, which Claude merges into the running work. While the Hub answer turn runs, every other delivery waits for it too. A question that waits longer than the 30-minute idle wait is reported undelivered (held as uncertain: the asker sees a status line, the owner a Needs-you item).
- **The window spans that turn.** The daemon sends `hub_question_input` (with the share's opt-out, carried in the delivery meta) just before the write and `hub_question_turn_ended` at the idle edge after real work — a compaction spinner is not its end — or before the next write. It keeps the turn on disk, so a daemon restarted mid-turn takes it up again (deliveries keep waiting; its first idle edge ends it). On every fleet connection it re-tells the current turn (`hub_question_turn_state`), which makes good a signal lost to a stale connection or a restart. The Fleet accepts these only from the instance's current daemon connection. A ClassicBot room uses the same signals.
- **Settling outside the turn.** A settled question lifts its window at once only when its own answer turn is not running (a lost turn end, a window left from before a restart): a representative question held or released, a room ask answered or acked. Inside the running turn, a hold, an expiry, a revoke or an accepted answer lifts nothing; the turn's end does. A held room ask still takes a late answer, so it is not settled; a lost end of its turn is made good by the daemon's re-told state, else the cap.
- **Fail closed.** A window that cannot be saved still holds in memory. With no member service attached, a window holds until its turn ends or the cap.
- **Backends.** The working edge comes from the instance state machine for every backend. Claude and Codex also need transcript activity for a turn's end; Grok, Kiro, Muse and others end on the idle edge after working. A backend whose pane never shows working keeps the window until the next write or the cap.
- **30 minutes is only a safety cap.** The refusal inside the turn names the question and says contact works again from the next turn. A labelled pass-through inside the turn is M-3661.
