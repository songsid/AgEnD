# Hub connector for a person's own app — phase 4c (M-3240)

The Hub serves the remote MCP door directly at its HTTPS `/mcp` address. A colleague adds an address to their existing Claude Code or Codex MCP configuration; they install no AgEnD command, proxy or package. Company sign-in and consent happen on the Hub, and the app receives a credential for this Hub's person-facing tools only.

This implements [connector §7 row 3 / §10 4c](https://github.com/songsid/AgEnD/blob/9cf2a9edc/docs/design/agend-connector.md) and [Hub MCP step 1](https://github.com/songsid/AgEnD/blob/docs/hub-ux-review-m2902/docs/design/hub-mcp-agent.md). It builds on 4a's fixed, locally described MCP catalog and readable call-time refusals. The local `agend connect` owner socket and its four tools remain separate: a company token is never a Fleet socket credential, member credential, browser cookie, human approval receipt or administrative credential.

## Delivery slices

1. **Authentication foundation:** SQLite app grants, public-client registration, S256 authorization-code binding, consent selection, token rotation, fresh company-person/policy checks, disconnect and audit. This first PR exports the service and migration only. It mounts no endpoint, registers no production migration and offers no feature or setup button yet.
2. **Person-facing Hub door:** HTTP OAuth discovery/endpoints and Streamable HTTP MCP; the eight specified tools, existing person room/grant services, explicit app attribution, default-off administrator policy and default-on room permission. One mount owns the existing Core/room instances; it does not re-enter the browser HTTP API or Fleet tool dispatcher.
3. **Pages and acceptance:** My AI apps, consent and install prompts, administrator/room switches in EN and zh-TW, and one isolated headless real Claude Code/Codex journey with a test authority trusted only inside that rig. No live Hub, user desktop or trust override.

The Hub's own assistant conversation and Hub General are outside this door. It supplies no inbox/stand-in agent, administrative operation, change to sharing or room membership, file content, or `@all`.

Step 1 deliberately limits `hub_room_*` to shared rooms. Direct agents use `hub_agent_list` and `hub_ask`/`hub_ask_result`, with result IDs private to that app. Browser and other-app one-to-one history never appear in the app's room list or reads. This limit was confirmed by the Leader during implementation; it does not wait on the undecided Hub General work.

## Authentication foundation

`HubMcpAuth` owns opaque pending requests, single-use authorization codes, app grants, and separate hashed access/refresh tokens. The HTTP layer will advertise the [MCP authorization discovery flow](https://modelcontextprotocol.io/specification/2025-11-25/basic/authorization), public dynamic registration and S256; no client secret is copied into a prompt. HTTP token/discovery handling does not use a web session as a bearer token.

Registration accepts bounded app display metadata, never a claimed person. It accepts HTTPS callbacks and native-app HTTP loopback callbacks. Authorization checks the registered callback; only a loopback port may vary. The exact selected callback, client, S256 challenge and canonical `<webOrigin>/mcp` resource are retained through code exchange. State is returned unchanged. Pending requests live ten minutes; codes live one minute. Neither callback validation nor registration fetches a client URL.

The browser supplies the person through an existing, current company session. Consent may narrow the requested `rooms:read`, `rooms:post` and `agents:ask` scopes. The surrounding browser route must apply the existing same-origin and CSRF checks before approve/cancel/disconnect. Browser-only service methods also require a real active browser-session row and refuse `mcp:` actor sessions. App contexts retain the directory actor shape only for existing person room/grant services: `kind: directory` alone is not browser authority. A local-host repair session is not a company person. Client names are unverified display labels, not proof of an app vendor or administrator.

Each grant is bound to the immutable company person, this Hub resource and directory epoch. Its token context rechecks company eligibility and the live administrator policy, and fences app disconnect, policy changes, scope reductions, epoch changes and shutdown across awaits. `requireAdmin()` always refuses, even for a person who administers the Hub. Calls still use each existing service's person/room/grant checks; this context does not bypass them.

Access tokens last one hour. Refresh rotates a single retained refresh token and cannot widen the consent. A connection ends after exactly 30 days without use or when disconnected. The first authoritative account/policy denial for a person atomically ends **all** of that person's app grants, including unused ones; reconnecting an app after eligibility returns requires fresh consent. The policy lifecycle port `revokePolicyGrants({kind:"all"}, "feature-disabled")` must run inside the administrator's disable transaction, so even unused connections stay ended after a later re-enable. It takes an explicit all/person selector; it is not a request dispatcher or tool. Temporary directory failure, stale in-flight checks and missing policy wiring refuse use without permanently ending grants. Logging out of the browser is independent of disconnecting the app. Limits bound public registrations, pending requests, active grants and live tokens; HTTP admission/rate bounds are added with the mounted door.

Connect, consent scopes, disconnect and automatic end are audited in the same transaction as the state change. Audit records contain no bearer/code/verifier, room text or question text. Audit failure rolls back consent. Existing current policy and identity fences protect the effect after any directory await; every token is checked again when an MCP tool runs.

## Product rules carried into the mounted slices

The three step-1 consent ticks start on. The administrator enables apps for joined people or selected AD groups, teams or people through the common picker. A room manager can disable app reads/posts while its room remains visible with the reason. Room reads return at most 50 messages, with member-join audience floors and quoted-data framing. Room posts display the actual person **via the consented app**, preserve person targeting of personal agents, and never manufacture a human receipt or Fleet on-behalf operation. Limit posts to five per person per minute and direct asks to thirty per hour. An ask returns its result within thirty seconds or a durable id for `hub_ask_result`.

## HTTP and person-tool slice

`HubMcpDoor` is mounted on the existing Hub web listener, using the same mount-local Core, sessions, catalog, shared rooms and direct-question services. It registers the two connector migrations once. This slice remains a draft until the third slice supplies the actual consent and setup pages: no browser feature or installation button is advertised yet, and app policy starts off. It does not mount a second Hub, expose a Fleet socket or add a member capability.

The canonical resource is the configured HTTPS `<webOrigin>/mcp`, never a request Host header. Protected-resource discovery is at `/.well-known/oauth-protected-resource/mcp` (also the root discovery path); authorization-server discovery is `/.well-known/oauth-authorization-server`. Public-client registration, authorization, form-encoded token exchange and revocation are under `/mcp/oauth/`. Authorization redirects to the same Hub's company sign-in/consent page with only an opaque pending-request ID. The stateless Streamable HTTP door accepts bearer-authenticated POSTs with JSON responses; browser cookies cannot authenticate it. The browser consent, app list/disconnect and administrator/room policy APIs instead require the current Hub browser session, with same-origin and CSRF on writes. MCP actors never authorize those APIs.

The static catalog is exactly `hub_room_list`, `hub_room_members`, `hub_room_read`, `hub_room_post`, `hub_agent_list`, `hub_ask`, `hub_ask_result` and `hub_people_search`. It reuses 4a's SDK catalog/handler shell, retaining 4a's original four tools and dispatch semantics. Every call validates the token, its consent scope, fresh company eligibility and the live policy before using existing room/grant authority. Tools have no actor, administrator, client name, exposure revision or credential arguments. The app label is frozen from the consented registration as unverified display metadata; it cannot select the person.

Policy starts disabled, with everyone eligible only after an administrator enables it. Selected AD groups, teams and people form a union. Team membership and directory facts remain live and image-fenced across awaits. An administrator change that can narrow access ends **all** current app grants in the same transaction, including unused apps: turning enabled off, changing everyone-on to selected subjects, or removing a subject while everyone is off. Removing then restoring an allowed subject cannot silently restore a connection; fresh consent is required after that narrowing. Pure widenings preserve grants: enabling access, adding subjects, switching everyone on (even while clearing the now-unused subject list), and subject label/order edits. The narrowing sweep is conservative and Hub-wide rather than a directory-backed per-person impact calculation. A room's app switch defaults on; turning it off fences reads and posts across awaits while preserving its disabled list entry and ordinary browser use.

Shared posts keep the existing person author and an explicit frozen `via` app label in the same post transaction. Agent questions use the real person's membership, grants and consented app label; no synthetic Fleet receipt is created. The browser projection and owner activity view retain attribution. App question/post audit events deliberately omit content references, and reads produce no content audit, following the step-1 privacy rule to audit connection/lifecycle actions rather than content read or posted. This creates an intentional difference from existing browser posts: the app event has no direct audit-to-content pointer. It retains actor, room/message IDs and outcome for investigation; the normal room/question store retains content under its existing retention and access rules, so correlation uses that store's IDs instead. Browser auditing and retention are unchanged. Connect, consent scopes, settings, disconnect and automatic end remain audited.

New posts and direct asks reserve an immutable intent under `(app, operationId)` before handoff. The operation UUID maps to a separate deterministic UUID for the existing service's dedupe path. Identical retries, including after a mount restart or an accepted result is lost, reuse the original delivery and quota slot. A changed body or target conflicts. A result is visible only through its original app grant and current agent grant. A refused or uncertain result never instructs an app to start another operation automatically. New asks immediately return a durable still-working ID; `hub_ask_result` returns only that question's answer/status, not the surrounding browser or another app's history.

Post and ask budgets are persisted per person across apps: five posts per minute and thirty questions per hour. People search uses the existing bounded directory admission with display/sign-in names only, at most twenty results and thirty searches per person per minute. After the third post-rate refusal in a room/minute, one quiet system line is stored and emitted, with no agent question. Reads are limited to fifty visible messages, support exclusive before/since anchors and retain join/audience floors. File projections contain names only, without file handles, download URLs or contents. No tool can mention `@all`, call the Hub assistant/General, change membership, share an agent or change settings.

HTTP bodies are capped at 128 KiB and five seconds, with duplicate OAuth fields refused. Public OAuth admission is bounded; authenticated work has global and per-app concurrent-request caps and a thirty-second response deadline. Owned transports close with their HTTP mount, and request-lifetime/current policy fences remain in force before effects. No CORS, self-signed trust exception, bearer redirect or local proxy is introduced.

## Evidence and rollback

Foundation tests use owned SQLite, existing Hub session contexts and an inert company directory. Their initial fail-first check was a compiling conservative service scaffold refusing registration, not a failure on a released binary. The second slice adds actual mounted HTTP plus SDK-client controls on owned loopback listeners, exercising the existing agent-answer lease path. Neither stage claims real CLI, trusted-certificate, browser-consent, live Hub/AD/Fleet or packaged-install acceptance; those remain the third slice.

Before production registration this foundation can be removed with no deployment or schema effect. Once composed, rollback first disables the app feature and fences active grants, then keeps its schema and compatible token refusal behavior. Older binaries must not silently accept app credentials or treat them as web cookies. The person removes an MCP entry from their own app; AgEnD does not edit personal app configuration automatically.
