# Directory security notice history and acknowledgements

M-2687 / S-112 / [#3425](https://github.com/songsid/AgEnD/issues/3425). The directory decision already queues a full redacted notice and the **pre-change** host/admin recipient snapshot in its owning SQLite transaction. This slice supplies its private reader and acknowledgement service. It is not mounted on HTTP, connected to Needs-you, or shown in the UI yet; the public AD Save route remains absent. It adds no migration or second settings writer.

Each recipient has an independent durable target. Reading a page never changes `queued` to `delivered`. Only an explicit acknowledgement of that exact owned notice does so. Here `delivered` means acknowledged, not a successful socket write or insertion into a transient feed. Another session of the same immutable person sees the acknowledgement; acknowledging the host target does not acknowledge any person target. An idempotent repeat produces no second acknowledgement audit.

History uses descending SQLite insertion order, with a validated, owned notice UUID as the older-page anchor. The default page is 50, the maximum is 100, and one additional row determines whether another page exists. An optional unread filter keeps acknowledged history available. Exact-ID acknowledgement is independent of the current page. Nothing evicts unread or acknowledged rows in this service. A future retention policy must preserve unread targets and expose the retained history; it cannot silently replace this queue with a bounded transient web feed.

The notice and its operation are parsed with the same closed schemas. Their kind, actor, time, change categories and original recipients must agree. A matching target row alone cannot grant access to a notice whose original recipient snapshot excludes that target. The public projection omits recipient lists, issuing browser session/request IDs, file images, secret references and directory values. Its phase remains `applying`: this reader does not infer a successful mount from a notice. Original and forward-compensation notices coexist.

Person reads and acknowledgements use the current Hub request context's fresh eligible PersonKey and directory actor, followed by its synchronous session fence. They require neither operational group permissions nor current administrator status: an original recipient must still be able to see a security notice after a policy change. No lookup through the candidate directory retargets old rows. The host adapter takes a fixed, server-configured sink and a private current-owner proof; the eventual fleet route must prove `hostSessionHere`/D3 and CSRF for acknowledgement. A request body cannot choose a recipient or assert host authority.

Each page disclosure and first acknowledgement requires synchronous audit in the same root IMMEDIATE transaction. Nested transactions and thenable audit results are refused. After the audit and authority callbacks, the service compares the current authority stamp and every selected notice/target image again. A late revocation, retargeting, operation mutation, missing target or changed policy rolls back the acknowledgement and audit. Permanent close also fences eligibility continuations that were already awaiting. Reads can be composed with the validated cold recovery database for the host when a replacement mount fails; this slice does not yet wire that adapter.

Evidence uses owned private WAL/FULL SQLite, the real directory decision, version floor and audit chain, plus inert authority contexts. It covers history beyond 100 notices, exact older ACK, independent recipients, compensation, close/reopen, input snapshots and audit-time invalidation. It claims no public route, browser, real directory/account, native manager, pilot or live-fleet operation. The remaining integration includes host Needs-you and Hub notice presentation, their authenticated HTTP adapters, final AD Save wiring and startup recovery intent.
