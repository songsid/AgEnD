# Preparation-aware directory controller and sign-in attestation

This private adapter slice preserves the server's opaque directory preparation or effect witness when the settings controller and proof engine ask the actual HubSessions helper for the administrator's recent sign-in. Previously the controller refused a preparation and both adapters discarded its authority before the helper, so a second administrator could not use the attestation already recorded by their own trusted sign-in.

The packet contains exactly one opaque handle and a frozen narrow source binding: the mounted directory identity, copied configured root, source image, epoch and optional exact SQL decision getter. It copies no configuration, service password, group snapshot or filesystem reference. It is an internal argument to the session helper, never a request/response DTO or a new authority source. The helper still validates the actual Core, session, actor, directory and source; the proof engine still exchanges preparation for a fresh effect witness before the writer.

Only preparation boundaries admit the longer operation identity. An ordinary effect witness retains its original five-second lifetime. A preparation cannot create or renew the five-minute sign-in attestation. Missing or old attestations require reauthentication; a valid recent sign-in still needs fresh eligibility in the old directory, followed by the existing candidate checks for both the actor and configured root. Personal credentials retain only their trusted old-directory destination. Source, session, time, lifetime and decision changes after callbacks withhold disclosure or effects; a retired preparation cannot revive when an old image returns.

The bare configured-root and host-owner/D3 paths remain. A D3 read does not acquire a browser session. Bare auxiliary actors, forged handles and simultaneous preparation/effect handles refuse. The shared physical directory slot is held through cancellation until the owned probe actually settles, and controller close drains it.

Tests use the actual canonical policy, SQL cutover and clock, Core, HubSessions and shared pool in owned in-memory SQLite, with fictional directory answers, an inert TLS probe and inert writer effects. The Save-path forwarding negative stops at fresh old-directory ineligibility before any candidate, writer or response capture. It does not demonstrate a mounted auxiliary Save, physical install, successor cookie, real LDAP or crash recovery.

No HTTP adapter produces preparations here, no startup cutover is registered, and no token is released through an old-generation response. Mounted Save and asynchronous new-generation successor authorization remain subsequent S-129 work. No UI/assets/protocol/config change or new PNG/SKEW claim. Parent-first plain alpha sync, resolution review and exact-head CI remain required. Before activation rollback is a code revert; after activation never restore an old policy/database or independent floor.
