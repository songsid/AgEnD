# M-3535 — platform-specific host monitoring

M-3534's critical-only option shipped first. This implementation starts from its actual merged dev tip in one standalone Dev-only PR. The split changes monitoring interpretation and defaults, not spawn admission or operating-system tuning. The design was approved before implementation.

## Boundaries

Replace the branched `host-monitoring-platform.ts` implementation with thin platform selection and separate `host-monitoring/darwin/{collector,interpretation,defaults}.ts`, `host-monitoring/linux/{collector,interpretation,defaults}.ts`, and `host-monitoring/wsl/{collector,interpretation,defaults}.ts`. Platform implementations do not import one another's parsers, pressure thresholds or help text. They emit the common snapshot shape; the existing scheduler, physical-stop ownership, history worker, confirmation/auth and durable alert state machine remain outside platform semantics. Common transport/command safety is infrastructure, not shared OS interpretation. Keep opaque resource identities stable so saved disk rules still address the same resource.

**macOS:** use the cached kernel pressure alarm as the alert signal, mapping recognized Normal/Elevated/Critical values directly; never derive an alarm from free RAM, swap occupancy or the admission sampler's synthetic recovery elevation. Existing bounded `DarwinMemoryProbe` readings provide diagnostics; expose compression and allocated/used swap as distinct optional data, without presenting a fixed swap capacity or Linux MemAvailable. Compression and swap help explain the reading, not independently trigger alerts. Apple's Activity Monitor describes pressure using several factors and identifies compressed memory and swap separately: [memory usage](https://support.apple.com/en-euro/guide/activity-monitor/-actmntr1004/mac).

APFS interpretation groups shared-container capacity and available space, rather than adding each volume's apparent free space. Show one shared pool with its relevant roles; retain unavailable states when container identity is uncertain. Apple's [APFS volume guide](https://support.apple.com/en-ie/guide/disk-utility/dskua9e6a110/mac) confirms that volumes in one container share its free space. Existing df/diskutil/mount discovery budgets and identity bindings remain bounded.

**Linux:** interpret MemAvailable (explicitly label a MemFree fallback), PSI some/full when supplied, and swap as Linux signals. Move the existing monitoring pressure policy into the Linux interpreter with unchanged numeric thresholds. Missing PSI is unavailable with the documented RAM/swap fallback, not zero stalls. [Kernel PSI](https://docs.kernel.org/accounting/psi.html) measures stalls; [proc documentation](https://docs.kernel.org/filesystems/proc.html) defines MemAvailable as an estimate of memory available without swapping.

**WSL:** owns its Linux-kernel interpretation plus separate Windows-backing-drive discovery and display. WSL memory/swap are the WSL environment's figures; they are not Windows host totals. Preserve the cached bounded registry/UNC discovery, explicit rollback-safe drive sidecar, local-drive checks and root/state/backing-drive identities. Do not import macOS storage or pressure semantics.

Low-level existing platform readers may be relocated with compatibility imports for `MemoryPressure`; its spawn-admission decisions, recovery timers and backoff remain unchanged. Monitoring consumes raw cached platform signals, not admission-only state. No second native memory sampler is introduced.

Implementation boundary: the existing Linux admission sampler remains the compatibility source of its pressure policy, including its unchanged numeric thresholds and PSI/RAM/swap fallback. Linux and WSL each own the monitoring projection and exclude the admission-only synthetic `recovery` elevation. macOS maps the raw cached kernel alarm independently. `memory-pressure.ts` is unchanged; extracting its stateful admission machinery would expand this card. Optional compression counters are parsed from the already collected `vm_stat` response. Shared transport owns command safety and physical closure only. UI help modules are separate flat files because the dashboard serves its module directory without nested module routes.

## Defaults and saved rules

Each platform owns its complete default table. Initially only memory alert eligibility differs: macOS `criticalOnly:true`; Linux/WSL `criticalOnly:false`. Critical dwell and Normal recovery retain M-3534's tested semantics. Other current thresholds are copied unchanged into the appropriate tables rather than retuned without a request.

Precedence is explicit: a saved memory rule with `criticalOnly` keeps that boolean; a legacy saved memory rule without the new member keeps its former Elevated-warning behavior (effective false); only an absent memory rule uses the platform default. Do not rewrite or materialize defaults into the sidecar on startup. A deliberate Restore defaults removes the override and adopts that platform's table. Schema defaults and Settings checked state must use this same resolver; the confirmed-save fingerprint remains bound to the actual saved preferences. A newly effective critical-only default uses M-3534's durable warning-retirement path.

Labels never imply that the three memory meanings are interchangeable. Add optional diagnostic snapshot fields with null/unavailable handling; preserve existing history series identities and label their platform meaning rather than silently reinterpreting old samples.

Keep Off inert, 30 s host/60 s disk cadence, command/output/deadline limits, cached handlers, one physical flight and bounded history. No recursive scan, account/model call or new long measurement is required by this refactor alone.
