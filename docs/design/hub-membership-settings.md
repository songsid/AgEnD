# Owner Settings for Hub membership

On the fleet's own dashboard, open **Settings → Hub**. The switch is available while membership is off. It changes only the boolean `hub_member.enabled`; enabling still requires the existing local-owner Settings confirmation. Pairing a Hub and sharing a representative agent remain separate owner choices. Neither a Hub account nor an agent can supply this local approval. Public-link pages show no control and both the confirmation gateway and route refuse their requests.

Off remains the default. Turning the switch off uses the existing immediate narrowing continuation and runtime switch observer: new work and later answer disclosure stop, while input already delivered to an agent's shared conversation remains there. Pairing/exposure records, working folders, tools and credentials are not edited by this switch. Re-enabling does not publish an agent or manufacture new consent.

The endpoint reads the raw switch because resolved fleet configuration does not contain Hub sections. Confirmation classifies a captured bounded `fleet.yaml` snapshot, so an old cached on value cannot bypass approval after a manual file edit turned it off. Existing Settings fingerprints reject a changed file or revoked owner before execution. A save applies just the enabled leaf through the lossless atomic configuration writer and the existing Hub observer. Invalid/unknown state is unavailable, never implicit consent.

The single **Hub connection** card reuses the company-account handoff, exact pairing controls, shared Settings confirmation card and Agent share selector. Company sign-in is the main entry; the existing membership switch and pairing-code flow are under **Advanced**. A saved profile with an offline transport says **Connecting**, never **Connected**. Sharing is opt-in immediately after connecting. Pause shows the retained Hub summary after reload, removes active member reads, and keeps the profile and Agent selections. Resume uses the same confirmed boolean write. Existing exact revoke stays in **Connection settings** while membership is running; a paused connection must first resume to use that existing API. The saved profile has no Fleet display name, so the summary truthfully identifies it as **This Fleet**.

An explicit owner-only `GET /api/settings/hub/membership?v=2` returns the existing bounded pairing projection with `connectionCardV1`. Its passive file read while off never mounts a runtime, connects a member, writes a profile or returns credentials. The legacy no-query boolean GET remains lazy and unchanged. Session and mounted-config/path/membership checks fence the response after the read; the raw config getter returns copies, so object identity of those copies is not a currency proof.

The lazy wrapper owns EN/zh-TW strings and checks the server projection and embedded-module marks. An earlier server or cached membership/company/manual component keeps the complete earlier UI. A missing or malformed current projection shows a retry state rather than inventing an unconnected Fleet. Cached section modules still use their existing controls. Public-link pages offer no private control. No confirmation, grant, consent or pairing-proof rules change.

Acceptance uses scratch configuration, the actual Settings gateway/confirmation/replay/save path with inert runtime/notification adapters, plus renderer and real-browser cache cases. No live fleet, real account, directory, host service or pilot is used. The format remains one existing boolean; rollback removes the UI/route and leaves the saved value usable by existing configuration and runtime handling.
