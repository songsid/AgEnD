# Hub roles: unmounted cutover and mode effects (M-3010 / S-128)

This prepares Appendix A of the accepted roles design at `9e000625658d55c6d8f522cfbae2a01448a9cc37`, following #3767, #3772 and #3777. Nothing registers these migrations, invokes the cutover, changes a route, schedules a timer, advertises a feature or imports a new browser asset. Production still uses the group policy. S-129 must convert all readers and live operation permits before invoking this helper. The current strict group readers cannot consume its output.

## Atomic cutover

`createHubRoleCutover` is a synchronous, server-owned startup boundary. Its caller supplies the complete existing migration registry, the actual transport store, Hub identity/directory generation/root, and the current mount fence. It refuses an ambient transaction, re-entry, foreign Hub ownership, incomplete or unknown schemas, missing authority tables and incompatible prior role state. Migration callbacks and transport methods are captured. There is a 20-second monotonic acceptance deadline, wall-clock rollback protection, and a persisted cutover timestamp checked on replay. No timeout pretends to cancel a physical directory operation: this helper performs none.

One immediate transaction installs the role auxiliary schemas, converts the exact old group document, stores a cutover marker, appends required audit, records the configured root's acknowledgeable notice, and advances the existing transport authorization epoch once. Conversion sets `rolesActive=true` while preserving revision, the three-way self-use state, the derived ever-enabled latch, denies, all eight old permission combinations, and every exact per-assignment Fleet limit including zero. It creates no implicit root self-use assignment. The marker retains the exact old serialized policy, conversion and inventory digests, original binding, transport revision, authorization epoch and audit identity. It has no audit-retention foreign key.

The actual transport store owns the durable floor and hash-chained audit write. The migration event is `role.migrated`, actor `local-host`; its audit policy version is the new authorization epoch and component sequence is the new transport revision. The retained old policy revision is explicit in the marker and notice metadata. The notice event has `kind: roles-available` and `accessChanged:false`; it contains metadata and digests, never a credential or conversation body. The existing role writer proves the root's current eligible session when reading or acknowledging it.

Before publication, the helper re-proves the exact policy, marker, audit image, event/recipient, schema, mount/time, and ordinary authority inventory. It checks again after the transport callback returns. A thenable audit/refresh is refused. SQL failures roll back the auxiliary schemas, marker, policy and notice together. Authorization refresh happens only after commit. A refresh failure reports unavailable while retaining the committed result; retry republishes without repeating the migration, epoch or notice. An audit purge may remove the original notice event but cannot remove the marker or re-announce the migration. Later legitimate directory bindings and policy revisions are not forced back to the original marker's image.

## Retained authority and delivery

`captureRoleCutoverInventory` returns only keyed table counts and digests, not row contents. Its fixed version-one set covers transport Fleet/pairing state; resource lifecycle rows and event provenance; exposures, grants, rooms, catalog cursor, quota preferences and auditor assignments; company-join control, pending/issued requests, invitation and nonce records; enrolment-code definitions, HMAC key identity and use receipts; pairing notices and recipient targets. It includes every current column, including future additive grant columns, ordered by actual primary key. Only transport revision and authorization epoch are excluded from its ordinary image. Missing/unkeyed tables refuse, rows are bounded, and the current/deadline fence is checked while scanning. New authority tables require an explicit inventory-version review.

Identity-preserving migration writes none of these rows. In particular, it does not rename a resource's `manual`, `group` or `code` source, rewrite its approver, change a suspended lifecycle, reset code uses, rotate a receipt key, or canonicalize retained raw join/provenance bodies. Issued delivery binds those exact bytes through authenticated encryption. Tests exercise actual code consumption, invitation signatures, request storage, receipt sealing/opening and original deadlines; they retain negative controls for a different provenance digest and a new use after code revocation. Full mounted redeem/ACK and fresh issuer-permission enforcement remain S-129 integration acceptance, not an assertion about the unchanged strict group readers.

## Forward-only roles off/on

`createHubRoleModeEffects` is an identity-only adapter for the existing role writer. It accepts only the rolesActive control on the current document and refuses other document edits. It preserves the self-use state/latch, current assignments/denies/limits and all inventoried ordinary resources. The writer still owns preview, fresh authority, exact CAS, audit, notices and epoch; the adapter cannot authorize a request. Re-enabling reads the current document, so an assignment removed while roles are off is not restored from the migration snapshot. Expiry and fresh membership remain evaluator/live-permit obligations. Generic role edits and expiry narrowing require their own real resource adapter and are deliberately not supported by this mode adapter.

## Crash behavior and activation boundary

The existing independent transport floor is raised durably before SQL commit. The tests kill an owned Node child with SIGKILL at four real file/WAL boundaries for both migration and roles disable:

- Before floor raise: old SQL and the old floor remain readable.
- After floor raise, and after required audit but before commit: SQL rolls back; the raised floor remains. A fresh store refuses the older SQL image. No floor is lowered or reconstructed.
- After commit, in authorization refresh: role SQL, marker, audit, epoch and one notice are durable. Reopening reports already converted without duplicate work.

A post-floor/pre-commit interruption requires the established held-storage recovery procedure; this preparation does not invent an automatic repair or silently restore old authorization. Old binaries reject the registered role schema components on both normal migration and cold-recovery paths. A restored transport snapshot is refused by the independent floor. Current unmounted code can be reverted without any production database effect. Once activated, rollback must be forward recovery or a coherent separately reviewed backup protocol; deleting markers or restoring the old policy alone is not rollback.
