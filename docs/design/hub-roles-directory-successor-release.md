# Response-owned successor session release

A directory change commits the successor session in SQL before remounting. The old session and its role preparation cannot authorize a cookie in the new directory generation. The existing private successor adapter obtains fresh hub.admin for that exact new session, but an asynchronous caller must also keep that proof current until its originating response publishes the cookie.

This slice adds an opaque, frozen release handle. Acquisition uses the actual new HubSessions/Core and its exact successor token context, existing shared physical directory admission and current named hub.admin permission. The handle contains only assertCurrent, release and discard methods; it reveals no token before release. The ordinary twenty-second acquisition and five-second effect budgets are unchanged.

Both assertCurrent and release re-prove the captured actual Core/provider/method, directory/config/root/UOW, actor/session, policy/version/time and final SQL operation/head/session declaration. SQL checks use the trusted proof scalar after the writer sample. The token hash is retained privately for the final response guard after the one permitted disclosure; release itself is single-use. A second acquisition or immediate shortcut refuses without cancelling the first owner. Abandonment, failed final checks and rotation cancellation retire disclosure permanently, including a SQL-head mismatch followed by restoration of identical rows.

The previous immediate-release adapter delegates to the new preparation and releases immediately. Its existing callers and guards retain their behavior. The legacy configured-root completion remains separate and cannot complete a proof-marked rotation. No authority is inferred from a browser-supplied token, ref, role label or an old preparation.

The new handle is not yet composed into HubDirectoryBrowserSessions, the mounted HTTP projection or the Save coordinator. That next composition must acquire before response.reply, retain the exact new mount and helper identity, release inside the response-owned producer and re-prove in its final current predicate. A withheld cookie does not roll back or retry the already committed directory decision. No startup cutover or actual HTTP preparation producer is enabled here.

Tests use actual in-memory SQL/cutover/clock, Core, HubSessions and the directory read pool with fictional people and directory answers. No HTTP response, physical file install, successful mounted auxiliary Save, real LDAP/account/Fleet/backend CLI/browser/container/native/pilot or crash-recovery claim. There is no UI, asset, protocol or config change and no new PNG/SKEW claim. Parent-first plain alpha sync, resolution review and exact-head CI remain required; full S-129 remains incomplete. Before activation rollback is a scoped code revert; never restore historical policies/databases or independent floors after activation.
