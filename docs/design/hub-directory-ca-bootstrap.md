# Directory CA bootstrap during Hub initialization

`agend hub init` accepts a CA PEM file, system roots (Enter), or `fetch` at the directory CA prompt. Imported and fetched CA certificates show their SHA-256 fingerprints and expiry dates. The operator compares them with a trusted source and explicitly confirms trust. The final sealed initialization confirmation includes the exact `caPem` bytes. This changes initialization only; the running directory client still requires ordinary verified LDAPS.

For `fetch`, a five-second TLS inspection sends no LDAP or credential bytes. It checks the requested hostname and certificate validity, labels the presented leaf as untrusted, and asks the operator to enter its complete SHA-256 fingerprint from a trusted source. Declining or entering another fingerprint cancels without requesting a password.

The subsequent bootstrap connection authenticates that exact confirmed leaf, with hostname verification and `rejectUnauthorized: true`, before any LDAP operation. It uses Node's [`allowPartialTrustChain`](https://nodejs.org/download/release/v22.23.3/docs/api/tls.html#tlscreatesecurecontextoptions) to trust the explicitly confirmed leaf for this one connection. Unsupported runtimes refuse the fetch; importing a CA file remains available. The credential-free inspection's relaxed issuer check and the bootstrap's leaf anchor never enter the Hub configuration.

The initializer first uses a cryptographically matching presented issuer chain. Otherwise it reads only a same-directory LDAP AIA `cACertificate` entry over the already authenticated LDAPS connection: exact base scope, one entry, fixed certificate attributes, no alias dereference, referrals, HTTP fetch, separate AIA host or plaintext LDAP. Anonymous lookup comes first. If the server requires authentication, the existing hidden read-only service password may be used after fingerprint confirmation. There is no reconnect or automatic credential replay. Errors show fixed guidance to import a CA PEM file instead.

Issuer traversal is limited to four certificates, certificates to 64 KiB, LDAP responses to 256 KiB, and each connection/operation has a five-second deadline. Every selected issuer must be a current CA with a matching signature; traversal must reach a self-signed root. Before offering the CA for confirmation, a fresh connection verifies normally against that CA bundle, without leaf pinning or partial-chain trust. An untrusted server or invalid chain refuses this check.

Acceptance uses OpenSSL-generated generic certificates, an owned loopback TLS/LDAP wire fixture, and the real initializer/private files. It covers no credential bytes during inspection or pin failure, exact bounded AIA searches, anonymous and authenticated lookup, certificate replacement, wrong issuers, external AIA/referral refusal, deadlines, ordinary final verification, and EN/zh-TW consent and cancellation. Person sign-in, Hub identity and service installation use inert adapters in wizard tests. No real directory, account, Windows trust store or existing pilot is accessed.

The local operator controls this trust decision. Directory accounts remain sign-in identities; the fetched certificate and directory metadata confer no administrator authority. Existing first-admin sign-in and sealed initialization rules remain in force. Rollback is a code revert: committed `caPem` uses the existing configuration shape and requires no migration. An incomplete initialization resumes its sealed plan rather than fetching a different CA silently.
