# Hub S4b: per-question CLI provider

This is the production-provider follow-up to [S4](hub-restricted-execution.md), on the experimental alpha line. It merges after #3107. The Hub still runs no agents. The member owner chooses exposures, data views and tools; an external question never becomes local human authority ([approved roles](hub.md)). Neither Hub switch is enabled by installing this adapter.

## Boundary

One question gets one disposable Linux container, one fresh home/config/workspace and one Claude Code or Codex process. It never resumes a thread or reads an owner CLI home, repository, account, fleet socket or normal conversation. The image is installed separately and selected by its immutable content digest, with reviewed runner and CLI versions. The adapter refuses missing/mismatched images and unavailable isolation. There is no host-process fallback or image pull during a question.

The container runs as a non-root UID, with a read-only root, a bounded private tmpfs for scratch data, all capabilities dropped, no-new-privileges, bounded memory/processes/CPU, no published ports, no devices or host mounts, and Docker network mode `none`. The member checks the actual container configuration before starting it. The Docker socket is never mounted. This first implementation supports a local Linux Docker engine with an amd64 image; other platforms remain unavailable unless they provide and prove that boundary.

CLI switches remove native tools and integrations where supported, but switches and prompts alone are insufficient. The container has only a loopback model endpoint and a two-tool MCP connector. Its controller forwards bounded requests over its attached stdin/stdout to the member. The member owns the only document gateway and the only model-API credential. No credential enters the container. The model broker has fixed HTTPS API destinations, methods, paths and a locally chosen model; it accepts no arbitrary URL, redirect, remote MCP or server-side browsing tool.

Before forwarding model requests, the broker reduces the tool catalog to the two exact document tools. Before returning any model response to the CLI, it buffers and validates the complete bounded response, refusing native/custom/unknown tool calls. Streaming cannot dispatch an unchecked prefix. SSE permits LF or CRLF; lone CR is refused before any original bytes can be forwarded, so downstream line-ending rules cannot hide an event from validation. Document calls are translated to `documents.list`/`documents.read`, validated again, and enter S4's existing current-policy/exact-operation lease gate. An unsolicited shell/write/network call cannot reach a CLI dispatcher. Its exact action/arguments can become an owner-local Needs-you proposal; that does not authorize execution. No generic tool, filesystem path, SQL, network client, code mode or child-agent interface is offered.

An adapter opens only after observing its exact question and external-identity label in the CLI's first model request. That request waits until S4 supplies the scoped gateway; spawning a process or writing a pipe does not count as consumed input. Failures remain uncertain and are never retried. Each session has fixed wall-time, API/tool-count, wire-byte and answer-byte limits. Abort, completion and errors fence broker dispatch immediately, then remove the owned container and wait for teardown. A failed cleanup poisons admission and withholds the answer. The provider retains ownership and its physical reservation until removal and process exit are confirmed. A later close can retry cleanup of the same owned container; a successful exact-ID absence check reconciles a lost removal response. Cleanup retry never retries question input or restores admission. No history survives teardown. If the controller dies abruptly, the independent runner exits and its private tmpfs disappears; stopped container metadata may remain for operator cleanup. Normal completion removes that metadata before disclosure. The local Docker engine and the explicitly reviewed immutable image are trusted; a label alone is not an image review.

Container preparation can outlast a five-second begin lease. The provider therefore calls S4's mandatory one-use `beforeInput()` callback after setup, immediately before sending question input. S4 checks the captured exact begin lease and current ownership again there; missing, repeated, revoked or expired checks hold the context without recording consumption. This member-owned callback never enters the container. It does not mint or refresh an operation and changes no S1 signature.

Final model text uses a validated JSON response with an answer and an optional exact action/arguments/consequences proposal. The proposal is passed to S4's owner-local Needs-you writer before returning the answer, without adding an execution tool. Output instructions request that format; the parser and gateway enforce it. Malformed output is held. A rejected native tool call also creates an exact local proposal when its arguments are available; neither path can approve or execute it.

## Integration and acceptance

The explicit factory returns the existing `HubIsolatedProvider`; its result can be installed in the member's trusted provider map only after local image/model configuration and availability checks. Imports, Hub frames and exposure policy cannot install a provider. No changes to S1 leases, outbox or signed identities are needed. S4 remains responsible for begin/tool/answer authorization, durable replay prevention and answer disclosure. The provider must close its container before returning its answer, so teardown failure prevents disclosure.

Acceptance uses actual pinned Claude Code and Codex executables with scripted mock model APIs and fake credentials in isolated containers. It proves the positive document-read/answer path and rejection of forced shell, writes, filesystem/home reads, arbitrary URLs, unknown MCP/tools, forged receipts and another question's state. It inspects model-facing catalogs and container settings, tests prompt injection in documents, overlapping questions and owner CLI idle/busy/resumed independence, input consumption, abort during open/API/tool work, bounded output/time, process death and teardown. It also runs through the real S4 gateway to prove exact authorization still surrounds reads and answer release. Focused tests and compiling semantic reversals cover each enforceable boundary; no real model account, live fleet or host network change is involved.

The acceptance rig reuses the local mock API patterns from `scripts/manual/web-only-e2e`. Build-time dependency downloads are separate from runtime; test containers have no external network. CLI version changes require renewed real-CLI acceptance before changing the reviewed image. Rollback withdraws exposures and removes the provider registration; S4's durable journals/floors and unresolved holds are preserved.

CLI restriction controls are documented in the [Claude CLI reference](https://code.claude.com/docs/en/cli-reference) (`--restricted`, `--tools`, strict MCP and session persistence) and [Codex configuration reference](https://learn.chatgpt.com/docs/config-file/config-reference) (shell/image/multi-agent/app features). The exact pinned binaries and adversarial runtime evidence determine support; these references alone do not prove isolation.

## Local setup guidance

Provider setup failures carry only a bounded member-local reason: `engine-unavailable`, `engine-unsupported`, `image-unconfigured`, `image-mismatch`, `credential-unconfigured`, or the generic `unavailable`. The existing protocol error code stays closed; no exception text, credential, socket path or Docker output is sent to the owner page. Unknown reasons use the existing unavailable message.

The owner sees an action in English or zh-TW under an unavailable exposure and in the member's Needs-you item. The actions are to start/check the configured local Docker engine/socket; use the required Linux/amd64 engine; select a reviewed local immutable image matching this provider; or configure the member's private model API credential reference. Configuration is still reviewed locally and reloaded through the existing path. Diagnostics neither install a provider nor grant consent, readiness, local approval or a tool capability. Unpublished rows also consult provider availability; publication still checks the exact candidate policy.

S5 owns the startup diagnostic and its Needs-you projection; S4 owns the bounded reasons and localized copy; S3c passes the diagnostic to the exposure projection. An omitted diagnostic retains the generic failure. The default registry remains empty. These messages add no automatic runtime installation, image pull, credential import, platform fallback or CLI-version update.

`scripts/manual/hub-provider/setup-guidance.mts` exercises the actual owner/public HTTP handlers and lazy browser renderers with inert setup metadata, including a real pre-upgrade dictionary. `setup-preflight.mts` checks the real Docker factory without creating a question container or sending a model request. Neither script qualifies a new platform, model account or login method.
