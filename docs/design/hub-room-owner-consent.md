# Owner consent for agents in Hub rooms

C owns `createHubRoomInvitations(core, host): HubRoomInvitations` and `HUB_ROOM_INVITATIONS_MIGRATION` (`s3-room-invitations`, version1). R registers the additive migration before its HTTP mount and injects `roomInvitations: createHubRoomInvitations`; importing the module does neither. The existing R routes and host are unchanged. Absence of this service keeps invitation actions unavailable. Team storage remains a separate slice.

A current room manager selects published agents. Their own agents join directly; another owner's agent gets a pending invitation addressed to that immutable owner. Repeated invites keep the same pending ID and original absolute expiry. An owner sees only their pending invitations, the named room and current people count, the named agent and inviter. Being invited does not make the owner a room person or reveal room history.

Invitations expire seven days after creation; pause never extends that time. Observed expiry is persisted, including when an action then refuses, and cannot revive after clock rollback. Managers can clear an expired entry without deleting its history. A reinvite gets a fresh ID and marks prior expired rows for that same room, exposure and owner cancelled in the new invitation transaction, so only the replacement is listed. Audit failure rolls that replacement back. Closed/expired actions use404 to match the existing UI's gone/reload path. Accept/decline/cancel return `{ok:true}`. Decline and cancel do not change membership. A future-dated pending row is withheld from the owner inbox until its creation time; it does not hide other current invitations, and its actions still refuse before that time.

Acceptance rechecks the exact pending row, owner, active room and current published exposure, then calls the R host's addAgentMember and consumes the invitation in the same `core.atomic` transaction. Audit failure, session retirement or a changed row rolls back both. Refresh events publish after commit. Replaying an accepted action is idempotent and never re-adds a member later removed. A paused agent cannot newly accept, but its invitation remains pending until expiry; existing room membership survives pause/resume.

The Team input consumes only the optional read/expand port already on Core. It snapshots the selected roster, invites its published agents with individual owner consent, and rechecks the selected versions before commit. It adds no Team storage, Team permissions or implicit directory-group enumeration. Missing Team support refuses rather than inventing an empty Team.

This pilot changes no direct-chat grant, member transport, roles activation or security-review gate. Compatible rollback retains the new table and consent/membership history; older builds must not discard a migration component to open it. The completed room UI/server/feature graph and ordinary review/CI are separate integration prerequisites.
