# Hub browser certificate renewal

The host owner can replace the initialized Hub's browser certificate at Settings → Access and security → Hub browser certificate. Generate prepares a new 30-day self-signed IP/DNS certificate for the sealed web origin; Import reads a certificate chain and matching unencrypted key from private files relative to the AgEnD home. Files and parent directories must be owner-only, without symlinks. Preparation checks the current hostname, validity, key match and TLS chain format. It does not change the listener or trust store.

The card shows the fingerprint, expiry and a self-signed warning before asking for the existing sensitive-Settings confirmation. The confirmation binds the exact prepared material and current certificate revision to the initiating host session. Only its opaque reference and revision are submitted for application. Keys are never returned, placed in the confirmation, or logged. A directory sign-in, agent or public link cannot prepare or apply a replacement. EN and zh-TW copy belongs to the lazy card so cached Settings modules can still load it.

Preparation writes one immutable private material file and synchronizes it and its directories before selection. At most eight preparations are retained per running Hub; they expire after ten minutes on a monotonic clock and are reclaimed on the next preparation or shutdown. Shutdown fences and waits for physical generation before deleting owned, unchanged, unselected material. A cleanup failure retains ownership for retry. Imported source files are never deleted. A process crash may leave private, unselected version directories; they are not selected on recovery and may be inspected and removed by the host owner after stopping the Hub.

The new `s5-browser-tls` database component starts with the sealed initial paths. Later replacements commit the selected material ID, digest and revision with required synchronous audit in one immediate transaction. Current authority and generation are checked again after audit. A stale revision, session mismatch, expired proposal or changed material refuses the save. The revision also incorporates the current material digest, so changing an initial PEM outside Settings invalidates an open proposal. Missing, foreign or corrupt state is refused rather than reset.

After commit the running HTTPS server receives the validated pair using `setSecureContext`; new connections use it. Existing connections can continue with the previous handshake. If activation fails while the active material differs, selection remains saved and Settings reports that a Hub restart is required. Reopening loads only the committed selection with its exact digest. Old selected versions remain private for recovery; renewal does not silently restore an older certificate.

Browser TLS is separate from the member transport. Renewal leaves the initialization seal, issuer key and member pins unchanged. It does not change the origin or listener address. An expired selected certificate can still be inspected and replaced through the host's ordinary Settings dashboard. Browser trust remains the owner's responsibility, and a newly generated self-signed certificate must be trusted separately after checking its fingerprint.

Validation uses private scratch homes, local OpenSSL, SQLite, loopback HTTPS with verification enabled, scripted host-Settings requests and inert browser DTOs. It covers selection/audit rollback, expiry/session/revision fencing, private imports, physical shutdown ownership, persistence, the real HTTPS replacement, member identity preservation and cached-module rendering. There is no native-service, directory-account, system trust-store or pilot deployment claim.

Rollback requires a build that understands the `s5-browser-tls` component and selected-material reader, or a forward fix. Older builds refuse an unknown schema component; do not delete the database or selected material to bypass that protection.
