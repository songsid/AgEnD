# Group-derived resource lifecycle

This internal slice follows [#3298](https://github.com/songsid/AgEnD/issues/3298) and the [foundation](hub-group-policy-foundation.md). It supplies a durable lifecycle ledger and binding inspection for the upcoming action adapter. It does **not** compose a policy into a running Hub, register either migration at server startup, add an HTTP route, or enable the experiment. Sign-in, local consent, explicit owner ask grants and member delivery are unchanged. The complete action adapter, confirmed impact preview, Settings/welcome and quick pairing remain separate work.

## Incomplete membership stays held

The implementation deliberately does not scan group members or follow AD ranges to prove a negative. When the last direct membership disappears, AD may omit `memberOf`; ldapts represents the omission as `[]`. Missing/empty, ranged, over-256, malformed, referred, unsupported and failed results remain unknown. The current protected action is held/denied, with diagnostic audit, while resource and policy records stay unchanged. This can last indefinitely until a complete read is available or the admin makes an explicit change. Recovery from an outage needs no resume because nothing was durably suspended. This also creates a user-visible exception to decision 5: if removing the last direct group produces only unknown facts, the resource was never suspended. Adding the person back lets the next complete positive read allow actions without administrator resume. Every action stays denied while facts are unknown. The explicit-resume rule applies after a confirmed negative actually suspended the record.

A complete result containing other group GUIDs proves absence of a configured group. Current immutable-ID ineligibility and an explicit policy denial also qualify. Such a denial suspends the corresponding **group-derived** lifecycle record. Later positive membership does not resume it automatically: an administrator must explicitly resume the exact resource after a fresh allow. A new sign-in alone does not resume anything. The administrator's authentication and confirmation remain the action adapter's responsibility; the ledger does not grant an administrator role.

The verified loopback LDAP/SQLite smoke exercises allow → omitted/empty/ranged/oversized/outage → unchanged/held → complete negative → suspended → positive/resume-required → explicit resume. These are real TLS/ldapts BER and ledger operations, with fake people; they are not a running-Hub suspension claim.

## Exact provenance and transactions

The ledger identifies a fleet, exposure or asker by its kind, stable local ID, exact resource revision and immutable owner. Its capability is fixed by kind. Capturing a manual fleet/exposure is allowed only before the policy has ever been enabled; askers cannot be grandfathered. A capture covers that exact revision, never a replacement, a new revision or a newly published agent. Manual captures survive group-membership removal and group-resource switch-off suspension. An explicit per-person deny still suspends the exact manual record; removing the deny requires explicit resume while preserving its membership exemption. Normal account/resource revocation remains independently required at each action boundary. Owner grants and fleet credentials are separate records and are not deleted by this library.

Group registration checks fresh membership and audits the allowance. It records provenance only; it creates no fleet, exposure, grant or delivery. Ordinary consent, fingerprint/code proof, grants and enrollment limits remain required. The composed adapter must commit the actual operation with its final revision/current checks, and cannot treat a ledger row as consent or as a cached allow. Every protected action, content read, dispatch and answer release must still perform its current group gate. A smaller positive fleet limit applies to new enrollment; it does not suspend already registered fleets.

Lifecycle changes use immediate SQLite transactions, exact row/policy revision checks and synchronous required audit on the same database. Actor, resource and caller fences are captured before awaits. Audit failure/thenable, reentrant changes or authority loss withhold the result and roll back the lifecycle write. Required append is synchronous; independent repeated checks also fence stale continuations. Explicit switch-off must call `suspendAll` in the **same outer transaction** as the confirmed policy change, so off/on cannot silently resume group-derived resources. This does not mutate transport credentials or manual grants.

## Directory selection and repair

Group lookup tolerates formatting after DN separators and different spelling of the selected RDN's escapes. The immutable-GUID recheck compares the first and second **server-returned** DNs, not the admin's typed text, and stores the server DN. A group moving during selection still refuses. Escaped commas do not become base boundaries. The configured `baseDn` must include both people and selected groups; for example a users-only OU excludes a sibling groups OU. P1 does not widen the base or add a separate groups-base setting. Out-of-base selection is invalid, rather than an outage. Enter the DN as AD displays it: this helper tolerates formatting after commas but does not normalize whitespace before a comma or implement a general LDAP DN parser.

`inspectHubGroupPolicyBinding` is a read-only composition probe. An intact same-Hub/same-realm `never-enabled` record with an old directory generation permits the future adapter to preserve legacy behavior while showing **group policy needs administrator repair**. It must disable group editing/enabling until repaired. A previously enabled/suspended policy, foreign binding, missing or corrupt state never authorizes legacy fallback. Those protected actions refuse with the repair state. The listener, ordinary directory sign-in, own preferences and configured-administrator repair access must stay available. Strict `store.read()` remains strict; the probe does not rewrite or reset anything. The next composition slice must wire and test these outcomes; this slice makes no UI-repair claim.

No UI module or wire format changes here. Acceptance has no browser/SKEW, native-platform, company directory, pilot or live-fleet claim. Rollback before composition is a code revert. Once the later composition registers migrations, an older binary may refuse the newer component set; deployment needs a database backup rather than assuming binary-only rollback.
