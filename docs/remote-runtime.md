# Paired Windows runtimes

繁體中文：[連接電腦與一行安裝](remote-runtime.zh-TW.md)（連接流程與 Windows 一行安裝；其餘章節目前只有英文）。

The default adapter remains per-turn **exec**. For the 2.3.5 alpha line's opt-in persistent Codex/Claude panes, see [Persistent Windows agents](windows-persistent-panes.md) ([繁體中文](windows-persistent-panes.zh-TW.md)). Its disconnect/stop/revocation rules replace the exec-only lifecycle below; ordinary runtime-client exit preserves those resident panes.

This preview lets a native Windows computer connect **outbound** to a central AgEnD coordinator. The computer reports its installed coding CLIs and executes Agents assigned to that machine. Its own CLI login, filesystem, ADB and serial devices stay on that computer. Opening the dashboard from another computer does not provide that browser's local tools.

The coordinator still owns the shared Fleet, Agent settings, task board, delegation, chat and permissions. A runtime owns local processes and a bounded execution journal. An Agent is pinned to its selected machine; a disconnected machine never causes its Agent's prompt to be automatically rerun on another machine.

Design references, source-review scope and bundled license notices are recorded in [Remote Runtime provenance](remote-runtime-provenance.md).

## Runtime version reports

Current runtimes report their own package version, code Build ID, supported protocol versions and transport capabilities when connecting. Open a computer card's **Computer information** menu to inspect them. `agend-runtime --version` prints the same installation's information without connecting or reading its private profile; `status --json` includes it alongside each profile's status.

The code Build ID hashes the installed fixed runtime modules (including the pane helper scripts) and package version. It distinguishes different program builds carrying the same alpha version; it is not a signature or the downloadable ZIP's SHA-256, and excludes user profiles, CLI installations and runtime dependencies. An incomplete program installation has no Build ID. Unreadable package metadata remains unknown instead of using the coordinator's version.

Older runtimes that report nothing keep connecting over protocol v1 and show **This Runtime does not provide version information**. Replace the portable program folder once (or run the [one-line install](#one-line-install-windows-powershell) again) and reconnect the existing profile to enable reporting. Reported capabilities grant no permissions. Reconnecting with an older client clears the prior connection's version report.

### A Runtime that does not match this AgEnD

AgEnD needs a Runtime that speaks a protocol AgEnD speaks (today: protocol 1) and offers the `exec` capability. A Runtime whose report says otherwise was installed from a different AgEnD release, so AgEnD **refuses it clearly instead of letting it connect and fail later**:

- AgEnD does not welcome it and sends it no work. Its computer card in **Settings → Runtime** stays offline and says it is not compatible and that the install command must be run again. The report is kept so you can see which version it is.
- The Runtime's own window stops with a non-zero exit and says: AgEnD refused it because its version is not compatible, **re-run the install command** shown in Settings → Runtime → Connect a computer, then start it again with `agend-runtime run`. The pairing is kept; no new code is needed.
- Running the install command again installs this AgEnD's Runtime **next to** the old one. It never deletes or replaces a version folder, so a Runtime that is running keeps working, and `agend-runtime` is repointed only after the new version is whole (see below). If you installed from the ZIP, download the ZIP from the same page instead.

A Runtime that reports nothing at all (installed before reports existed) is not refused: it is shown as legacy, with a hint to run the install command again. There is no automatic update or remote installation.

## CLI diagnostics on a selected computer

In **Settings → Runtime**, the host's Windows installation and approved paired computers use the same machine cards. Each card shows detected CLIs, versions and sign-ins. Click **CLI diagnostics** on a card to open a dialog fixed to that computer. Paired-computer diagnostics also work when the coordinator has no local Windows CLI support.

Opening the dialog reads saved inventory. **Detect Windows CLIs** explicitly refreshes that computer only. Expand a CLI row for its executable path and reported models. Expand **Test CLI** for the optional one-off task form and results; it starts collapsed until a test is active. Closing the dialog does not cancel submitted work; reopen the same computer to read its task status. Working directories, models and drafts stay separate for each computer. Offline computers show saved inventory with detection and dispatch disabled. Revocation never moves diagnostics to another computer.

Test tasks use the existing per-turn execution protocol and task journal. An unconfirmed acknowledgement remains visible and blocks another task until the Runtime reconciles its outcome; reopening the panel never replays the request.

## First connection

Turn on **Allow other Windows PCs to pair** in **Settings → Runtime** (fleet.yaml `runtimes.remote_runtime: true`; off by default). Turning it on asks a fleet admin to confirm, like other access settings; it applies without a restart. This machine stays your fleet; the other PC runs only the small runner below, never a fleet. Remote Windows agents work even when this machine is a Linux machine without Windows interoperability. **Use this PC's Windows CLIs** (`runtimes.windows_cli`) is the separate switch for this machine's own Windows CLIs.

Turning the switch off fences new work immediately and keeps machine approvals. Persistent panes drain through confirmed owned cleanup; offline or unconfirmed outcomes remain held. **Agents at once on each Windows PC** (`runtimes.max_agents_per_machine`, 1–16, default 4) limits each PC separately. Lowering it blocks new starts without stopping existing agents.

The environment variable `AGEND_REMOTE_RUNTIME` still overrides the setting: `1` forces it on and `0` forces it off (Settings then shows "Set by the environment" and cannot change it). Any other value, or none, leaves it to Settings.

1. On the coordinator, open **Settings → Runtime → Connect a computer**.
2. Review the **AgEnD address** that the other computer can reach. The page starts with the browser's origin; replace localhost with your existing reachable HTTPS origin unless the other computer has a loopback tunnel. This does not configure a proxy or change network access.
3. Choose how the other computer gets the Runtime, in the tabs under the address:
   - **Windows (PowerShell)**: copy the **one-time install command** (it checks the SHA-256 of `install.ps1` shown on the page before running it, and carries a short-lived, single-use token), and paste it into PowerShell on **any** Windows computer, or hand it to an AI agent running there. It installs the Runtime and connects it: no pairing code, no approval step. See [The one-time install command](#the-one-time-install-command-no-pairing-code-any-computer-ai-agents) for what that token is and what it allows. A pairing code is offered under **Manual options**.
   - **Other install methods (ZIP)**: click **Download Windows Runtime (ZIP)**. This authenticated download includes the reviewed public origin in `agend-server.json` and a `connect-agend.bat` launcher. No pairing code, browser token or machine credential is embedded. The address is read as JSON, never interpolated into a batch command. Transfer the ZIP to the Windows computer, extract it, and double-click **connect-agend.bat**.
4. Run it under the Windows user whose CLIs are installed and signed in. A supported Windows Node.js installation is required with either method. The Runtime prints the destination before it connects.
5. With the **one-time install command** nothing is typed and nothing is approved: the computer joins and appears under **Connected computers** with a notice. With the ZIP, or the pairing-code route under **Manual options**, enter the one-time code from Settings on first connection. Compare the **Pairing fingerprint** printed in the Runtime terminal with the fingerprint on the machine card, then approve it in AgEnD (a dialog opens for it, see [Approving a computer that asks to pair](#approving-a-computer-that-asks-to-pair)). The Runtime then moves to the background and the window can be closed (add `--foreground` to keep it in the window). If AgEnD ends the connection (the computer was revoked or is not recognised, another Runtime took over the same pairing, or AgEnD rejected a message), a Runtime in a window stays open with the reason and the next step and its exit code is non-zero; a Runtime in the background writes the reason to its log (`agend-runtime logs`) and ends; stopping with Ctrl+C or `agend-runtime stop` is the only silent end. If it says the profile still holds an unfinished job from another pairing, check that no CLI that job started is still running, delete `jobs.json` in the profile folder as the message says, and pair again. An existing profile paired with the same origin reconnects without asking for another code; a profile paired with another origin is never reused or sent to the new server. With a connection-ready ZIP, `connect-agend.bat` keeps that profile untouched and pairs a separate one under `%USERPROFILE%\.agend-runtime\profiles\<host>-<port>`; the same bat, and `run`, `status`, `rotate` and `disconnect` started from that folder, find it again. Without `agend-server.json`, or when you choose one yourself with `--profile DIRECTORY` or `AGEND_RUNTIME_HOME` (which always wins), the command fails and names both addresses; keep both with a separate `--profile` and pass the same `--profile` to every later `run`, `status`, `rotate` and `disconnect`.
6. In Settings, explicitly detect this computer's CLI inventory when needed. Connecting alone starts no CLI discovery.

The manual command remains available under **Manual connection command**:

```powershell
.\agend-runtime.cmd connect --server https://your-agend-host --name "Windows desktop"
```

`run` still reconnects a saved profile. Connection defaults never replace its credential or retarget it to another server. Generic packages without `agend-server.json` keep supporting the explicit `--server` command. The connection-ready download uses an administrator POST with the existing same-origin and CSRF protections; GET download URLs cannot embed a caller-selected server.

Creating a pairing code and approving a computer also take an administrator session on the directly reached dashboard (cookie and CSRF): the page's **Connect a computer** and **Approve computer** buttons. A request carrying only the `X-Agend-Token` header is refused (#3327); see the [threat model](SECURITY.md#threat-model).

The ZIP download from Settings requires an administrator session on the local dashboard and is unavailable through public gateway links; the one-line install routes above are separate, public and read-only. It includes program assets, license notices and, for a connection-ready download, the administrator-selected public server origin. It excludes pairing codes, machine credentials, CLI sign-ins and workspaces. If installed runtime assets are missing, update or reinstall AgEnD and retry. Developers can also run `npm run build:runtime` after the normal TypeScript build and transfer the resulting `.artifacts/runtime-bundle` folder.

### Approving a computer that asks to pair

When a computer asks to pair (the ZIP, or the pairing code under **Manual options**), **Settings → Runtime** opens an approval dialog by itself, within about five seconds of the request: the computer's name, host name, platform, when it asked and its **pairing fingerprint in large type**, to compare with the one in that computer's terminal. It is a shortcut to the card's own **Approve**, and nothing about the decision is relaxed:

- **Approve** sends the fingerprint and stays off for the first second the dialog is shown, so a click that was already on its way cannot land on it; the focus does not start on any button, so Enter cannot approve. Without a fingerprint it stays off.
- **Reject** drops the request and asks nothing more. It works only on a computer that is **still waiting**: if that computer was approved meanwhile (in another tab, or by another administrator) the server answers 409, nothing is revoked, and the page says it was already handled and reads the list again. A rejected computer leaves no "Revoked" card.
- **Later**, Esc, the backdrop and × only close the dialog. A computer put off that way **does not open the dialog again by itself**, not even when another computer asks later (that one opens it alone). It stays on the bar above the computers ("N computers are waiting for approval", with **Review and approve**, which scrolls to the first one and opens the dialog) and on its own card. Waiting computers come first in the list, oldest first.
- Several waiting computers are shown one at a time ("1 of 2"); a computer that asks while the dialog is open joins its list. The dialog never opens over another open dialog (rename, diagnostics, a question); it waits until that one closes.
- A request runs out when its pairing code does (ten minutes after the code was made; the Runtime stops waiting then too). An expired request opens no dialog and is not counted: its card says to run the connect command on that computer again, has no **Approve**, and **Reject** clears it.
- Computers that share a name get **#1**, **#2** (by when they asked), when they paired or asked and the first 8 characters of their id, with a hint to rename them; the dialog also says when a paired computer already has that name, which is what a computer pairing twice looks like. A computer's name and host name are shown as text, never as markup.

A computer that joined with the one-time install command never waits, so it never opens this dialog: it is announced by the **A new computer joined with an install command** notice instead, which is an inline notice with **Revoke** and **Dismiss**, not a second pop-up. Only the Settings → Runtime page opens the dialog.

## One-line install (Windows PowerShell)

**Settings → Runtime → Connect a computer → Windows (PowerShell)** shows one command with the address you confirmed in step 1. Paste it into PowerShell on the other Windows computer, as the Windows user whose CLIs are installed. No administrator rights are needed.

```powershell
[Net.ServicePointManager]::SecurityProtocol = [Net.ServicePointManager]::SecurityProtocol -bor 3072; $agend = 'https://your-agend-host'; $s = $null; $h = $null; $s = (iwr "$agend/runtime/install.ps1" -UseBasicParsing).Content; $h = (-join ([Security.Cryptography.SHA256]::Create().ComputeHash([Text.Encoding]::UTF8.GetBytes($s)) | % { $_.ToString('x2') })); if ($s -and $h -eq '<sha256 shown on the page>') { iex $s } else { Write-Host 'install.ps1 could not be verified against the hash on the AgEnD page (a certificate or download error above is the usual cause: trust this AgEnD certificate, or use the ZIP; otherwise reload the page and copy the command again)' -ForegroundColor Red; throw 'install.ps1 was not run' }
```

The page fills in your address and the SHA-256 of `install.ps1`, **and** a one-time token and your AgEnD's server fingerprint (the command above is shown wrapped as `$agendEnroll = '…'; $agendFingerprint = '…'; try { … } finally { … }`; the token part is described in the next section). The command downloads the script, hashes the bytes it received, compares that with the hash on the page, and runs the script **only if they are equal**. The script then installs the Runtime and **connects that computer in the same window**. There is no second command to type.

What happens after the install depends on whether the command carries a token and where it runs:

| Where it runs | What the script does |
|---|---|
| Any window, when the command carries a one-time token (the page's default command) and `$agendNoConnect` is not set | Connects, with **no pairing code and no approval step**, whether or not the window is interactive (an AI agent, CI, a pipeline and `powershell -NonInteractive` all work). It runs the Runtime's own `connect --connection-dir … --enroll-stdin --server-fingerprint …` with the token on the Runtime's **standard input**. See the next section. |
| An interactive console (stdin and stdout are the console, not `-NonInteractive`, not the PowerShell ISE, none of the usual CI variables `CI`, `GITHUB_ACTIONS`, `TF_BUILD`, `BUILD_BUILDID`, `JENKINS_URL`, `GITLAB_CI`, `CIRCLECI`, `BUILDKITE`, `TEAMCITY_VERSION` set to anything but empty, `0`, `false`, `no` or `off`), with no token (the pairing-code route: the command without `$agendEnroll`), and `$agendNoConnect` is not set | Connects, in that window. It runs the Runtime's own `connect --connection-dir`, which is the logic of the ZIP's `connect-agend.bat`: a **new profile** asks for the pairing code, shows the fingerprint, waits for your approval and then keeps running in the foreground; a profile **already paired to this AgEnD** reconnects without asking for a code; a computer already paired to **another AgEnD** gets its own profile and the existing pairing is left alone. |
| Anywhere else without a token: an AI agent, CI, a pipeline, `powershell -NonInteractive`, redirected input or output, or `$agendNoConnect = 1` (with or without a token) | Only installs. It prints the exact command to run next (`agend-runtime connect --server "…"`), says that a person has to type the pairing code in an interactive terminal, and ends with exit code 0. |

The **pairing code** is accepted only from an interactive terminal, never from a command argument, an environment variable or a file, so the script cannot pass it on and never sees it; for the pairing-code route, fingerprint comparison and the approval in AgEnD are unchanged. The **one-time token** is a different, time-limited authorisation with its own rules (next section); it is not a pairing code in an argument. `$agend` is used only as the server address, after the same origin check as before (HTTPS, or HTTP only for this computer; no credentials, path, query or fragment).

**For an AI agent or a script**, give it the **one-time install command**: it connects by itself, in any window, with nothing to type, and when it is run as `powershell -Command "<command>"` its exit status is 1 if the install or the connection failed (0 otherwise); `$LASTEXITCODE` holds the Runtime's own status. (Once the Runtime is connected it moves to the background and the command ends, so an agent is not kept waiting and nothing needs to be started as a separate process; see [Running in the background](#running-in-the-background).) The page's collapsed **Manual options** hold two lines for the pairing-code route. The first only installs (it sets `$agendNoConnect = 1` for that command and clears it again afterwards, so it does not stay set in the window and quietly turn a later paste into an install-only one); the second connects with a pairing code and has to be run by a person in an interactive terminal:

```powershell
$agendNoConnect = 1; <the same install command>; $agendNoConnect = $null
agend-runtime connect --server "https://your-agend-host"
```

**Reconnecting.** Next to the Runtime the installer leaves a reconnect entry for this AgEnD, `%LOCALAPPDATA%\agend-runtime\connect\<host>-<port>-<hash>\`, holding `agend-server.json` (only the public server address, never a credential or a pairing code) and the same `connect-agend.bat` the ZIP has, and it prints where. Double-click it to reconnect; a saved profile reconnects without asking for the code. Each AgEnD gets a folder of its own, so two AgEnDs on one computer never overwrite each other's entry. The batch file calls `agend-runtime.cmd connect --connection-dir <its own folder>` (so it follows `current.txt` to the newest installed Runtime). `--connection-dir DIRECTORY` makes the Runtime read the address from `DIRECTORY\agend-server.json` and pick the profile as the ZIP's `connect-agend.bat` does (the default profile while it is unpaired or paired to this AgEnD, otherwise a separate `profiles\<host>-<port>`); it works with `connect`, `run`, `status`, `rotate` and `disconnect`, and cannot be combined with `--server`. If the install folder's name contains `%` or `^` (a batch file's `call` would misread it) no entry is written and the script falls back to printing the connect command. A repair run (`AGEND_RUNTIME_REPAIR=1`, used by the update flow) writes no entry and never connects.

### The one-time install command (no pairing code, any computer, AI agents)

**Why.** The command comes from a page you are already signed in to, so it can carry the authorisation itself. It works on **any** computer that can reach this AgEnD's address, not only the one the browser is on (copy it on computer A, paste it on computer B or hand it to an AI CLI running on B), and needs no pairing code and no second approval click. This is the same shape as GitHub Actions' `config.sh --token`, Tailscale auth keys and `kubeadm join --token`.

**What the token is.**

- 256 random bits (`agend_enroll_` and 43 URL-safe characters). The server stores **only its SHA-256**; the token is shown once, on the page, and kept in the page's memory only (never in storage or a file, and gone after a reload).
- **Valid for 15 minutes and one use.** Generating a new command ends every earlier unused token. **Revoke and close** (and the *New command* button) end it at once. A used, expired or revoked token is refused with its own message.
- Made by the same people, through the same check, as a pairing code: an administrator signed in on this AgEnD's dashboard (its session and CSRF: the page's own buttons). A request carrying only the `X-Agend-Token` header, a public gateway link, a foreign origin, a guest or a read session is refused (#3327), for making and for revoking a token. Nothing new is granted to anyone who could not already create a pairing code and approve it.
- Bound to this AgEnD's identity: an Ed25519 key kept in the AgEnD data folder (`runtime-server-identity.json`, private, created on first use). The command carries its SHA-256 **server fingerprint**.
- Every issue, use, revoke and replacement is recorded in the machine journal (bounded) and in the AgEnD log, with the token's id, an opaque actor handle and, for a use, the computer's id. So is a **refused attempt on a known token** (with its reason). Where a use or a refusal came from is kept only **masked** (`203.0.x.x`, or the first two of an IPv6 address's eight groups written out, `fe80:0:x:x`; nothing for loopback, which is every client behind a local proxy). Requests that name no known token are not listed one by one: when such a bucket starts refusing, one **throttling summary** is written per bucket and minute. Never the token, its hash or a full address.
- **The owner is told when a computer joins.** The token approves the computer by itself, so nobody is standing at an approval button. When one joins, AgEnD sends a message through its existing notice pipeline (the General topic, the primary chat channel, or the web Notices of a web-only fleet) naming the computer, its host, the token's id and how to revoke it (Settings → Runtime → that computer → Revoke connection). The computer's name and host are what the computer itself said, so they are cut to plain characters and a short length, shown inside quotation marks and with every dot written as a middle dot (so a name that looks like a domain is not turned into a link) before they go into the message. There is **no quarantine**: the computer is usable at once, which is the point of a one-line install.

**What happens when the command runs.** `install.ps1` is still the same fixed bytes pinned by the hash on the page. It reads `$agendEnroll` and `$agendFingerprint`, clears them from the window at once, checks their shape **before** anything is installed (a malformed token stops with a message and exit code 1), and hands the token to the Runtime on its **standard input**: never a command-line argument (it would show in the process list), never an environment variable, never a file; `agend-server.json` and `connect-agend.bat` still hold only the public address. The command's `try … finally` clears the two variables again even when the page's hash check refuses to run the script. The Runtime then:

1. **Proves the server, and agrees a key with it, first.** It asks `POST /runtime/v1/enroll-hello` with a fresh nonce and the token's non-secret id (the first 64 bits of its SHA-256, only so AgEnD can rate-limit that token's own traffic apart from everyone else's). The server makes a **fresh X25519 key** for this one request, keeps its private half in memory for two minutes, and answers with that public key and an **Ed25519 signature, by its enrollment key, over the nonce and that fresh key**. The Runtime requires the enrollment key to hash to the fingerprint in the command and the signature to verify. A server that cannot sign (a reused address, a wrong network, something that is not an AgEnD) fails here, **before anything secret has left the computer**, and the Runtime stops and says so.
2. **Spends the token, sealed.** The Runtime makes its own fresh X25519 key, derives two keys with X25519 and HKDF-SHA256 (one per direction, bound to the nonce, the token id and both fresh keys) and sends `POST /runtime/v1/enroll` with the request (token, fingerprint, name, host) **encrypted with AES-256-GCM**. Only the holder of the fresh private key can read it. The computer is created already approved (the token is the approval) and its machine credential comes back **encrypted under the other direction's key**; the Runtime opens and checks it before anything is saved. The fresh key is spent by the `enroll` call, whatever its outcome, so a request cannot be replayed. The machine credential is stored exactly as for a pairing. (All Node's own `crypto`; no new dependency.)
3. **A profile already connected to this AgEnD just reconnects** and does not use the token (it stays valid until it expires; revoke it on the page if you do not need it). A profile connected to **another** AgEnD gets its own separate profile, exactly as `connect-agend.bat` does, and the existing pairing is untouched.

**What the page shows.** A countdown with *New command* and *Revoke and close*; when a computer joins, the card says so and names it. A notice, **A new computer joined with an install command**, stays on the Runtime page (with **Revoke** and **Dismiss**) until it is dismissed, so a computer that joined without anyone watching is not missed; its card is labelled **Joined by install command**. Revoking the computer closes its connection at once.

**Errors.** Each says what happened and the next step (open Settings → Runtime → Connect a computer, generate a new install command, run it again), exits with a non-zero code, and never prints the token:

| Situation | Message starts |
|---|---|
| Token malformed or incomplete | "…one-time token… is not valid…" (before anything is installed) |
| Unknown token | same as above (an unknown token is not told apart from a malformed one) |
| Expired | "…one-time token has expired (it lasts 15 minutes)…" |
| Already used | "…already used; each token works once…" |
| Revoked, or replaced by a newer command | "…was revoked in AgEnD…" |
| Different AgEnD (fingerprint) | "…did not prove it is the AgEnD this install command was made for… The one-time token was NOT sent…" |
| Machine limit | "…reached its limit of connected computers…" |

**Security analysis (for the owner to judge).**

- *The permission boundary is unchanged.* Whoever can open **Settings → Runtime** can already see a pairing code and approve a pending computer; a token from the same page grants nothing more.
- *The real new risk is leakage of the command.* It can end up in chat logs, AI conversation history, screenshots, PowerShell's PSReadLine history (`ConsoleHost_history.txt`) or CI logs. Whoever gets it **while it is valid and unused** can register **their own computer** as your Runtime, and from then on the work AgEnD assigns (code, prompts, possibly repository credentials available to the agent) is sent to that computer. Mitigations: 15 minutes, one use, replaced by the next command, revocable, stored only as a hash, the token never in an argument, an environment variable or a file, the computer announced on the page with a one-click revoke, and every use audited. What remains is the window between making the command and using or revoking it: **treat the command like a password**, do not paste it into chats or tickets, and revoke a computer you do not recognise. Pasting it into an AI agent's conversation puts it in that conversation's history; that is the cost of letting an agent run it.
- *A used token cannot be replayed*, and a request cannot be replayed either (its fresh key is spent). A server that cannot prove it is the pinned AgEnD never receives the token. And **a server that sits in between cannot read it**: one that has taken over the address and has its own valid certificate can forward `enroll-hello` to the real AgEnD and get a valid proof, but the token and the credential that follow are encrypted to a key only the real AgEnD holds, so the relay sees ciphertext only. It can drop or delay the exchange (the Runtime then stops with a message and the token is not spent), but it can neither read nor alter it: a changed byte in either direction fails the AES-GCM check. (This is tested with a real relay between a real Runtime client and a real coordinator.)
- *Not covered:* script-block logging or session transcripts on the computer that runs the command record the pasted text, and a person or tool that is given the command can of course use it (the point of it). **If the command is run through an outer `powershell -Command "<command>"`** (as an AI agent or a CI step often does), the text, token included, is on that **outer** PowerShell's command line: in the process list, in Windows process-creation events (4688, if command-line auditing is on) and in script-block logs (4104), until the token is used or expires. The Runtime's own command line never holds the token. A profile that was revoked must be disconnected (`agend-runtime disconnect`) before a new command can join it again. If the exchange is cut after AgEnD has spent the token but before the answer arrives, a computer stays approved with nobody holding its credential: revoke it on the page.
- *The pairing-code route is unchanged:* the code can only be typed at an interactive terminal; the token is a separate, time-limited authorisation, not a pairing code moved into an argument.

### Why the command pins the script

The script and the Runtime archive come from the same server over the same TLS channel, so a hash written inside the script can only prove that the archive matches the script. It cannot protect against a modified script, which is the real risk of running a downloaded script. The page the administrator is looking at is the trust anchor: the script's SHA-256 is shown there and put in the command, and is checked **before anything of the script runs**. So the integrity of what runs does not depend on a TLS trust decision. The script then checks the archive against the hash pinned inside it (a second, separate check).

- The hash on the page is read from AgEnD by the signed-in local administrator, not from the script's own response. The server builds the script once as bytes and sends exactly those bytes every time (no newline rewriting, no compression, nothing that depends on the request), so the hash shown is the hash of what is sent. A script modified in transit, a line-ending conversion, a byte-order mark or a script from another server fails the check. So does a stale page: after AgEnD is updated, reload the page and copy the command again.
- **No failure reaches `iex`.** In PowerShell a failing .NET method call is only statement-terminating: that statement is skipped and the next one runs, so a check written as `if (<hash check>) { throw }; iex $s` would run the unverified script whenever the hash cannot be computed (for example under Constrained Language Mode, where `[Security.Cryptography.SHA256]::Create()` is refused). The command is therefore written the other way round: `$s` and `$h` are cleared first, the hash is computed into `$h` in a statement of its own, the condition is only `$s -and $h -eq '<hash>'` (nothing in it can throw), and `iex` sits only inside the branch that condition admits. Whatever fails (the download, the hash, the TLS line), `$h` stays empty, the condition is false, and the other branch prints why and throws; `iex` is never reached. The first statement only adds TLS 1.2 to this PowerShell session (Windows PowerShell 5.1 may not offer it by default); if it fails, nothing the check depends on has changed, and the check still refuses. (The message is written with `Write-Host` before the `throw` because a person's own `$ErrorActionPreference = 'SilentlyContinue'` swallows a bare `throw`.) This shape differs from `if (-not $s -or <hash> -ne …) { throw }; iex $s`, which fails open, and that is the only reason for the difference.
- If the page cannot get the hash (for example the Runtime files were not built on this AgEnD), it shows no install command at all and points to the ZIP; there is no unpinned fallback.
- **If PowerShell reports a certificate error** (for example a self-signed certificate: Windows PowerShell 5.1 refuses those), make that computer trust the AgEnD server's certificate, or use a trusted HTTPS address such as Tailscale Serve, or use the ZIP. **Never turn certificate validation off**, by any switch, callback or policy: this documentation never suggests it, and the command never does it. The hash check does not replace TLS; it removes the need to trust the connection for the script's integrity.
- The address is taken **only** from `$agend`, which the page filled in with the reviewed remote-runtime address you confirmed in step 1. The script reads the address from nowhere else: not the `Host` header that served it, not a redirect, not the network. An address with credentials, a path, a query, a fragment or a quote produces no command; plain `http` is accepted only for `localhost` (an SSH forward).
- Under **Constrained Language Mode or AppLocker** the command **stops without running anything**: the hash cannot be computed there, so the script is never trusted. Use the ZIP instead. `iex` of a string is not subject to the execution policy, and the command never changes your execution policy (machine, user or process).

### What the install script does

1. Checks that Node.js 22.14 or newer (22.14+, 23.6+ or 24+) is installed. If not, it stops and shows `winget install OpenJS.NodeJS.LTS` or nodejs.org. It never installs software for you.
2. Downloads the Runtime archive from `$agend` (one bounded request, redirects refused, at most 16 MiB).
3. Computes the archive's SHA-256 itself and compares it with the checksum written inside the installer script. On a mismatch it stops before anything is unpacked.
4. Unpacks into `%LOCALAPPDATA%\agend-runtime\<version>+<build>`, **beside** any version already there. `<build>` is the first 8 characters of the archive's SHA-256, because one version number can cover more than one build.
5. Points `agend-runtime` at it (below), and adds `%LOCALAPPDATA%\agend-runtime\bin` to **your user PATH**.
6. Writes the reconnect entry (above), then connects in the same window: with a one-time token in any window, with no token only when it is an interactive console; with `$agendNoConnect` set, never (and a token is then reported as not used). Otherwise it prints the connect command. The Runtime is started **after** the install lock is released, because a running Runtime takes that lock to update itself.

**Versions side by side.** An existing folder is never deleted or replaced, because it may be the Runtime that is running right now (a running Windows program holds its files). The install folder is named `<version>+<build>`, so a newer AgEnD's Runtime, and a different build of the same version number, each add a new folder beside the old ones; running the same build's command again finds its own folder and only repoints `agend-runtime`. Nobody has to delete a folder by hand to update. `bin\agend-runtime.cmd` is written once and never changes: it starts the version named in the one-line file `bin\current.txt`, and the install swaps that file in with an atomic replace only **after** the new version is whole. So `agend-runtime` starts either the old or the new version, never a half-installed one, and a batch file that is running is never rewritten. The shim starts with `setlocal DisableDelayedExpansion`, so a `!` in the install folder (an accepted `AGEND_RUNTIME_INSTALL_DIR` can contain one) is kept even when cmd.exe runs with delayed expansion on (`/V:ON` or the DelayedExpansion registry setting). A Runtime that runs in a window keeps its own version until you stop it (Ctrl+C) and start it again; one that runs in the background is restarted by the installer itself when it switched `agend-runtime` to a different build (see [Running in the background](#running-in-the-background)). If a failure happens before the switch, `current.txt` still names the working version. **Earlier folders are not removed by this installer** (one of them may be running); clearing old ones comes with the update and uninstall commands in a later phase. Until then they stay, and you can delete one yourself once no Runtime uses it. The one case the script refuses is a folder that already carries this build's own name but does not hold it, which only happens if it was changed by hand or left incomplete: it is left alone, and the script says so.

**PATH.** The `bin` folder is added to the **user** PATH by writing the registry value back with the kind it had, so a PATH with `%VARIABLES%` stays expandable. `[Environment]::SetEnvironmentVariable('Path', …, 'User')` is not used for the write because it turns a `REG_EXPAND_SZ` PATH into a plain string (measured on Windows PowerShell 5.1 and PowerShell 7), and `setx` is never used because it truncates at 1024 characters. An entry already there, written out or with `%VARIABLES%`, is not added again, and nothing else in the PATH is touched. A running terminal does not see the change; open a new one, or use the full path the script prints.

It deletes only its own staging folder, a temporary sibling file it just wrote, and an install folder it created itself and that is still empty after a failure. It reports failures with a non-zero `$LASTEXITCODE`.

Optional variables, set in the same PowerShell window before the command:

| Variable | Effect |
|---|---|
| `$agendNoConnect = 1` | Install only: do not connect, even in an interactive window. Any value except empty, `0`, `false`, `no` and `off` counts as set; it stays set in that window until you clear it with `$agendNoConnect = $null`. |
| `$agendEnroll`, `$agendFingerprint` | The one-time token and the AgEnD server fingerprint. Set by the page's command, read and cleared by the script (and cleared again by the command's `finally`). You do not set these by hand. |
| `AGEND_RUNTIME_NO_PATH=1` | Leave PATH alone. The final message then shows the full path of `agend-runtime.cmd` to run. |
| `AGEND_RUNTIME_INSTALL_DIR=D:\agend` | Install under this folder (a full drive path) instead of `%LOCALAPPDATA%\agend-runtime`. |

### What the server serves

Three read-only GET routes, next to the pairing endpoints, need no sign-in:

| Route | Content |
|---|---|
| `/runtime/install.ps1` | The installer script, with this server's runtime version and the archive's SHA-256 written into it. |
| `/runtime/v1/bundle/windows.zip` | The generic Runtime archive: the same `createRuntimeBundle()` output Settings downloads, without `agend-server.json`. |
| `/runtime/v1/bundle/windows.json` | Exactly `{version, sha256, bytes}` for that same cached archive. No download URL or pairing data. |

They are served only while **Allow other Windows PCs to pair** is on (otherwise all answer `404`, exactly like an unknown route), never through a public gateway link (`404` there too: the gateway does not list them), and only over HTTPS or loopback (plain HTTP from anywhere else is refused with `403`). The usual Host allow-list still applies.

Both are **static for a server version**: the generic bundle is built once per server process and kept, so its hash is stable, and the script is that bundle's version and SHA-256 inside a fixed template. Nothing in a response depends on the request: not the Host header, a query (a query is refused), a cookie or the caller. Neither carries a token, secret, pairing code, profile, user data or server address; the address comes from `$agend` in the command. The script is never cached (`Cache-Control: no-store`). The archive carries `Cache-Control: no-cache` and an `ETag` made from the server version and its SHA-256; a matching `If-None-Match` is answered `304` without the body. The script still verifies the archive's pinned SHA-256, so a cached copy is never trusted on its own. Downloading the installer grants no authority: pairing (one-time code, ten-minute expiry, fingerprint, local administrator approval) is unchanged, and an unapproved computer can do nothing.

The metadata comes from that same cached bundle, so its hash and byte count describe the ZIP actually served. ZIP and metadata use the same `ETag` (`"<version>-<sha256>"`), `Cache-Control: no-cache` and conditional `304` behavior. `HEAD` returns their headers without a body. Managed Runtimes use these fixed endpoints for automatic updates; fetching metadata alone never switches a running Runtime.

The two enrollment endpoints (`POST /runtime/v1/enroll-hello` and `POST /runtime/v1/enroll`) sit with the pairing endpoints, not with these downloads: loopback or TLS only, no browser `Origin` or cookie, small bodies, and a rate limit per token and per address. `enroll-hello` is public by design (it signs a caller's nonce with a fresh key and spends nothing); `enroll` needs a valid token inside its sealed box. A request that names an existing token by its non-secret id has **that token's own rate bucket**, so flooding the address bucket (every client behind a local proxy shares one address) cannot keep a real installer out; requests that name no known token share the address bucket.

Requests are rate limited per client address with a small burst, and in total, because a reverse proxy makes every client look like one address. Metadata polling has its own allowances, so it cannot consume the script/ZIP download budget. Conditional requests and `HEAD` also count. A client address is asked first: a request its own allowance refuses costs the shared total nothing, so one address that hammers a route is held by its own limit and cannot use up what everyone else shares. A held request gets `429` with `Retry-After`. The archive can never exceed the bundle's 8 MiB cap.

### Automatic Runtime updates

A new one-line installation records its paired origin and registers every running Runtime using that installation. It checks only that paired AgEnD, on connection and periodically. It verifies the bundle's SHA-256, never downgrades SemVer, and aligns a different build at the same version. Switching waits for positive idle evidence: no running pane, task, delivery or physically unfinished transport operation is stopped to obtain idle.

Settings → Runtime shows **Update pending**, the target version/bundle hash and the running version/build. A candidate that fails before activation returns to the previous verified code and reports **Update failed** there and in the owner's **Needs you**. Its failed hash is not retried until the server offers another hash. An uncertain activation keeps the candidate and exact attempt; it never guesses that rollback is safe. Updates replace Runtime code only, preserving the pairing/profile and the user's CLIs and execution policy.

ZIP/npm installations, older managed roots without a proven origin, and shared installation roots do not automatically switch. **Show reinstall command** offers the existing hash-pinned one-line installer in a fresh separate folder. Run `agend-runtime status` with the same `--profile` or `AGEND_RUNTIME_HOME`, note its profile folder, then close the old Runtime. The repair installer leaves PATH unchanged, restarts any Runtime that already runs in the background (so it uses the new build) and prints a command for its new full-path shim to `start` the Runtime in the background; enter that same existing profile folder when asked. It prints no new pairing steps. Separate installations are required for different paired AgEnD origins; another live/unknown owner of the same root also defers updates.

Update reports are bounded diagnostics tied to the authenticated Runtime connection, not update permission or health evidence. Older peers that do not negotiate reporting show **Update status unavailable**, never an invented success. A previous/offline report is labelled as such. A reconnect clears a cached positive match until a check for that connection confirms it again. Failed-build Needs-you notices are omitted from public links. A hard-crash recovery journal remains manual/fail-closed; a blocked Runtime cannot promise a fresh online report.

### Remove it

Disconnect the profile (this stops its background Runtime and removes its sign-in task) and delete the program folder, then remove its `bin` folder from your user PATH (Windows **Settings → System → About → Advanced system settings → Environment Variables**, user variable `Path`):

```powershell
agend-runtime disconnect
Remove-Item -Recurse -Force "$env:LOCALAPPDATA\agend-runtime"
```

That removes every version folder and every profile's logs at once; stop every Runtime window first. Run `agend-runtime disconnect` (or `agend-runtime autostart disable`) for **each** profile first: a sign-in task whose program was deleted would only fail quietly at the next sign-in. `agend-runtime status` lists every profile. There is no separate uninstall command yet.

The profile (`%USERPROFILE%\.agend-runtime` by default) is separate and stays until you delete it. Revoke the computer in AgEnD Settings to invalidate its credential centrally.

## Running in the background

Once the Runtime has connected (the first time, or when a saved profile reconnects), `connect` moves it to the background and ends: the Runtime keeps running with no window, so closing the window that ran the install command, `connect-agend.bat` or `agend-runtime connect` does not disconnect it. The pairing code, the fingerprint comparison and the approval (or the one-time token) still happen in the foreground window, **before** that. An AI agent or CI that runs the one-time install command gets its exit status as soon as the Runtime is connected; nothing has to be started as a separate process.

| | |
|---|---|
| `agend-runtime connect … --foreground` (or `$agendForeground = 1` before the install command) | Keep the Runtime in the window instead, as before; Ctrl+C stops it. No sign-in task is created. |
| `agend-runtime start [--profile DIRECTORY]` | Start the background Runtime of an already paired profile. This is what the sign-in task runs. |
| `agend-runtime run` | Unchanged: reconnects an existing profile and stays in the window. |
| `agend-runtime status [--profile DIRECTORY\|NAME] [--json]` | Every profile on this computer: state (running in the background, in a window, or not running), process id, since when, the AgEnD address it is paired to, autostart and the log folder. `--profile` takes a folder or a profile name that `status` printed. |
| `agend-runtime stop [--profile …\|--all]` | Asks the background Runtime to stop the way Ctrl+C would, and waits until it is gone (30 seconds). With several running, name one or use `--all`. A Runtime in a window is refused: close that window. Autostart is not turned off. |
| `agend-runtime restart [--profile …\|--all]` | `stop`, then `start` with the installed version. Nothing running: nothing is started. |
| `agend-runtime logs [--profile …] [--tail N]` | The end of the profile's log (50 lines by default). |
| `agend-runtime autostart [enable\|disable\|status]` | See below. |

**One Runtime per profile.** The profile lock decides it. Starting a second one (a second double-click, the sign-in task while it is already up, `start`, `connect --foreground`) says "already running", names the process and ends with exit status 0; nothing is started and nothing is stopped.

**Logs.** A background Runtime writes what a window would have shown to `%LOCALAPPDATA%\agend-runtime\logs\<profile>\runtime.log`, one line per event with a timestamp. `<profile>` is `default` for `%USERPROFILE%\.agend-runtime`, the folder name (`<host>-<port>`) of a per-server profile (when that name is longer than 64 characters or has characters a file name cannot carry, it is shortened and ends in 8 hex characters of the complete profile folder path, so two long names never share a log folder or a task), and `custom-<folder>-<8 hex>` for a folder chosen with `--profile` or `AGEND_RUNTIME_HOME`. A file is at most 2 MiB; then it becomes `runtime.log.1` and older ones move up to `.5`, the oldest is deleted, so a profile's logs never take more than 12 MiB. The log holds the Runtime's own messages (connected, disconnected, update, stop, the reason AgEnD ended a connection); like the window it replaces, it holds no pairing code, token or credential.

**Autostart.** The first time a background connect succeeds with the Runtime **connected** (not while the one just started is still connecting, and not when a Runtime in a window was found), the Runtime adds one Windows **Task Scheduler** task for your own account, `AgEnD Runtime - <account> - <profile>` (task names are unique on the computer, so the name carries 8 hex characters of the Windows account as well as the profile: two people's `default` never share a task), triggered 20 seconds after you **sign in**. It is not a Windows service and needs no administrator rights: it is created with `schtasks.exe` from an XML definition that names your account with an ordinary (limited) token, no password and no elevation, so there is no UAC prompt. The task does not keep the Runtime alive; it runs the short command `agend-runtime start --profile <folder>` (the installer's `agend-runtime.cmd`, which always starts the newest installed version), which starts the background Runtime, or reports that one already runs, and ends. A computer that was off, or a user who signed out, therefore gets the Runtime back at the next sign-in, and it reconnects by itself. `autostart disable` removes the task and keeps it off for that profile (a later `connect` does not turn it on again); `autostart enable` creates it again; `autostart status` says which. If Windows refuses (a company policy), `connect` still succeeds and says so, and `autostart enable` tries again. `disconnect` removes the task, and keeps an "off" you chose: if you ran `autostart disable`, disconnecting and connecting again does not turn it back on (a profile that never had a choice, or had it on, starts afresh). A path the task cannot carry safely (a quote, `%`, `& ^ | < >` or a line break, in the install folder, the profile folder or the program's own path) is refused with the way out, never written into a task that would do something else. Whether the task exists is read from Windows' own task list when the direct lookup fails, so a broken `schtasks` is reported instead of being taken for "no task".

**How it stops.** (A stop that cannot be confirmed, because an account process is still running, leaves the Runtime up and watching: the next `stop`, `restart` or `disconnect` asks again.) A detached Windows process has no console and no signal that lets it stop in an orderly way, and a hard kill would skip the orderly stop of its account processes and its profile lock. So `stop` writes a small request file (`stop-request.json`, only a time) into the profile folder, which the background Runtime watches and consumes; `stop` then waits for the profile lock to be released and asks again if the Runtime is handing over to a new version. Whoever can write to the profile folder (the same Windows user) can already end the process, so this adds no authority.

**What is in the profile folder.** Besides `connection.json` and `jobs.json`: `instance.json` (which process is the background Runtime, so `status` can say so), `autostart.json` (your autostart choice), `background-state.json` (the word a starting Runtime leaves for the command that started it) and, briefly, `stop-request.json`. None holds a secret. A background Runtime's command line is `node.exe …\runtime-cli.js run --profile <folder>`: no pairing code, one-time token or credential, ever (the token is read from standard input by `connect`, before the Runtime is started).

**Starting without holding the caller.** A process that Node starts "detached" still inherits every inheritable handle of its parent on Windows, among them the output pipes of whoever ran the command (an AI agent's shell, CI): that caller would wait for the Runtime to end because the pipe never closes. Measured on Windows: 40 seconds with the Runtime stand-in alive, 0.3 s through the method used here. So the background Runtime is started with Windows PowerShell's `Start-Process` (hidden, with the same environment and its own hidden console), which passes no handle on, and the launcher learns that it connected from `background-state.json`. It also outlives the Task Scheduler task that may have run the launcher (measured: still online 20 seconds after the task ended).

**Updates, repair and the installer.** The in-place update of a managed install hands over to the new build and the new process takes over everything above: same log, same stop request, same marker (measured: after the hand-over `status` shows the new process in the background and `stop` stops it). When the install command switched `agend-runtime` to a different build, or a repair run (`AGEND_RUNTIME_REPAIR=1`), it runs `agend-runtime restart --all` after the install lock is released, so a Runtime in the background uses the installed build; a Runtime in a window is left alone, and a failed restart is a warning, not "install failed" (and when the installation itself failed after the build was selected, or its lock could not be confirmed released, nothing is stopped or restarted and the status stays a failure). `$agendNoConnect = 1` still means "install only: do not connect", and does not hold back this restart.

**Limits.** The sign-in task runs only while you are signed in, which is also when your Windows CLIs and sign-ins exist; there is no pre-logon service. A Runtime in the background has no window to show a problem: `status` and `logs` are where to look, and `status` prints the log folder. A real sign-out and sign-in was not exercised in verification (it would end the session that runs the tests); the task was run by hand with `schtasks /Run`, the same action Windows runs at sign-in.

## Network connection

The runtime uses `/runtime/v1/connect` on the same externally reachable AgEnD service as pairing and the dashboard. Remote origins require HTTPS/WSS and a valid certificate. HTTP is accepted only for exact loopback hostnames, for example `http://localhost:19280` through a private SSH forward. The client refuses credential-bearing URLs and redirects.

The existing coordinator listener still binds to loopback. Publishing a new port, changing a firewall or configuring TLS/proxy access is a separate host operation; pairing does not make the listener reachable automatically. A proxy must pass WebSocket upgrades on `/runtime/v1/connect` and POST requests on `/runtime/v1/pair`, `/runtime/v1/claim` and `/runtime/v1/rotate`. The one-line install also needs GET on `/runtime/install.ps1` and `/runtime/v1/bundle/windows.zip`. Pairing codes expire after ten minutes and are single-use. The runtime machine credential is unrelated to browser sessions; browser cookies and origins cannot authenticate the runtime channel.

This preview does not open a runtime listener for other computers. Its per-turn MCP relay binds an ephemeral port to **127.0.0.1 only**, and requires a separate random capability for the active execution. It relays scoped AgEnD tool calls over the authenticated outbound runtime connection. The CLI never receives the permanent machine credential. Existing local `/agent` restrictions remain in place.

## Connecting over a private network

### Tailscale Serve (recommended for another computer)

Install and sign in to Tailscale on the coordinator host and the Windows runtime computer, using an approved tailnet. The runtime computer also needs the Windows Node.js installation and CLI sign-ins described above. Enable HTTPS certificates for the tailnet when prompted by Tailscale. Serve provides a valid certificate for the host's `https://<host>.<tailnet>.ts.net` address; tailnet access rules still control which devices may reach it. See [Tailscale Serve](https://tailscale.com/docs/features/tailscale-serve).

1. On the coordinator host, verify that `http://127.0.0.1:19280/ui` reaches AgEnD locally. If AgEnD runs in WSL, run this check and Tailscale Serve on the **Windows host**. Windows can normally reach a WSL application through localhost, but verify this on the actual machine before configuring Serve; WSL networking mode, localhost forwarding and host configuration can affect reachability. Keep AgEnD bound to loopback while resolving that local connection. See [Microsoft's WSL networking guidance](https://learn.microsoft.com/en-us/windows/wsl/networking).
2. Inspect existing mappings with `tailscale serve status` **before** adding a proxy. Do not overwrite an HTTPS port or root mapping that already serves another application. The example below assumes port 443 is unused; otherwise choose an unused HTTPS port, substitute it in `--https`, and include that port in the runtime's server origin (for example, `https://coordinator.example-tailnet.ts.net:8443` if 8443 is free). Then proxy the AgEnD origin from a coordinator terminal:

   ```powershell
   tailscale serve --https=443 http://127.0.0.1:19280
   ```

   Leave this foreground command running. In another terminal, use `tailscale serve status` to verify the HTTPS hostname, selected port and root `/` proxy target. These commands follow the [Serve CLI reference](https://tailscale.com/docs/reference/tailscale-cli/serve).
3. On the other Windows computer, enter the extracted Runtime folder and use the exact HTTPS origin printed by Serve:

   ```powershell
   .\agend-runtime.cmd connect --server https://coordinator.example-tailnet.ts.net
   ```

   Enter the pairing code interactively and approve that computer from the local AgEnD administrator dashboard. Keep the Runtime terminal running too.
4. Stop the foreground Serve command with **Ctrl+C** when sharing is no longer needed. An operator can also remove this HTTPS mapping with `tailscale serve --https=443 off`; substitute the original HTTPS port if changed. Avoid resetting unrelated Serve mappings.

**Never use `tailscale funnel` for this setup.** Funnel publishes the service to the internet; Serve is intended for access within the tailnet. Tailnet membership and its access rules become part of the trust boundary for the reachable pairing/claim endpoints. Admit only intended devices and users, and retain AgEnD's single-use code, local administrator approval and machine-credential checks. Tailscale identity headers do not replace AgEnD authentication.

Mount the origin at `/`, without rewriting paths. The proxy must preserve both JSON POSTs (`/runtime/v1/pair`, `/runtime/v1/claim` and `/runtime/v1/rotate`) and the HTTP/1.1 WebSocket upgrade (`/runtime/v1/connect`), including the runtime's Authorization header. Verify a complete pairing/approval/claim and an online Runtime connection through the chosen proxy; loading the dashboard alone does not establish that the WebSocket path works. Record the Tailscale version and confirm that the connection remains online, including a reconnect, when validating an actual tailnet deployment. Automated proxy tests do not by themselves certify a particular Tailscale installation or its access policy.

### SSH local forward

With an SSH server and account already configured on the coordinator, open this forward **from the Windows runtime computer**:

```powershell
ssh -N -o ExitOnForwardFailure=yes -L 127.0.0.1:19280:127.0.0.1:19280 user@coordinator
```

The first loopback address binds the forwarded port only on the runtime computer; the second is reached from the SSH server's host. `-N` runs the forward without a remote command, and `ExitOnForwardFailure` stops SSH if it cannot establish the requested listener. See the [OpenSSH client manual](https://man.openbsd.org/ssh) and [forwarding configuration](https://man.openbsd.org/ssh_config#ExitOnForwardFailure). For a WSL coordinator, choose an SSH endpoint from which AgEnD's loopback port is reachable. Keep the SSH terminal open. In another terminal, inside the Runtime folder, run:

```powershell
.\agend-runtime.cmd connect --server http://localhost:19280
```

Enter the pairing code and approve the machine as above. This HTTP origin meets the runtime's loopback rule; SSH encrypts the traffic between computers. If port 19280 is already used on the runtime computer, choose another **local** port in `-L` and use that port in `--server`. Stop the Runtime and SSH commands with **Ctrl+C** when finished.

**Plain HTTP to a LAN or tailnet IP address is refused deliberately**, including `http://192.168.1.20:19280`. On an ordinary LAN, HTTP would send the pairing code and permanent machine credential in cleartext, allowing interception or impersonation of the coordinator. The client keeps its HTTPS-origin requirement even when a private network provides separate transport encryption. Use a valid HTTPS origin or the loopback SSH-forward path. This preview does not accept a self-signed certificate or implement certificate fingerprint pinning; that is a possible follow-up, not a prerequisite for these two paths.

## Inventory and models

Pairing and reconnecting establish the runtime connection without launching CLI discovery. After approving a newly paired computer, open **Settings → Runtime** and click that computer's **Refresh CLI inventory** button to run detection explicitly. Until a successful detection has been saved, the computer can be online while its CLI list is empty. Local Windows CLI detection likewise requires an explicit administrator action in the local diagnostics.

Agent creation, CLI selectors and native model selectors read the last successful saved inventory. Opening those screens, refreshing a model selector through a GET request, connecting or reconnecting a runtime, and starting a task do not run CLI discovery. There is no periodic background detection. Use **Refresh CLI inventory** after installing, removing, updating or signing in to a CLI; refreshing the machine list only reloads the coordinator's saved machine information.

Successful detection saves the CLI inventory and its update time for subsequent reads and reconnects. A failed or incomplete detection retains the previous successful inventory. Detection reports versions, login availability and model list provenance, without reading or uploading CLI login tokens.

The Runtime's private inventory file is the local execution gate. If that file is removed or corrupted, the Runtime reports an empty, never-detected inventory and requires a new explicit detection; it does not restore runnable capabilities from an older central snapshot. The machine card's inventory update timestamp records the latest central synchronization. The inventory's `probedAt` records when detection actually ran, so reconnecting and republishing a cached list is not a new detection.

Only installed, execution-compatible CLIs are selectable. Each CLI retains its normal approval and sandbox policy. No `--yolo`, blanket approval or sandbox bypass is added. A provider that cannot enforce read-only execution must use its explicitly selected native permission mode. Installing a runtime does not make every local tool safe or available without the CLI's normal permissions.

## Disconnects, cancellation and recovery

- Accepted execution identity is saved **before** starting a child process. Repeating the same ID and arguments returns the original snapshot; changed arguments under the same ID are refused.
- During a short connection loss, the runtime retains the child process and its bounded output. It reconnects with exponential backoff and jitter, capped at thirty seconds. Reconnection replays snapshots; it never relaunches a prompt automatically.
- If the connection remains down for forty-five seconds, cancellation is requested for the active execution. A cancellation request is not proof of stopped processes. The terminal status is reported only when the worker confirms completion or shutdown.
- After a runtime crash/restart, an unfinished execution is marked **unknown** and blocks new work. Check its Windows processes and use the explicit recovery action after confirming they stopped. Recovery clears the block; it never reruns that execution.
- AgEnD MCP authority is checked centrally for each execution and tool. A disconnected or revoked execution does not gain a new MCP grant simply because it reconnects.
- Each runtime currently has one execution slot and retains the existing native worker's five-minute execution limit. The journal retains 128 recent snapshots and 4,096 used execution identities; old identities cannot be silently reused after snapshots expire.

## More than one Claude account on one computer

A Windows computer can keep several named Claude Code sign-ins ("credential profiles") and each agent can use one. The names work like the Linux/WSL `credential_profile`, but everything stays on that computer.

On the Windows computer, in the Runtime folder and under the Windows user whose Claude Code you use:

```powershell
.\agend-runtime.cmd login claude-code work       # creates the sign-in and runs `claude auth login` for it, here
.\agend-runtime.cmd login claude-code home
.\agend-runtime.cmd profile list                 # name and signed in / not signed in
.\agend-runtime.cmd profile default work         # optional: used by agents that choose none, for this pairing
.\agend-runtime.cmd connect --credential-profile work   # the same default, set while connecting
```

Then choose **Detect again** in that computer's **CLI diagnostics** (Settings → Runtime): the card lists the profile names and whether each is signed in, and the agent settings (new Windows agent, **Change runtime / CLI**) offer a **Claude account** choice. Changing the account of an existing agent starts a new conversation, like any runtime change, because a conversation lives in one account's folder.

How it is kept safe:

- **AgEnD only sends a name.** The Runtime turns it into `<this pairing's profile folder>\credential-profiles\claude-code\<name>` on that computer and sets `CLAUDE_CONFIG_DIR` for that one run or terminal, replacing any ambient value. A name resolves only through that fixed folder; anything that would leave it is refused. AgEnD never accepts, stores or sends a folder.
- **Changing the default** (`profile default NAME` or `--clear`) works while the Runtime is running and is used from the next run or new terminal; a terminal that is already open keeps the profile it started with, and reconnecting does not disturb it.
- **Consent.** The profiles live in the pairing's own folder, and only the computer's local administrator creates and signs one in. Approving the pairing lets that fleet use every profile signed in there, and no other fleet that pairs with the same computer. The fleet admin can choose which profile an agent uses from the ones the computer reports; they cannot create a profile, set the pairing's default, read a credential or point at a path. The pairing's default profile is set only on the computer (`connect --credential-profile` or `profile default`).
- **Names** follow the Linux rule (letters, digits, `.`, `-`, `_`; start with a letter or digit; at most 64) and also exclude Windows device names (`con`, `nul`, `com1`…, also with an extension such as `nul.txt`) and trailing dots, which Windows would alias to another folder. Names are unique without regard to letter case when creating, listing and resolving: `work` is refused when `Work` exists, and two folders that differ only by case are neither listed nor usable.
- **Sign-ins never leave the computer.** Only the names and a signed-in yes/no are reported to AgEnD; no path, e-mail or token.
- **It fails closed.** An unknown, signed-out or unconfirmed profile, a malformed name, or a Runtime that is too old to report the `credential-profiles` capability stops the run or terminal with a message that says what to do. It is never replaced by the computer's own account. AgEnD refuses to send a profile to an older Runtime for the same reason.
- **Which account is it?** The Runtime reads `claude auth status` on that computer for each profile and for its own default sign-in and reports the account's whole e-mail address and the plan, shown as `work · alice@example.com · Team` on the computer's card and in the **Claude account** choice (the whole address, because one person's accounts usually share a prefix and a shortened `al***@example.com` would show two of them as one). The address is sent only over the Runtime's own authenticated connection to the AgEnD it is paired with; it is never logged, never part of an error message, an audit line, a notice or a chat reply, and the Runtime keeps it only in the status cache inside that profile's own folder (protected by the profile folder's user ACL on Windows, mode `0600` on POSIX). A missing address, a non-ASCII address, one with a space or a second `@`, or one over 254 characters sends none (it is never shortened to fit); an API-key sign-in is shown as "No account email (API key)". The plan is one of `free`, `pro`, `max`, `team`, `enterprise`, or `unknown`. AgEnD accepts only that exact form (an older Runtime's cached `ab***@example.com` is still accepted) and treats anything else as a protocol error that names the field, never the value. `agend-runtime` prints the redacted `ab***@example.com` form in the terminal, never the whole address. It is refreshed only when you choose **Detect again**, and automatically after `agend-runtime login` (so signing a profile in to another account updates it). A Runtime without the `account-identity` capability simply shows no account. **Only a fleet admin on the dashboard reached directly sees these details** (the e-mail and the plan; "directly" is this machine, a LAN, a tailnet or your own proxy, see [The three ways in, compared](web-dashboard.md#the-three-ways-in-compared)), on the Runtime page, the Claude account choice, Settings → Agents and Settings → Accounts. Everyone else gets the same pages without them, with the profile names and signed-in yes/no unchanged: a session over the temporary public link or a fixed address (a named tunnel), even a fleet admin's; a guest or read-only session; an agent calling with the CLI's header token. They are not in agent tools or in anything an agent can read.
- **Terminals** (persistent panes) take the profile per terminal, so one long-lived host never carries another account's environment. A terminal host that is already running from before an upgrade keeps refusing profiles until its panes are closed and a new host starts.
- **Limits.** Claude Code only. A sign-in made with a Console login that creates no API key is stored outside the config folder and cannot be separated by profile. `ANTHROPIC_API_KEY` and `CLAUDE_CODE_OAUTH_TOKEN` are still not passed to a Windows Runtime's Claude Code. AgEnD shows no usage or quota for accounts on a Windows computer. Changing a pairing's default account makes conversations that were started under the old account impossible to resume under the new one.

## Letting AgEnD manage accounts on a computer (remote setup)

By default a fleet administrator can only *choose* among the profiles a computer already has. With the **accounts** switch on, the computer's local administrator also lets the dashboard add, sign in, sign out and remove Claude Code profiles **that this Runtime created**. A second switch, **install**, is reserved for installing a CLI from the Runtime's own closed list. This section is the Runtime side (#3190 Part 3a); the dashboard side, in Settings → Accounts, is [below](#managing-a-computers-accounts-from-settings--accounts-remote-setup-3c).

```powershell
.\agend-runtime.cmd remote-setup status
.\agend-runtime.cmd remote-setup accounts on --for 2h    # off again by itself after two hours
.\agend-runtime.cmd remote-setup accounts off
.\agend-runtime.cmd remote-setup install on|off          # same shape; a Runtime reports `cli-install` only when it can install
```

- **Off by default, set only on that computer.** The switches live in `remote-setup.json` in the pairing's own folder. Nothing in the Runtime protocol writes them, so AgEnD cannot turn one on. While a switch is off every matching request is refused with the command to run there. The two switches are independent. `--for` takes `2h`, `90m` or a number of hours (1 minute to 168 hours); an expired switch is off, and so is a timed switch whose end is further away than 168 hours from now (a clock that was moved back, or a hand-written value, cannot bring it back). The switch is looked at again after every check that can wait (ownership, the PowerShell link check, the CLI lookup) and immediately before each step that changes something: creating a profile folder, starting the sign-in child, starting the logout, deleting the backups, the rename of a removal, writing the cache of a check, and starting an install. A switch turned off or run out while a request waits stops it there; nothing is created, started, renamed or deleted afterwards. Ending and closing what already runs stays possible while the switch is off. While a sign-in is open the Runtime looks at its switch every few seconds: if the switch is turned off or runs out, the sign-in is ended (its CLI process is killed, and again at the next look if that could not be confirmed) and the record says `switch_off`.
- **Two requests do not look at a switch, on purpose.** `accounts.switches` only reads the two switches, so a dashboard can say why a request would be refused. `signin.close` only ends a sign-in that is already running, so turning a switch off can never leave a sign-in that cannot be closed.
- **Stopping, and the connection.** A request is admitted only while the Runtime is not stopping and the connection it arrived on is still the live one; it is counted until it has completely unwound. When the Runtime stops, admission closes first, then it waits for every request in flight (a start that is waiting for the CLI lookup finds the door shut when it wakes and creates nothing), then ends any sign-in. When the connection drops, a sign-in that was opened over it is ended, requests of the old connection may not start anything more, and an answer is only ever sent on the connection that asked (a late answer is dropped, never sent to a later connection). A managed update that is preparing or in trial refuses account requests (`holding new work`), and an open sign-in, a running logout or install, and a request in flight all count as Runtime activity: the update fence does not pass while any of them exists.
- **Own frames, not stored by AgEnD.** The requests travel as `account.request` / `account.response`, not as `request`: the server journals every `request` and its answer to disk, and a sign-in link or one-time code must not be written there. Capabilities: `remote-signin` (this Runtime can do the account operations) and `cli-install` (only when an installer is wired in; this program reports it never yet). AgEnD must send an `account.request` only to a Runtime that reports `remote-signin`; an older Runtime treats the frame as a protocol error and disconnects.
- **Names and ids only.** A request carries a CLI id, a profile name, a sign-in method and the person's name for the record. Never an argv, a command, a path or an environment; an extra field is refused naming the field, not its value.
- **Sign-in.** The server's `StructuredSignIn` drives five calls (start, capture, status, write, close). The Runtime builds the command itself (`claude auth login --claudeai`), with `CLAUDE_CONFIG_DIR` set to the profile's folder, `BROWSER=true`, pipes, no shell, and a scratch folder it removes at the end.
  - **Subscription accounts only.** A request for a Console sign-in (`method: "console"`) is answered `unsupported` with the command to run on that computer (`agend-runtime login claude-code NAME`): a Console login that creates no API key is stored outside the config folder, so a profile could neither isolate nor remove it. The protocol keeps both method values so that this can be opened later without changing it.
  - **Minimum Claude Code 2.1.79.** The host's sign-in picks the method in the menu of `claude auth login`; the Runtime has pipes and no menu, so it passes the flag. Measured: `claude auth login --help` of 2.1.78 lists no `--claudeai`, that of 2.1.79 does (and `--console`, which the changelog records for 2.1.79); 2.1.319 was used for everything else here. A Claude Code that does not know the flag exits at once, and `signin.status` reports `alive: false` immediately; it does not wait for the ten-minute limit.
  - **What `capture()` carries.** It is not the CLI's output: it is rebuilt from a closed table of lines: the sign-in link, the code prompt, and the outcome, each in its fixed form (`Logged in as <e-mail>` reaches the server as `Login successful`). The link must be `https://` followed by printable ASCII only (a bell, backspace, NUL or any control character drops the line), on an allowed host, no credentials, at most 4096 characters, and is sent as the URL parser writes it back. **The link's query string is chosen by the CLI and is not a closed set**; it is the sign-in request itself, so it is what lets the administrator's browser sign in, and it is shown to administrators only. Outcome lines count only at the start of a line (or right after the prompt, where the CLI prints its verdict).
  - **Limits.** One code per sign-in, in the characters a code has, only while the prompt is showing, sent with a carriage return (measured on Linux with claude 2.1.319 and a temporary `CLAUDE_CONFIG_DIR`: a wrong code gets `Invalid code` with `\n`, `\r` and `\r\n` alike; the Windows check is still to do). One sign-in at a time on the computer, at least 5 seconds between starts and at most 12 an hour, and a ten-minute timeout (retried until the process is confirmed gone), all enforced here. A sign-in whose process has ended, or whose earlier close failed, is closed again by the next start, so it cannot block sign-ins until the Runtime restarts.
  - **Success** is the CLI's own `auth status` for that profile (the shared parser), never output text. A test pins that this flow's argv and patterns equal the host's `LOGIN_FLOWS["claude-code"]`.
- **Only what this Runtime created.** Sign-out and remove need *evidence* that the Runtime made the profile (`created.json` in the profile root, written when `login` or a remote sign-in creates it) and that it sits where it should: under this pairing's fixed root, a valid name, a real folder, and no link at any level. The four levels above and including the profile folder (the pairing folder, the profile root, the CLI folder, the profile folder) are checked as links **and** as any other Windows reparse point (junction, symbolic link, OneDrive placeholder and so on) by asking Windows PowerShell; if that cannot be answered (PowerShell missing, or restricted by a constrained language mode) nothing is changed. Inside the profile folder only links are looked for (what the file system reports as a symbolic link or junction); other reparse points inside are not checked. A folder made by hand, or by a Runtime from before this feature, is only changed on the computer. The Windows user's own sign-in (`~\.claude`) is never touched.
  - **Remove** takes one more look, synchronously and immediately before the rename, at the switch, the default profile, tasks, terminals and sign-ins as they are at that instant (the earlier checks wait; this one does not), then renames the folder to a unique temporary name (renaming a link renames the link itself), then checks again: the folder above it (its real path must be this pairing's `credential-profiles\claude-code`), the renamed folder itself (a real folder, not a reparse point, nothing linked inside), and only then deletes it; any failure puts the name back. So a folder, or the CLI folder above it, swapped for a junction between the check and the delete is neither followed nor deleted.
  - **A leftover is never silent.** If a removal fails and the name cannot be put back either, the folder stays as `.removing-<16 hex>` (not a valid profile name, so it is never listed as a profile or selected) and may still hold a sign-in. `agend-runtime profile list` on that computer lists it and says what to do: delete the folder yourself to finish removing it, or rename it back to its profile name to keep it. The Runtime never deletes or restores it by itself.
  - **One start at a time on the computer.** Starting a sign-in takes a computer-wide flag in the same synchronous step as the switch and profile checks, and keeps it until the sign-in is running (or has been refused), because the sign-in slot itself is only taken at the end: without it, many starts under different names could each pass the checks, record `started` and create a folder before the first one took the slot. The same holds for installs (one at a time). The other changes are exclusive per profile, which is enough because each of them names a profile.
  - **Sign-out follows no replacement.** The folder is isolated exactly as for a removal (checked, last look, renamed to `.working-<16 hex>`, re-checked), `claude auth logout` runs with `CLAUDE_CONFIG_DIR` pointing at the renamed folder, the folder is verified again before the backups are deleted, and the name is put back (only if it is still free). The renamed folder is looked at before the PowerShell inspector is asked, again after it has answered, and again after the walk of its contents: the real path of the folder above and of the folder itself, that it is not a link, and that it is the same file system object (device, index, creation time) as the folder that was taken, so an answer given about the real folder cannot be used for a junction that took its place while the answer was on its way. A folder replaced by a junction to the Windows user's own sign-in after the checks is found before anything is run or deleted. If the name cannot be put back, the person at the computer is told in the Runtime window and `agend-runtime profile list` names the leftover folder (`.working-*` or `.removing-*`); nothing deletes or restores it by itself.
  - **A process that was told to stop is not assumed gone.** For a sign-in child and for the logout, only the child's `close` is evidence that it ended; an `error` event from a child that exists is not (Node also emits it when a kill fails). A logout that is not confirmed ended 5 seconds after the tree was killed keeps its profile busy (and its working name) until the process really ends. A sign-in child that cannot be confirmed gone keeps the sign-in slot and its scratch folder, and every later start tries to end it again. **Stopping is not complete while such a process exists**: `RemoteAccounts.stop()` and the Runtime's `stop()` fail with `Account process shutdown was not confirmed`, the pairing's lock is not let go, the account module is not thrown away, and a restart (or a second client on the same pairing folder) is refused; calling `stop()` again tries again and succeeds once the process has really ended (the foreground `agend-runtime run` says so and takes Ctrl+C again).
  - **Reserved while it changes.** While a sign-out, remove or sign-in start of a profile is under way, a task or terminal that would run under that profile (named, or through the pairing default) is refused with a message to try again; a terminal that is still being opened counts as using its profile until the pane host has answered. A default profile that cannot be read is `unconfirmed` for a remove, never "no default". The local administrator's `profile default` (and `connect --credential-profile`) is written by another process, so there is no lock; the two sides check each other instead. The removal reads the default just before the rename and again after it, before the delete (a default set in between puts the folder back and refuses the removal, `unconfirmed` if the default cannot be read). `agend-runtime profile default` looks at the profile folder again immediately before the write and once more after it: a profile that was taken away in between (a removal renames the folder first) puts the default back as it was and the command fails with a message. Of the two, one always notices the other.
  - **`accounts.check` is bounded.** At most two run at a time on the computer, a profile that is being changed answers `busy`, and the refusals are made before PowerShell or the CLI is started.
  - **One operation at a time per profile.** Sign-in, sign-out and remove of the same profile (by lower-case name) cannot overlap: the second is answered `busy`.
- **Sign-out** runs `claude auth logout` for the profile and deletes `backups\.claude.json.backup*` in it, then confirms with `auth status`. **Sign-out and remove are refused** (not queued) while a task or terminal runs under the profile, while a sign-in for it runs, and while another operation on it is in flight. A terminal counts when it is not exited in the pane host's ledger (`pane-host\state\panes.json`, or `panes\panes.json` for an in-process host); a Claude Code terminal that names no profile counts as using the pairing's default. A row recorded under an earlier boot of the computer cannot still be running and does not count (the pane store treats it the same way after a restart). If the ledger, or the default profile a terminal needs, cannot be read, the answer is `unconfirmed`: the request is refused with a message that says this computer could not confirm the state of its terminals and sends the person to that computer, not a message that claims a terminal is running.
  - **At least 5 seconds between two sign-outs or removes of one profile** (by lower-case name; a request refused for another reason does not start the wait): the answer is `rate_limited`. This only slows a server that keeps asking. **The risk that remains, stated plainly:** while the accounts switch is on, a compromised AgEnD server can still sign a Runtime-created profile out again and again (and, once, remove it). The computer's local administrator accepts that when turning the switch on and choosing how long it stays on (`--for`); the rate limit and the switch's time window bound it, they do not remove it. **Remove** is also refused for the pairing's default profile (only the Runtime knows it). **Sign-out of the default profile is allowed**, which is the difference between the two.
- **Record.** Switch changes name the switch (`accounts` or `install`), on or off, and the end of a timed one (`until`), as `started` then `ok` (or `failed`, never `ok` for a change that was not made); turning a switch on whose result line cannot be written puts it back off, and says "turned off again" only when the saved switch reads back as off; if the rollback cannot be shown (it failed, or the file still says on) the command says `unconfirmed` (the switch may still be on), records `failed` with reason `unconfirmed`, and names the command to run. Every record is written whole: a short or empty write is an error, and what was written of it is cut back. Before each record the end of the log is looked at: the front of a record that an interrupted write left (no newline; it begins the way every record begins) is cut off; a tail or a last record that is not ours or not JSON is refused, so an operation that needs its record does not go ahead on an unreadable log and no accepted record is ever glued to a partial one. One writer at a time, and every supported writer takes the lock: the look at the end of the log, the repair, the write and the taking back of a failed write all run under a lock file in the same folder (`audit.lock`; it holds the process id and a token, and is removed only if it is still that writer's). The lock of a live process is never taken; a writer that cannot have the lock within a few seconds refuses, so its operation does not run, and it never repairs, cuts or writes without it. Recovery is deliberately small and conservative. Only a lock that names its owner (readable pid and token) whose process is gone is taken over, and only without contention: the taker creates `audit.lock.reclaim` exclusively, looks at the lock again (it must still be the very file that was seen to be stale: same file, same bytes), writes the new lock whole to a file of its own and renames it over the old one. Nothing is ever unlinked to make room: if the rename fails the takeover fails. Everything else is waited for and then refused, and left for someone to look at on this computer, never cleared automatically: an `audit.lock.reclaim` that is already there (its taker may be alive, or it died there), and an `audit.lock` that holds nothing readable, however old (its creator may only be slow). A writer that is refused this way says so (`audit.lock` or `audit.lock.reclaim` in the pairing's folder); after checking that no Runtime or `agend-runtime` command is running, remove the file named. A writer checks that the lock is still its own, as the last thing before any cut and before the write, and a writer that finds it has lost the lock stops there: it does not cut, and its operation does not run. A cut is also made only on an end of the log that no other writer has changed since it was looked at. Operations that change something are appended to `audit.jsonl` in the pairing's folder, before and after: a switch change (`local`), a sign-in start and its end (signed in, failed, timeout, switch off), the creation of a profile, the submission of a sign-in code (`signin.write`; who, when, which profile; never the code), sign-out, remove and install. `accounts.check` and the screen reads only read, and are not recorded; `accounts.switches` and `signin.close` are described above. The line is built from a closed set of fields, so a link, a code, CLI output, a folder listing or an e-mail cannot be written. If the record of a remote operation cannot be written, the operation does not run; turning a switch **off** works regardless (the record is then best effort and the person is told).
  - **Refusals are folded.** A refusal that repeats within a minute is not written again; it is counted, and the count is on the next line of its kind (`repeated`), or is written when the next real operation starts. **The folded line carries the actor, profile and CLI of the first request of that run only; the requests counted in `repeated` may have named other actors, profiles and CLIs. `since` (a UTC ISO time) is where the folded run began; `at` is when the line was written.** A count that has not been written when the Runtime is killed (not stopped) is lost; that is accepted, because the first refusal of every window was already written. The key is the action and the reason only, never the actor, profile or CLI, which the server chooses. This only holds because every refusal that changes nothing is made *before* `started` is written: a request is first checked (switch, one operation per profile, then the operation's own checks: its form, ownership, in use, a free sign-in slot, the CLI being there, a wrong or repeated code, a closed table) and only a request that will really do something leaves a `started` line. `signin.write` follows the same rule, so a flood of wrong codes folds into a line or two. Five rotated copies of about 1 MiB are kept. Started, ok and failed entries and switch changes are never folded, so the most refusals can add is one line per (action, reason) per minute, and a flood of requests cannot push real operations out.
  - **`actor` is what the server says.** The Runtime cannot check it: a compromised server can put any value there. The record shows what a server asked for and what the computer did; it is not proof of who sat at the dashboard.
- **Codex.** Not offered on a computer yet. Codex can keep its login in the Windows Credential Manager (`cli_auth_credentials_store`) instead of a file in its home folder, which a profile folder can neither hold nor remove, so signing out or removing a Codex profile would leave the login behind. Every operation refuses Codex with that reason until a Windows check shows where it keeps its login and a profile can be confined to a file.

## Managing a computer's accounts from Settings → Accounts (remote setup, 3c)

With the **accounts** switch on (`agend-runtime remote-setup accounts on --for 2h`), a fleet administrator manages that computer's Claude Code accounts in **Settings → Agents → Accounts**, under **On <computer name>**: **+ Add account**, **Sign in**, **Sign out…** and **Remove…**. This is the same view, dialogs and sign-in implementation as for the host ([web dashboard](web-dashboard.md#settings)): a computer is more rows under the `machine` scope, not a second screen, and the sign-in is `StructuredSignIn` with the computer's Runtime as its transport. See the Runtime side above for what each operation does there.

- **What the server asks, and nothing else.** A CLI id, a profile **name**, the method (`subscription` only) and the asker's audit name (`admin:<session handle>`, never a label or an address), in `account.request` / `account.response` frames: the coordinator's `callAccount`, which keeps the call in memory and never writes it or its answer to the journal. The server sends an `account.request` only to a Runtime that reports `remote-signin`; it never sends an argv, a command, a path or an environment. The sign-in reaches the Runtime as `signin.start`, `signin.capture`, `signin.status`, `signin.write` (one code) and `signin.close`.
- **Who may ask.** Only the fleet's local admin session on the dashboard reached directly, checked before the request body is read and again after it, with CSRF: not a guest, a read session, the CLI's header token, the public link or the gateway. The same routes as the host's carry a `machine` (a paired computer's id): `POST /ui/accounts/<cli>` `{ name, machine }`, `DELETE /ui/accounts/<cli>/<name>` `{ confirm, machine }`, `POST /ui/accounts/<cli>/signout` `{ profile, confirm, machine }`, and the sign-in controls at `/ui/browser-backend-signins?machine=<id>&profile=<name>`. An older Settings tab sends none of these and still works.
- **What the rows say.** The computer's Runtime reports each profile with whether it **created** it (its own `created.json` record; a Runtime that does not say is treated as "not known to be ours"). Only such a profile is offered Sign in, Sign out and Remove. A row that cannot be changed carries the reason as a code in `scope.readOnlyReason`, which the page words: `offline`, `runtime_old`, `accounts_off` (the owner's switch, read from the computer and cached for a few seconds), `switch_unreadable`, `not_installed` (for the whole computer), `not_created` and `default_login` (for one row). Each says what to run on that computer. The Windows user's own sign-in is read-only: no Sign in, Switch or Sign out. There is no usage on a computer's row.
- **One sign-in at a time per computer**, under that computer's own `LoginWindowLock` (the Runtime also enforces its own limits: one at a time, 5 seconds apart, 12 an hour, ten minutes). The same profile joins; another is `machine_busy`. A close that cannot be confirmed (the computer went offline) keeps the computer reserved and is retried by the next start, which succeeds once the Runtime says that sign-in is no longer running.
- **Remove** is refused before anything is sent while an agent on that computer uses the profile, while it is the computer's default, and while a dashboard sign-in for it runs; the Runtime then checks its own side (a running task or terminal, the pairing's default, ownership, no link at any level) and deletes its own folder. **Sign out** runs the CLI's own logout there and deletes the profile's backups. A computer's refusal is shown as the Runtime's own sentence (bounded, no control characters).
- **The answer comes after the inventory it changed.** A Runtime that has signed an account out, removed one, checked one or made a new profile sends its new inventory over the same connection before it answers (the answer waits for it, as long as the switch is still on and the connection is still the live one), so the Accounts view that reads the inventory on the answer sees the change. As a second guard the server applies a just-finished sign-out or remove to that computer's rows until the computer's next inventory arrives, which then is the truth again. A removed profile is `missing` at once, not a second request.
- **Not logged, not stored.** Neither the fleet log nor the computer's audit record ever holds a sign-in link, a code, the CLI's output, a folder path or an e-mail address; the fleet log has the computer, the profile name, who (the session's label), the action and the outcome. A name that passed the dashboard's checks in + Add account is logged as `add_checked`, not `added`: the Runtime makes the folder only when the first sign-in starts. The link and code are shown only to the admin session that started the sign-in.
- **Not in this version.** Codex on a computer (after #3212 PR 4 and a Windows check of where Codex keeps its login), Anthropic Console sign-ins (use `agend-runtime login claude-code NAME` on the computer), Move agents and Switch account on a computer's rows, and `profile adopt`.

## Installing a CLI on a computer from the dashboard (remote setup, 3b)

With the **install** switch on (`agend-runtime remote-setup install on --for 2h`), a fleet administrator can press **Install** on a paired computer's card in Settings → Runtime. It is off by default and only that computer's local administrator can turn it on; the dashboard can read the switch but never change it. A Runtime reports `cli-install` only when it has an installer (native Windows on x64; Windows on ARM is not supported by this version); an older one is told to update.

- **Claude Code and Codex only.** The server sends a CLI id. The package, the **exact version**, the registry (`https://registry.npmjs.org/`), the argv and the folder are written in the Runtime (`runtime-cli-install.ts`). The version and the registry hashes of its packages are one entry of one table, so they only change together; the version is a fixed pin for integrity and is not tied to the persistent-terminal version list. Grok, Antigravity and Kiro are not installed from the dashboard: they ship as vendor PowerShell scripts (or an MSI that needs an administrator) whose content cannot be pinned, so the dashboard shows each official command for the computer's owner to run.
- **Per user, no administrator, no PATH change.** `node.exe npm-cli.js install <package>@<version> --ignore-scripts` with no shell, into `<pairing folder>\cli\<id>\<version>`. No global npm, no vendor script. npm reads no user or global configuration: it is given two controlled `.npmrc` files in the staging folder (`--userconfig`, `--globalconfig`), `--global=false`, `--prefix <staging folder>` and the official registry, on the command line and in its environment, so a `global=true`, a `prefix=`, a scoped registry or a token in the user's own `.npmrc` can neither move the install out of the pairing folder nor send it elsewhere. The child environment is an allowlist (Windows basics, proxy and certificate settings); no fleet secret reaches it.
- **Four checks, all required before `current.json` moves** (atomically): npm's own integrity check; the registry sha512 of every package, written in the Runtime; `npm audit signatures`; and the Authenticode signature of the native binary, whose certificate subject must have a CN and an O that are each exactly the expected name (`Anthropic, PBC` / `OpenAI OpCo, LLC`; a name that merely starts with it, or a right O beside a wrong CN, is refused). Any failure leaves nothing switched. A version that is already installed is left untouched, and a request for it is refused before anything is recorded as started (`rate_limited`, folded with its repeats in `audit.jsonl`), so a coordinator that keeps asking cannot push real operations out of the log; the same CLI is also tried at most once every 5 seconds. Replacing an install moves the old folder aside as `<version>.old`, puts the new one in place, then deletes `.old` (a failed delete is ignored and cleared at the next install); if the swap fails, the old folder is moved back and `current.json` is not touched. After a switch, the other versions of that CLI and the npm cache are removed on a best-effort basis. A link where the Runtime is about to write is refused. There is no uninstall yet.
- **The Runtime finds it first.** `findCli` looks in `<pairing folder>\cli` before the PATH (the folder is passed to the helpers through `AGEND_MANAGED_CLI_ROOT`, an allowlisted Windows-path variable). A pointer for another version than this Runtime pins is not used.
- **One at a time, one overall 10-minute deadline for all steps together (npm install, signature audit and publisher check), stopped with the Runtime.** The deadline ends the install as `timed-out`; the Runtime stopping ends it as `cancelled`; npm output beyond its size limit is `install-failed`. AgEnD's own wait is 11 minutes, longer than the Runtime's. A second install is refused (also when two requests arrive at the same moment, and while the first request is still waiting for the Runtime's first answer); failures are typed (`npm-missing`, `install-failed`, `timed-out`, `integrity-mismatch`, `signature-check-failed`, `publisher-mismatch`, `cancelled`) with sentences that carry no path, URL or npm output. The dashboard shows the job as installing, done or failed; it does not show the individual steps.
- **The switch and the connection are looked at again at every effect.** The install switch (still on, not run out) and the connection the request arrived on (still the live one) are checked before npm install, before `npm audit signatures`, before the publisher check and again in the same synchronous step as the folder swap and the pointer write. A change while a step runs stops the next one (that step's own process is not abandoned: it is waited for and its lock released as above), nothing is activated, and the Runtime's own sentence and reason (`switch_off`, or `failed` for a connection that changed) are the ones recorded.
- **Containment holds while it runs.** The CLI folder, the id folder and the staging folder are admitted before the wait for the shared lock (their identity is taken then, and checked again straight after the wait, before anything is written: an id folder that appeared during the wait is not adopted). Their identity and place are checked again after every wait and before every write, rename, removal and the pointer write; one that was replaced by a link or another folder stops the install and is never written, renamed or deleted through. Looking for the installed program refuses a CLI folder that is itself a link, not only links inside it.
- **A finished install is visible at once.** When an install succeeds the Runtime detects again for real (not from its cache) and sends that inventory before it answers, so the dashboard shows the new CLI and version without "Detect again". That detection starts programs and writes the status cache, so it is asked, before each probe and each profile status and before its cache write and its inventory, whether the install switch is still on and the request's connection still the live one; withdrawn consent stops it, including after the CLI lookup and before a profile's status program is started (the finished install is still answered).
- **The shared install lock, held until every child process has really ended.** Before it starts, an install takes the Runtime install lock of #3258 (`acquireRuntimeInstallLock(<lock root>, { type: "installer" })`, the `.agend-runtime-install.lock` folder that `install.ps1` and the update supervisor also take); there is no second lock of its own. The lock root is the managed Runtime install root the code runs from (`<root>\<version>+<sha>\dist\…` with `<root>\bin\current.txt` or the install receipt), else the CLI folder for a ZIP copy. Inside the lock it writes an `inflight` marker; the lock, the marker and the staging folder are released only after the last child process (npm, the signature check) has been confirmed ended by its `close` event, so a connection that drops or an AgEnD deadline that passes does not free it. When the install is stopped (the 10-minute limit, the Runtime stopping, too much output) the whole process tree is killed and its `close` is waited for up to 5 more seconds; if it has still not come, the install ends with its reason, the Runtime stays non-idle (an update is deferred, never forced) and a new install is refused, until the process really ends. A Runtime that dies with a child still running leaves the marker behind: the next owner sees an uncertain lock and refuses (a lock with anything beside its owner record is never reclaimed). The lock is checked again before the npm steps, the publisher check, the folder swap and the pointer write; a changed lock stops the install and puts the old install back. A lock held by an update, a reinstall or another Runtime makes the install `busy`, with nothing written. The folder the lock lives in (the CLI folder itself when there is no separate install root) is looked at before the wait for the process observation and after each such wait, by the installer and by the lock module itself: one that was swapped for a link or another folder stops the acquisition before the lock folder, its owner record or the marker is written through it. A release is only ever skipped on positive evidence that the lock is not ours any more: the lock folder is gone from that very folder, or a complete, valid owner record of another owner (read without following links) is in it; an unreadable, partial or linked record, or a folder replaced by an empty one, keeps the lease and the Runtime busy.
- **A refusal that comes back at once is an error, not a job.** After sending the request, AgEnD waits up to 1.5 seconds for the computer's answer. If the computer refuses in that time (its install switch is off, the CLI is not in its table, it is offline), the request answers 400 with the computer's own sentence and leaves no job (an earlier job is shown again). If nothing has come back by then, the request answers 202 and the page follows the job.
- **Not stored by AgEnD.** The request travels as `account.request` through `RuntimeCoordinator.callAccount`, kept in memory only: no journal write, no file, no log of the payload or the answer. The install job the page follows is also memory only.
- **Who may ask.** A local administrator session only (the same people as for seeing an account): not a header token, guest, public link, outside administrator or an agent. The name in the computer's `audit.jsonl` is an opaque session handle (`admin:<16 hex>`).
- **Not done here:** uninstall (delete `<pairing folder>\cli\<id>` by hand), update (a new AgEnD release moves the pin), Codex sign-in.

## Private state and removal

The default local profile is `%USERPROFILE%\.agend-runtime`; `--profile DIRECTORY` or `AGEND_RUNTIME_HOME` selects another private profile. `connection.json` contains the permanent machine credential, and `jobs.json` contains bounded result snapshots and argument hashes. The runtime does not save a separate input-prompt field or provider login credentials in that journal. A CLI result can quote its input, so treat result snapshots as private too. The CLI itself may retain its ordinary local conversation history.

Windows checks the profile before reading its state, including a custom `--profile` / `AGEND_RUNTIME_HOME` directory. POSIX mode bits do not enforce Windows privacy. A new directory is created with an ACL for the current Windows user and SYSTEM only. An existing profile is checked without changing any existing ACL: its owner and its files’ and subdirectories’ access grants must be limited to that user, SYSTEM or local administrators. Windows may use Administrators as the default owner of files written by an elevated process; this uses the same trusted-principal set, without allowing another ordinary user or service account. Reparse points, broadly shared children, an unreadable ACL, or an ancestor that another ordinary Windows account can replace cause a refusal before state is read. Parent ACLs and unrelated files are never rewritten.

The check visits at most 20,000 entries and takes at most 25 seconds (the PowerShell process has a 30-second deadline). A large or slow profile can therefore be refused too. Use a new dedicated directory, or have its owner review and restrict the existing profile's permissions; do not point `--profile` at a whole home directory or shared work folder. An older shared profile is refused rather than silently hardened or copied. These checks do not isolate the Runtime from the same Windows user, SYSTEM or local administrators. **The machine credential is not encrypted.** Do not share or synchronize the profile. Existing CLI authentication files and profile ownership/removal markers are not modified.

```powershell
.\agend-runtime.cmd status
.\agend-runtime.cmd disconnect
```

`status` lists every profile on this computer with its state, process, AgEnD address and autostart, without the credential or prompts (`status --json` adds machine identity and job states). `disconnect` stops the profile's background Runtime first (a Runtime in a window must be closed by you), forgets the local connection and removes that profile's sign-in task. To invalidate a credential centrally, **revoke the machine in AgEnD Settings**. Revoke rejects new runtime connections and closes an existing connection. Local process shutdown remains subject to the explicit completion/cancellation rules above.

**On the AgEnD side**, the machine journal (`runtime-machines.json` in the AgEnD data folder) keeps only SHA-256 hashes of pairing codes, claim secrets, machine credentials and install-command tokens, plus the bounded token audit trail. The server's enrollment key lives in `runtime-server-identity.json` beside it (private, mode 0600); it is created the first time a one-time install command is made. Keep it with your AgEnD data: if it is lost or replaced, commands already handed out stop working (they are refused as "for a different AgEnD") and a new command has to be made. It is not a login credential and is never sent anywhere; the fingerprint is its public hash.

## Rotate a machine credential without pairing again

Stop the Runtime (**Ctrl+C** in its window, or `agend-runtime stop` when it runs in the background), then, in the same extracted Runtime folder and under the same Windows user, run:

```powershell
.\agend-runtime.cmd rotate
.\agend-runtime.cmd start
```

Pass the same `--profile DIRECTORY` to both commands if you use a non-default profile. A profile that a connection-ready ZIP created under `profiles\<host>-<port>` is found automatically when you run the commands from that folder. Rotation refuses while that profile is in use; it never stops an execution automatically. It keeps the machine identity, approval, inventory and job journal. Once the coordinator commits the rotation, the previous credential can no longer connect. Neither credential appears in command arguments or status output.

The replacement is saved privately in `connection.json` before the request. If a response is lost or the final local save fails, keep the profile intact and retry `rotate`, or use `run` to finish the saved rotation before connecting. `status` reports `rotationPending` without the credential. Do not downgrade or delete the saved candidate while rotation is pending. A revoked machine cannot rotate itself back into authorization. Anyone holding the current credential can request a rotation, so rotation is not recovery from credential theft; revoke a compromised machine.

Valid pairing codes, claims and rotations have independent rate-limit buckets even when a proxy or SSH forward makes every connection appear to come from loopback. Invalid traffic has a separate bounded bucket; forwarding headers do not grant identity or bypass limits. The comparison fingerprint is not a password or a replacement for HTTPS and administrator approval.
