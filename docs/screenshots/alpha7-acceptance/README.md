## Guidance and findings

The exercised Claude account flow uses the private browser terminal and local provider page, rather than a host-command instruction. Membership, join, publication and grants finish in web pages in both fleet kinds. Chat and remote/runtime paths outside that coverage are not implicitly approved.

Known allowed/parked leftovers are unchanged in classification: paired-PC/remote guidance (#3333), bootstrap host-issued web access, folded Advanced CLI confirmation, and the remaining Batch B inventory. The current phone Accounts page still offers Antigravity “Sign in from chat”; this run does not claim that backend's web sign-in is implemented.

New P3 [#3385](https://github.com/songsid/AgEnD/issues/3385) (legacy option): Settings → Chat & connections → Telegram → Access mode still offers raw `pairing` alongside `locked` and `open`, with no explanation in EN or zh-TW. #3358 intentionally keeps saved `pairing` as a locked/allowlist-only compatibility alias; there is no remaining enrollment-code flow. The phone PNG selects the option only to expose its label, then cancels without saving it. This is a misleading legacy choice, not a P2 broken enrollment path. The child issue is linked above.

New P3 [#3386](https://github.com/songsid/AgEnD/issues/3386) (stale status): both Connected/Online screenshots retain “Sent for confirmation: confirm it in General's chat or Settings to share it.” after joining succeeds. Navigating away and back clears it. This suggests another confirmation is needed even though the fleet is online. It does not prevent the subsequent grant or chat. The separate child issue is linked above.

No new P1/P2 issue was found in the fresh Pass 2 flows. Existing #3332/#3333/#3334 remain limitations for the release decision, rather than being converted into passes. The #3370 first-sign-in blocker is resolved on the exact candidate in both fleet kinds.
