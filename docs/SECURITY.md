# Security Considerations

Running coding agents remotely through Telegram or Discord gives chat participants a way to request actions on the host. AgEnD's chat permissions, MCP tool permissions and HTTP credentials protect different entry points; they do not sandbox the coding CLI.

Paths below use the default data directory, `~/.agend`; `AGEND_HOME` can select another directory.

## Threat model

AgEnD defends against:
- remote parties;
- other users of the same computer (other OS accounts);
- visitors over the public link or gateway;
- web guests;
- cross-site requests (CSRF) from other pages in the owner's browser.

A process running as the **same OS user as the fleet** is treated as the owner (fleet decision 64a289a0, #3327). Such a process can read `~/.agend/web.token`, edit `fleet.yaml`, read credentials and run the CLIs directly. Blocking it on one HTTP route would give no real protection. Use a separate OS user, or an isolated container, for anything that must not have the owner's authority.

Inside that model, AgEnD still keeps sensitive steps on the human path, as defence in depth, without adding clicks:
- **The host's sign-in code:** `/auth/issue-code`, which is what `agend web` uses, answers only a direct request from this computer: a loopback peer and a loopback Host, with no forwarding header. The web token used from elsewhere, or through a proxy, cannot mint a dashboard session. You can still type the printed code into a browser anywhere.
- **Pairing a computer:** creating a pairing code and approving a computer take an administrator session on the directly reached dashboard, with its cookie and CSRF value. These are the page's own **Connect a computer** and **Approve computer** buttons. The bare `X-Agend-Token` header is refused.
- **Joining a computer with an install command (no approval):** the **Connect a computer** page can also issue a one-time install command that joins a computer with **no approval step**. Issuing and revoking one take the same administrator session as pairing. The token is 256 random bits, valid for 15 minutes and one use, and AgEnD stores only its hash. See [The risk of an unused install command](#the-risk-of-an-unused-install-command) below.
- **Turning remote runtimes on:** this is a held Settings change, which the bare token cannot request.
- **On a web-only fleet:** the host operator is the owner (decision 28c2d3a3). Setting the authenticator up again, or removing it, is announced in Notices, so a change the owner did not make is noticed.

## The risk of an unused install command

Pairing with a code needs a person to compare a fingerprint and press **Approve**. The one-time install command (Settings → Runtime → Connect a computer, the page's default) deliberately does not: whoever **runs it first** joins a computer, at once, with no approval. The maintainer has accepted this residual risk, in these terms:

- **Possession is the authority.** An unused, unexpired command is a bearer credential. Anyone who obtains it before it is used, expires (15 minutes) or is revoked can enroll **an endpoint they control** as one of this fleet's Runtimes. The enrollment returns a **permanent machine credential**; agent work sent to that computer (prompts, code, repository access the agent has) goes to them. The token is bound to **this fleet** (the command carries this AgEnD's server fingerprint), not to a particular computer: it works from any computer that can reach AgEnD.
- **What it does not give.** It does not mint a dashboard session, grant administrator rights or a tool permission beyond what any Runtime has, and it does not touch other Runtimes. There is **no quarantine**: the new computer is usable immediately.
- **Where a command leaks.** Chat and AI-agent conversation logs, screenshots, PowerShell's PSReadLine history (`ConsoleHost_history.txt`, which keeps the pasted text), script-block logging and transcripts, and, when an agent or CI step runs it through an outer `powershell -Command "<command>"`, that **outer** process's command line (process list, Windows process-creation event 4688 with command-line auditing, script-block event 4104). The Runtime's own command line never holds the token. Treat the command like a password: do not paste it into chats, tickets or screenshots.
- **What limits it.** 15 minutes, one use (a used, expired or revoked token is refused; a second use never joins anything), hash-only storage, a new command ends the previous unused one, the page's **Revoke and close** ends it at once. The token goes to the Runtime only after it has checked AgEnD's Ed25519 identity against the fingerprint in the command, and it travels encrypted (X25519 + AES-256-GCM): this pins AgEnD's identity and stops a relaying server reading it; it does **not** replace TLS validation.
- **The owner is told.** When a computer joins this way AgEnD sends a notice to the owner (the computer's name and host, the token's id, and how to revoke), through General or the primary channel, or the dashboard's Notices on a web-only fleet. The notice is **kept on disk first and removed only when a delivery is acknowledged** (the platform accepted it, or the dashboard's Notices wrote it to disk: a Notice held only in memory, a failed file write, or a native General's status line, which has no receipt, does not count): no destination yet, a send the platform refuses (also on a retry) and a restart do not lose it, and it is retried every minute. If more than 100 notices are undelivered at once, the oldest are folded into **one** notice that says how many computers joined, never silently dropped. Delivery is at least once. The Runtime page also announces it and offers **Revoke**, and every issue, use, revoke and refused attempt is in the audit trail (addresses masked).
- **Two different revocations.** Revoking an **unused token** (Revoke and close, or a new command) stops anyone from using it. It does **not** undo a computer that has already joined: for that, **revoke the machine** (Settings → Runtime → the computer → Revoke connection), which removes its credential and closes its connection at once. It does not promise to end processes already running on that computer or to erase its local credential file.
- **Background autostart.** After a Runtime connects it moves to the background, and the first background connect adds a per-user sign-in scheduled task (limited token, no password, no elevation, not a service), **on by default**, so a connected computer reconnects at each sign-in until it is revoked or `agend-runtime autostart disable` / `disconnect` is run there. Closing a window does not disconnect it.

Details and operating guidance: [The one-time install command](remote-runtime.md#the-one-time-install-command-no-pairing-code-any-computer-ai-agents) and [Running in the background](remote-runtime.md#running-in-the-background).

## Chat access and administration

An admitted user can ask an agent to read files, change code or run commands, subject to the backend's permissions. Treat those users, their accounts and any admitted bots as trusted with the agent's workspace and host access.

- Use an explicit `access.mode: locked` and a small `allowed_users` list to restrict fleet chat access. **Omitting the entire `access` block falls back to open.**
- Persisted access mode overrides YAML; persisted and YAML user lists are unioned. Removing a user from YAML alone may not revoke access. See [configuration](configuration.md#channelaccess).
- Fleet administration requires an explicit entry in the target instance’s owning adapter's YAML `allowed_users` (the invoking adapter when there is no target). Open access or a saved chat grant alone does not grant that role. ClassicBot has its own admin and chat allowlists; see [permissions](permissions.md).
- Enable account 2FA and protect bot tokens. `tool_set` is enforced on AgEnD operations at the server; it does not restrict the backend's own shell, filesystem or network tools.

## Permission bypass (`skipPermissions`)

For Claude Code, **bypass is enabled by default**: AgEnD passes `--dangerously-skip-permissions` unless `skipPermissions` is explicitly `false`. The flag bypasses Claude's tool permission prompts, so an admitted chat request can lead to host actions without an individual approval.

Set `skipPermissions: false` to omit that flag and use Claude Code's own permission configuration. AgEnD does **not** generate a shell allowlist or a destructive-command denylist. Configure restrictions in the CLI's supported user/project settings, and use OS isolation when you need a host boundary.

The per-instance `claude-settings.json` is generated again on startup (including the status line and bypass-warning acceptance when applicable). Do not use edits to that generated file as a persistent security policy.

## Tool profiles and the shared host account

`tool_set` is policy protection for the instance identity resolved by AgEnD. It
refuses disallowed operations on that identity across MCP, direct IPC and the
agent HTTP endpoint. It is **not a security boundary against a shell-capable
agent running under the same uid**. Such an agent can read a sibling's
`agent.token` or connect to its `channel.sock`, claim the sibling's identity and
receive that sibling's permissions, including a coordinator's. A `0600` file
does not distinguish processes belonging to its owner. Per-spawn rotation does
not change that fact. Treat same-account agents as mutually trusted; use separate OS users or
properly isolated containers for agents that must not share authority.

## IPC socket

The daemon communicates with the AgEnD MCP bridge over `~/.agend/instances/<name>/channel.sock`. AgEnD uses a restrictive umask and attempts to set the socket to `0600`. It creates private instance directories with `0700` and tightens eligible existing directories. There is **no shared-secret handshake**. These filesystem permissions separate Unix users; they do not authenticate or isolate processes running as the same UID, or protect against root. Check warnings when permissions could not be restricted.

## Dashboard sign-in and browser sessions

Two credentials open the local gated dashboard routes, and neither ever travels in a URL:

- **`X-Agend-Token`**, the fleet-wide bearer token in `~/.agend/web.token` (created with mode `0600`; permission tightening on an existing file is best effort). The CLI and scripts send it as a header. It persists across fleet restarts. `agend web-token rotate` replaces it, which also signs every browser out (see below). Rotation is not a promise to retract an already authorized request or close every existing connection.
- **A browser session**, made by signing in with a **one-time code**. A fleet admin gets the code with `/web`: the General menu sends it only by DM, with an awaited Discord ephemeral fallback; Telegram DM refusal asks the admin to `/start` the bot privately. On the host, `agend web` prints one, using the header token. A code is 8 characters, works **once**, expires after **5 minutes**, and only the newest code works. The first code `agend web --code` prints to an interactive terminal before a host session has **ever** been authorized on this fleet (a new install — a persisted marker, so signing out or expiry never brings it back) lasts **60 minutes**, counted from the first one, instead (#3270): it can be redeemed from this computer only (never over the public link, from a LAN host name or through a forwarding proxy), and it stops working as soon as the first host session exists. It is printed to the terminal that asked for it and nowhere else: never to a pipe, a redirect, an install log or a service's journal (`agend web` says whether its stdout is a terminal; a caller that does not say gets the ordinary 5-minute code), and the fleet never logs a code. It is never issued on WSL, where the user's Windows processes reach the fleet as loopback and can read the distro's files. On WSL, and once the first hour is over, every code is 5 minutes. `agend web` opens the browser through a `0600` launch file in the AgEnD home (created with `wx` in a `0700` directory, deleted after two minutes) that redirects to `/signin#code=…`, so the code is in no process's command line; a code that goes into a URL always keeps the 5-minute lifetime. The terminal also always prints the clean address and the code, because a browser installed as a Snap or Flatpak cannot read a launch file under a hidden directory of the home folder: open the address and type the code. The fragment never reaches the server; the sign-in page removes it from the address bar before making any request, and exchanges it only on `localhost`, `127.0.0.1` or `[::1]`, on a fresh navigation, in a browser with no session. Five wrong tries spend a code (a wrong try from off this computer never spends a bootstrap code). Twenty wrong tries within 15 minutes, across codes, pause all redemption for 5 minutes. While no code is outstanding there is nothing to guess. Local sign-ins are announced in General (`web.notify_login`, on by default); public sign-ins require a confirmed notice regardless of that setting.

A `?token=` in a URL is **not** a credential, including in old links and bookmarks. It gets the sign-in page, and the token is removed from the address bar.

About the session:

- The cookie is an opaque random 256-bit id, unrelated to `web.token` or to the code. The server's session records keep only its SHA-256, persisted in `~/.agend/web-sessions.json`, so a stored record or that file cannot be replayed as a cookie. The raw id still passes through the process: when the session is created (the `Set-Cookie`), and in every request that carries the cookie. At most 8 sessions are kept; past that the least recently used one is dropped.
- The **server** enforces the expiry: by default 48 hours after sign-in, or 48 hours without use, whichever comes first (for the dashboard reached directly, `web.session.local.*` can set them between 1 and 720 hours; a public-link session's limits are fixed; a shorter setting also ends existing sessions it now outlives). Use is what the person does: opening a page, reading a chat's history, any change. The reads a page makes on its own timer are authorized in full but are not use: the dashboard's live stream (`GET /ui/events`, also when it reconnects) and its fallback poll (`GET /ui/poll`), and, with `web.view_access: session`, `/view`'s terminal (`GET /api/pane/<instance>`), roster (`GET /api/profiles`) and usage panel (`GET /api/ai-usage`). The server fixes that list by method and path; a request cannot declare itself passive. So a tab left open does not keep its session alive (#1373). The cookie's `Max-Age` only tells the browser to forget it at the same time. Sessions survive a fleet restart.
- The cookie is `HttpOnly`, `SameSite=Strict` and `Path=/`. On the local listener, when `X-Forwarded-Proto` reports HTTPS it is named `__Host-agend_session` and is `Secure`; use TLS for remote access. Managed public cookies are always Secure, based on the listener-owned context, not a forwarded header.
- **A write authorized by the cookie** must also carry an `Origin` equal to `Host`, a `Sec-Fetch-Site` of `same-origin` when the browser sends one, and the session's own `X-Agend-CSRF` value. The cookie alone cannot change anything. A local header-token request is exempt from cookie CSRF and Fetch-Site checks and may omit Origin. If it supplies Origin, that Origin must still match Host; a page cannot make a browser add the token header.
- On every gated route, an `Origin` whose host/port differs from `Host` (or that does not parse, such as `null`) is rejected. A read without `Origin` is accepted when its credential is valid.
- **Revoking:** the Session menu signs out one device or every device, `/web revoke` signs out every browser and withdraws any unused code, and `agend web-token rotate` ends every session made under the old token on its next request, without a restart.
- **Returning devices (#1570).** A sign-in with a code that `/web` delivered privately also sets a second cookie, `agend_device` (`__Host-agend_device` on https and on the public link; `HttpOnly`, `SameSite=Strict`, 90 days). Its value is a random 128-bit id plus an HMAC keyed from `web.token`; it names no chat or user. `~/.agend/web-devices.json` (`0600`) keeps the id's SHA-256, the owner who received that code, and the token epoch. Only such a browser can ask the sign-in page for a fresh code (`POST /auth/request-code`, which requires `Origin`). The fleet then re-checks that the owner is still a fleet admin of that bot and General, and sends the code by DM only (never a group, no fallback). The DM names the browser and the surface. Limits: per device 1 a minute and 5 an hour, for the fleet 1 every 20 s and 20 an hour (monotonic clock), and none while the wrong-code breaker is open. A public-link request must belong to the open, current exposure; its code is scoped to that exposure and still requires the confirmed public notice. `/web revoke` clears the registry, and `agend web-token rotate` invalidates every device cookie (both the HMAC key and the epoch change).

This is a shared operator credential, not a per-user account or role system. `/web` requires a fleet admin, but whoever holds a code, a session or the header token can use it, and local chat allowlists are not rechecked for each HTTP action. Public requests additionally require the issuing owner/binding and exposure to remain current. Treat a code like a password until it is used; menu codes are sent privately.

## Temporary public gateway and local reads

An explicit owner-adapter General admin action may open the managed public link for two hours (configurable 1–480 minutes, fixed from consent; with a fixed named-tunnel hostname up to 10080 minutes or no expiry, and an opt-in `auto_open` that reopens it after a restart for the last admin who opened it — without sending any sign-in code). Only pinned/checksum-verified cloudflared is used, in the same one-tunnel lane as `/login`. The listener is separate and carries code-owned provenance, not a trusted proxy header. Only the current exact public HTTPS Host and reviewed panel routes are accepted; no wildcard is added to the local Host list. `/view` and usage reads require public sign-in even if local reads are open. Health, agent, issue-code, SSE, preview and legacy restart endpoints are not exposed.

What each way in allows (the dashboard reached directly, the temporary public link, a fixed named-tunnel address), row by row: [The three ways in, compared](web-dashboard.md#the-three-ways-in-compared).

Public cookies are Secure `__Host-` cookies and bind one exposure. The gateway rejects local header tokens, cookies and codes; public codes and sessions are exposure scoped. Public sessions have a four-hour absolute and 30-minute idle limit, also bounded by earlier link closure. Every public login needs a confirmed 🔐 public notice in the owning General within five seconds, regardless of `notify_login`; the candidate is neither usable nor persisted before confirmation. Code leakage can still grant full web-admin access. Cloudflare terminates TLS; forwarding a link alone does not sign in, but reveals the endpoint to guessing and shared-breaker denial of service. Exact Origin plus CSRF protects browser writes; Host checks are not authentication. Expiry, disable, private close, revoke, owner/binding loss and shutdown close access and withdraw public credentials before child cleanup. An unconfirmed child stop blocks another tunnel.

**Web authority over the admin's named link (#2453), opt-in, off by default.** `web.verified_authority.named_link: true` lets a session on the admin's own named-tunnel hostname be authorized with the account's Confirm card (#1939 §0.2).
- **Which requests count.** The gateway marks a request as named only when its pinned host is exactly the configured hostname. No header can set or change that. A quick-tunnel request is governed by the quick-link option below.
- **Turning it on** is a held Settings change like any other, and it can't be proposed over the public link. Since AGEND-122 a signed-in admin confirms it with Apply now from wherever they reach the dashboard (see [Sensitive Settings](#sensitive-settings-need-a-second-confirmation)), or with the confirming admin's own authenticator code while their own switch is on — but never over a link while a code is asked. Every confirmation from another device posts a Notice, because a change that opens a link is the one that lets the internet in. "On the AgEnD computer" means a loopback request with a loopback Host and no forwarding header. A local port-forward (`ssh -L`, an IDE's port forwarding) arrives exactly like that, so it counts as this computer. Whoever can create one already has the host, so this is consistent with the threat model. The quick-link option follows the same rule.
- **Turning it off** applies at once. Every receipt from a named-link session then reads as none (`downgraded: named_link_off`). Turning it back on moves the revocation epoch, so those receipts never come back.
- **`loopback_only`** still wins.
- **Risk accepted by turning it on.** Cloudflare terminates TLS and sees the traffic, including the session cookie. A stolen cookie of an authorized named-link session can be replayed from anywhere until one of these ends it:
  - the 30-minute idle or 4-hour absolute public-session limit;
  - `max_session_hours`;
  - **Not me** on the notice card;
  - `/web revoke`;
  - the option turned off.
- **A named-link session is never the authority that confirms a held Settings change itself.**

**Web authority over the temporary public link (#1939 §0.3), on by default since #2819.** A session on the temporary public link that `/web` opens (a quick tunnel, `*.trycloudflare.com`) can be authorized with the account's Confirm card too, unless `web.verified_authority.quick_link: false` is set. Nothing is granted by the default itself: each session still needs its account's Confirm in the DM.
- **Which requests count.** Every gateway request that is not named, known from the listener alone; no header can set or change it. The session must belong to the current exposure, and every quick URL is a new one.
- **Turning it back on** (from `false`, by `true` or by removing the key) is a held Settings change like any other, and it can't be changed over the public link: a signed-in admin confirms it with Apply now from any device, or with the confirming admin's own authenticator code while their own switch is on, and a confirmation from another device posts a Notice (see [Sensitive Settings](#sensitive-settings-need-a-second-confirmation)). It is judged on the value in force (the key unset means the default, on; a value other than `true` or `false` is off). A session that arrived over the temporary link can only confirm while this option is on; the same holds for the named link and `named_link`. Every time it goes on, the first time too, the revocation epoch moves in the same write: every authorization given so far ends, and browsers confirm again. That includes the first start after updating to #2819 on a fleet that never set the key.
- **Turning it off** applies at once. Every receipt from a quick-link session then reads as none (`downgraded: quick_link_off`), and those sessions' authorizations are dropped. Turning it back on moves the revocation epoch, so those receipts never come back.
- **`loopback_only`** still wins.
- **Risk accepted while it is on.** The quick URL is a public internet address: anyone who has it reaches the sign-in page. The barrier is the same as the named link's: a sign-in code sent privately to an allowed account, then that account's Confirm for the session. Cloudflare's quick-tunnel service terminates TLS and sees the traffic, including the session cookie; AgEnD starts the quick tunnel with no front authentication. A stolen cookie of an authorized quick-link session can be replayed from anywhere until one of these ends it:
  - the 30-minute idle or 4-hour absolute public-session limit;
  - `max_session_hours`;
  - **Not me** on the notice card;
  - `/web revoke`;
  - Close, or the link's expiry;
  - the option turned off.
- **A quick-link session is never the authority that confirms a held Settings change itself.**

**Signing in does not protect all local HTTP reads.** `/view` and its GET APIs, including `/api/pane/<instance>`, profiles, avatars and sort order, are public to anyone who can reach the listener with an allowed `Host`. The listener binds `127.0.0.1`, but that still includes:
- other local users and processes;
- whatever a reverse proxy, tailnet share or port forward admits (`web.allowed_hosts`);
- on WSL2, the Windows host.

The anonymous `/view` reader sees every instance: it has no account and no scope. Signing in doesn't add one to `/view`: with `web.view_access: open`, anyone who reaches the dashboard's own port, a guest too, can read without signing in. A request that carries a guest's session is checked as that guest's (#2855): its own agents only, and a pane only at the Trusted level and within its limits. `/api/ai-usage` is also public when enabled, and GET `/health` needs no token. Pane captures can contain commands, credentials and other private output.

Set `web.view_access: session` to close those reads: `/view`, its GET APIs and `/api/ai-usage` then need a session or the header token, like the dashboard. `/view`'s writes (profile, avatar, sort order) always go through the dashboard gate: a session with the cookie-write checks above, or `X-Agend-Token`, never a `?token=`.

The local health/dashboard listener binds to `127.0.0.1`. Every request, including public reads and `/agent`, must pass the `Host` allowlist: `localhost`, `127.0.0.1`, `[::1]`, configured `hostname`, and names in `web.allowed_hosts`. Missing, malformed or unlisted hosts get 403. The login terminal listener also uses a Host allowlist.

This check limits DNS rebinding from a browser. It is **not authentication**: an ordinary HTTP client can choose an allowed `Host`. If a proxy or port forward exposes the listener, protect public reads at that boundary and add only host names you intend to serve. A `/login` terminal has a separate per-login credential; its temporary public tunnel is not a tunnel to the dashboard. Existing local sessions cannot authorize the managed public host, and public sessions cannot authorize the local listener or a later exposure. See [login configuration](configuration.md#finishing-a-login-away-from-the-machine-public-link).

## Agent HTTP token

`POST /agent` bypasses the dashboard gate and requires `X-Agend-Instance-Token`. The header value is `<encodedInstance>:<token>`, where `<encodedInstance>` is `encodeURIComponent(instanceName)` and `<token>` is the 64-character hex token the daemon writes to `<instanceDir>/agent.token` (mode `0600`) on each CLI spawn. The endpoint decodes the instance name, verifies the token before reading the request body (missing or wrong token returns 401 without consuming the body), and caps the body at 512 KiB (413 if exceeded). The server also enforces that instance's AgEnD tool permissions. A web token is not a substitute for this token. As with the IPC socket, a process running as the same Unix user can read the credential; this is not isolation between mutually untrusted local agents.

## Secrets storage

Bot tokens and API keys are stored in plaintext at `~/.agend/.env`; `web.token` and per-instance `agent.token` are plaintext credentials too. Filesystem permissions restrict access but do not encrypt these files. `web-sessions.json` holds only hashes of session ids, not anything that signs a browser in.

Minimal `agend export` includes `.env` when present; a full export can also include other credential files. The gzip tar archive is not encrypted, and the command warns about secure transfer. Protect exports and backups as credentials. Consider filesystem encryption if the host is shared.

### Sensitive Settings need a second confirmation

A browser session (local or public) can propose changes to access/F/C lists, credentials, connection destinations/order, public exposure and control-bearing instance settings. The server keeps an immutable, memory-only request for at most five minutes, tied to the live session and configuration snapshot, and shows the complete bounded diff. Secret values are replaced by key names and fingerprints. Ordinary model/display changes remain immediate, with a snapshot check before writing. What confirms such a request changed in AGEND-122 (upstream [#3486](https://github.com/songsid/AgEnD/issues/3486)); the older rule is described under "What changed" below.

**Who confirms: a role, asked on every request.** A signed-in human fleet admin on a **web cookie session** confirms a held change with **Apply now** (`POST /api/settings/pending/<id>/confirm`, or at Save with no extra click), from wherever the dashboard is reached: the AgEnD computer's own browser, a direct LAN or tailnet connection, or a public link. It covers every kind of change — secrets, access lists, connections, outward Hub changes, opening a link — on a chat fleet and a web-only fleet alike. There is no per-browser proof to give first: no DM confirmation (#1939), no "a General card could be posted", no trip to the host. Checked on the live session when it is asked and again when the change executes (a session that was signed out, expired, revoked or whose admin was removed leaves the change stale, nothing applied):
- a cookie session with the admin tier; a chat account is still an admin of its own connection and of every connection the change touches (account ids are per platform);
- the owner's own knobs hold: the web authorization switch (`web.verified_authority.enabled`), **Only this computer can authorize** (`loopback_only`: then only the AgEnD computer's own browser confirms, with or without a code), and, over the temporary or named link, that link's option (`quick_link`, `named_link`). A web-only fleet's session over a link must be the owner signed in from outside with the authenticator (#3008).

**What never confirms.** An agent never confirms its own request, including one steered by prompt injection. What stops it is that it has no person's browser cookie session, not where it runs: an agent on the host is also on loopback. `agend settings confirm` refuses agent environments, and an agent token is not a session. A guest, a read-only session, a non-admin, a header token (the CLI's) and a paired Windows PC never confirm Settings. The General card stays another way to confirm for a chat fleet; the host command `agend settings confirm <id>` stays the way on the host and for the setup page (before any fleet exists).

**Your own authenticator and your own switch (per admin).** Each admin can set up their own authenticator app and turn on their own "Ask for my authenticator code to confirm changes from other devices" (Settings → Access & security → **Owner verification**, the card's switch; off by default; it needs your app first). Nobody is required to enrol: an admin without an app confirms as in the default. The switch applies **only to that admin's own confirmations**; no admin can turn it on for another, and no admin can set up, replace, remove or switch off another admin's app — only its owner, or someone using that admin's own account on the AgEnD computer's own browser. While your switch is on, your confirmations from a page that is not the AgEnD computer's own browser do not get Apply now, whatever the session is (a LAN or tailnet session, a session over a link, the owner signed in from outside): each change takes the code of **your** app for **that one change** — bound to the change's digest (checked before the code is), one use per time step, the fleet-wide wrong-code limit, asked again at execution against the same app. A chat account must still be an admin of the connections the change touches at entry and at execution. **Only this computer can authorize** stays fleet-wide and host-only, and blocks the code too. A change that opens a link is never confirmed over a link while a code is asked. The computer's own browser is not asked. Changing an app that exists — replacing it, removing it, turning your switch off — is its owner's, proven with that app's current code off the AgEnD computer, **whether or not your switch is on** (the switch is about ordinary confirmations; this is ownership of the app itself). With no app there is no old code to ask: a first set-up asks nothing, and the AgEnD computer's own browser is never asked, so that is the recovery path. A set-up begun on the computer, or while no code was asked, cannot be finished by a session that is now asked for one. At most 64 admins can have an authenticator: the 65th set-up is refused up front, never accepted and then dropped at a restart. The fleet-wide wrong-code pause is cleared only by a set-up made on the AgEnD computer itself, never by the host identity used remotely. "The AgEnD computer" is a request that arrives from a loopback address with a loopback Host and no forwarding header, so an `ssh -L` or IDE port-forward, and any process on the host, count as the host (consistent with the threat model). **The switch does not close every path:** on a chat fleet a General's confirm card is a separate way to confirm the same change — a switch change included — that never asks for the code; it needs a chat account that is an admin, a different factor. A web-only fleet has one admin (the owner), so it has one authenticator, the one connections from outside use. **What a stolen session can do about this:** with a stolen cookie of an admin who has no app, enrol an app of the attacker's own and turn the switch on — that admin's own remote confirmations then need a code only the attacker holds, so the real admin is locked out of confirming from other devices until they use the AgEnD computer's own browser, where nothing is asked and they can remove the app and switch off. It cannot lock out any other admin, and every enrolment and switch change posts a Notice to the fleet. If the app file is lost an admin's switch is lost with it (back to the default), never a lock.

**Notices.** Always posted, besides the audit entry: (1) a confirmed change that opens a public link or changes a secret, when it is confirmed from another device (not the AgEnD computer's own browser); and — from anywhere, the computer included — (2) every set-up, replacement or removal of an authenticator and (3) every switch of "ask for my code" on or off, each naming the admin it concerns. They go to the fleet's admins: every connection's General (their admin lists can be disjoint; with no General, the primary connection's notice target) **and** always the dashboard's Notices, which are persisted and shown to every admin — so a chat send that fails after being dispatched still leaves the Notice. A web-only fleet's audience is the dashboard Notices. Notices carry the redacted diff, who and the outcome — never a secret value. The audit entry names who confirmed and how, as before.

**The risk you accept, in plain words.** Until an admin turns on their own "ask for my code" switch (it protects that admin only) or the owner turns on **Only this computer can authorize**, anyone holding a signed-in admin session — an unattended browser, or its session cookie — can make any change from any device that can reach the dashboard, including opening a public link and changing secrets, without a second step. The Notice is how the owner finds out, not a gate. Sign-in codes, session limits and `/web revoke` are what limit how long such a session lives. "LAN" in the code and in these notes means "reached directly and not on the AgEnD computer": a tailnet, a reverse proxy or a funnel the owner runs also arrives that way, even from the internet. It does not mean a private local network.

**What changed (AGEND-122).** Before: a held change needed the account's one DM confirmation of the browser (#2170) plus a General a card could go to, or the host's own session on the AgEnD computer; outward Hub changes and opening a link were the host's own session only; the authenticator code (#3355) worked only on a web-only fleet, for a LAN or loopback admin session, and never for a link opener. Now: one role rule for every class and place, an optional code for all of them, and the Notice. The temporary-link and named-link options, the web authorization switch and **Only this computer can authorize** are unchanged and still narrow who qualifies. Settings that were never proposable over a public link (the web settings, the Hub's, runtime switches) are still refused before they are proposed.


If the affected connection cannot safely receive the prompt, AgEnD tries another world's General, then requires local `agend settings confirm <id>`. That command uses a separate same-user Unix socket (0700 parent, 0600 socket); agent environments are refused. It prints the authoritative source, requester and diff before an interactive confirmation or explicit `--yes`. There is no HTTP/MCP confirm route. Setup before a fleet exists uses the same host confirmation; a pending response never starts the fleet.

Revocation, expiry, shutdown or a changed baseline prevents new effects. An admitted operation retains its resource leases through actual settlement and conditional cleanup; it may remain `applying` while native work settles. Rollback restores only still-owned fields, preserving later edits. Intentional final session revocation can return a completion receipt but cannot authorize further effects. Pending requests disappear on restart, so submit again. This boundary does not defend against another process running as the host user; independent filesystem edits are detected where possible, rather than claimed to be atomic.

### Signing a new browser in with your own authenticator (#3486)

The same per-admin app is the way a browser that is not signed in yet becomes **that admin**: `POST /auth/totp` with **only the 6-digit code** of their own app — no name, no list (the temporary page is `/signin/authenticator`; the sign-in page's own UI calls the route in the PR description). The server works out whose code it is. The rules:

- **Who.** The code is compared with the app of **every** admin who has one and is still an admin of their connection — each of them, every time, the codes of their app for the same 7 time steps (three either side of now, which covers the accepted window of three steps, the clock-skew look and the collision rule below), compared in full with no early exit, and only afterwards is anything decided by what was already spent or who may sign in here; so the cryptographic work (7 HMACs per admin, plus a fixed pool of 8 retired-app slots of 7 each, decoys when empty) does not depend on whose code it is, whether it was used, or whether it is a digit string at all (with no app at all, one admin's worth is done with a decoy secret). **Exactly one match** signs that admin in and spends their step. **No match** is the one 401 `wrong_code`. **A collision** — the digits equal the code of one admin's app in the accepted window and of another admin's app within two steps of it (about 3 in a million per other admin who has an app, for a right code) — signs **no one** in, spends **nothing**, and answers with the very same 401, counted as an ordinary wrong code: the person simply waits for the next code, and nobody can tell a collision from a typo. The rule looks only at the raw codes of the apps, so those digits stay refused for as long as any step they matched is still accepted — after one of the admins spent their step (by a named sign-in or a confirmation), was demoted, or after one of the two steps aged out — and a restart cannot lose it. It also survives the matching admin removing or replacing **their own** app: the old secret is then kept as a *retired* one for 3 minutes (longer than any step the refused digits could still be accepted for), saved in the same file as the apps and **used only by this collision check** — it can never sign anyone in, confirm anything or be asked for. The retired pool is fleet-wide and fixed in size (8) and always compared in full, so the work does not change with it; if more apps are retired within those 3 minutes than the pool holds, the oldest is dropped and code-only sign-in is refused (as an ordinary wrong code; the named path and the 8-character code are not affected) until the dropped one's 3 minutes would have run out. Each removal or replacement is already a Notice to every admin. (Counting only unspent matches would let a refused collision sign the same digits in as the other admin later.) Nothing lists admins and the page suggests no names. A request that still sends a name (`account`; the page no longer does) is accepted as before: the name resolves — among admins that have an app and are still admins — to exactly one (the platform handle, the chat user id or `connection:id`) and is held by the per-name and per-admin counts too. A web-only fleet has one admin and one app. The session is the account's own (a chat fleet) or the fleet admin's (web-only), exactly what a sign-in code from chat or `agend web --code` makes; it carries no authorization of the web authority (§0 "Authorize this browser") and nothing an agent takes as a go-ahead. What it may do afterwards is the role #3503 gives that admin — including their own "ask for my code" switch.
- **No oracle.** A wrong code, a code that is nobody's, an admin demoted since, a step already used, an admin with no app and a code that matched two apps at once all get the same answer (401 `wrong_code`, the same headers) after the same work, and the same counting: every failure raises the same counters (this browser's and the whole sign-in's) and is saved. No answer, header or count says which admins exist, who has an app, or that two codes collided. (An admin's own ceiling is started only by requests that still send a name and holds only the named path; the code-only path is not affected by it, so someone typing wrong codes under an admin's name cannot block that admin's code-only sign-in — that path is bounded by the whole sign-in's ceiling and each browser's limit.) A Notice is sent for the whole sign-in's pause and a real admin's, so a flood of strangers is one Notice per wait, not one per try; the answer is the same either way.
- **Same protections as a confirmation, and one person's typos stop only that person.** Each time step is used once, in the same `lastStep` as that admin's confirmations and switch. Wrong codes are limited in layers, none of which is the confirmation limiter (an open route must not be able to pause the confirmations of admins already signed in): (1) **this browser's bucket** — a cookie id handed out with the first answer, plus the address on a direct connection (over a link the gateway only sees the tunnel, so the cookie alone), or the first known-device mark it carries — 5 wrong codes in one bucket pause that bucket for 5 minutes, doubling up to an hour, and no one else. It is **not a hard per-person ceiling**: a browser that drops its cookie, or drops one of several marks and keeps another, lands in another bucket. What really bounds guessing is the whole sign-in's ceiling below and, for a browser carrying known-device marks, the known-path counters of every admin whose mark it carries; (4) **the whole sign-in** — a shared ceiling: **20** wrong codes from anyone, with a name or without, → 15 minutes, doubling up to a day (it was 50 before the name went away; see the arithmetic below). A code with no name belongs to no admin, so there is **no per-admin and no per-name count for it**: what replaces them is exactly layer 1 plus the whole sign-in's ceiling, which does not depend on how the guesser spreads the tries. (Layers 2 and 3, the admin's own count and the typed name's — 10 each — still apply to a request that sends a name.) A shared count is forgotten only after **a day** without a wrong code (this browser's after an hour) — so a guesser who paces eighteen tries a day is still caught — and the doubling steps down a level per quiet day. A correct code clears that admin's own counts and this browser's but never the whole sign-in's (only time lowers it). **Half-way** — the whole sign-in's count reaching 10, or a known-device admin's path reaching 15 — the fleet's admins get one Notice ("someone keeps trying", nothing of the code; once per cycle); the answers do not change. Because a browser that drops its cookie is a new browser to layer 1, the shared ceiling is what stops guessing. As the session is made it is checked again: the same app (not replaced or removed), still an admin of the connection, still allowed here. **Only this computer can authorize** closes the route (404, counted as nothing) except on the AgEnD computer's own browser. Every successful sign-in is a Notice to the fleet's admins — every connection's General **and** the dashboard Notices — naming the admin, the device and how; a shared wait starting is a Notice too.
- **The known-device mark.** After a correct sign-in as admin X the browser gets a long-lived (90 days), HttpOnly, SameSite=Strict "known device" cookie: up to four entries, each an HMAC (keyed from `web.token`) over X's identity, the enrolment id of X's current app, the revocation epoch and the expiry. It grants nothing and names no one. It only lets that browser, signing in as X **with a correct code**, skip the shared pause (the whole sign-in's) that someone else's wrong codes started — for the admin the mark was made for; for any other admin's code it is held like anyone — so while a stranger is guessing, a device you have used can still sign in; a new device waits, or uses the 8-character code. It is held by two limits of its own: its wrong codes are counted **by the mark** (5 → 5 minutes; dropping the cookie id resets nothing), and, with every other attempt carrying one of X's marks, in a **known-path limiter per admin** (30 wrong codes → 15 minutes, doubling up to a day, forgotten after a day without one; the admins get a Notice at 15) — so several copies of a stolen mark cannot add up their tries either. **The price:** someone who holds a stolen mark and keeps sending wrong codes can, after about 30 of them, pause the devices that admin has already signed in from too (up to 24 hours, doubling). The admins get a Notice first (half-way, then the pause); the admin can use the 8-character sign-in code meanwhile, or end every mark at once by revoking authority (the epoch moves). The limit is high on purpose, so that it only trips on an obvious attack; without it a stolen mark could still guess five times an hour — about forty thousand tries a year. Strangers' wrong codes (no mark) never touch these counts. It stops vouching when X no longer resolves (demoted — while they are not an admin the name is nobody's; adding them back with the same app revives it), when X's app is replaced or removed (another enrolment id), when authority is revoked (the epoch moves) and when `agend web-token rotate` changes the key; an expired or altered entry never verifies.
- **Where.** A direct connection (this computer, LAN, tailnet, the owner's own proxy) on any fleet; on a chat fleet also a public link (quick or named), decided in one place: `TOTP_SIGNIN_OVER_PUBLIC_LINK` in `src/web-remote-access.ts` — set it to `false` to refuse links (404) and keep direct connections; a session over a link still follows the link's own option for held changes (#3503). A web-only fleet's link stays only the one "Allow connections from outside" opened (#3008).
- **Unchanged.** The 8-character sign-in code, the first set-up's trust start (the AgEnD computer), and who can never confirm or become an admin session by this route: an agent, a guest, a non-admin, a header token and a paired Windows PC. An admin with no app keeps the 8-character code.

**The risk this adds, in plain words.** Anyone who gets a current code of **any** admin's app — a phone left unlocked, a shoulder-surfed or phished code used within its 30-second window — signs in as that admin from a new browser, over a public link too while that is on; and a guesser needs no name, so **each wrong guess can match any of the admins who have an app**: with N such admins one guess is N times as likely to hit as before (about 3N in a million: three codes are valid for each admin at a time). The limits pay for it, and what is left is the arithmetic in the next paragraph. The other defences: one use per time step, the Notice to every admin on each sign-in (so the real admin finds out) and on each pause, the Sign out controls, and — if you do not want links to be a way in — turning `TOTP_SIGNIN_OVER_PUBLIC_LINK` off or **Only this computer can authorize** on. **What is also left:** someone sending wrong codes can keep the shared pause in force, so **new** devices cannot use an authenticator meanwhile (a device the admin has already signed in from can, with a correct code; a new one waits, or uses the 8-character code). Someone who steals a known-device mark is not held by the shared ceiling but is held by the mark's own count and the admin's known-path limiter (30 wrong codes across every mark of that admin, then a doubling wait — which also holds that admin's other known devices for the time) — and still needs a correct code, so the mark alone opens nothing. The "known device" mark of a demoted admin whose app is unchanged works again if they are made an admin again.

**The arithmetic behind "20".** Let N be the number of admins who have an app. Each admin has three valid codes at any moment (the current step and one either side) out of 10⁶, so one wrong guess hits somebody with probability p ≈ 3N / 10⁶ (two at once — a collision — signs nobody in). A guesser who spreads tries over fresh browsers is limited by the whole sign-in's ceiling L (= 20) wrong codes, then a pause of 15 min, 30 min, 1 h … doubling up to 24 h; because the next try comes the moment the pause ends, the count is never forgotten and the level never steps down, so in the long run the guesser gets **L tries per day** — measured with a clock-driven run of the real limiter (`tests/signin-per-admin-totp-3486.test.ts`): 140 tries in the first day, 260 in a week, 720 in 30 days, **7 420 in a year**. The chance to be signed in as someone is exactly 1 − (1 − 3N / 10⁶)^7420 (2.2014 % for N = 1, 19.9568 % for N = 10); by time and for the other ceilings, below. "2.2 % × N" is only the small-N approximation of it (N = 10 would be 22 %, not 19.96 %).

| admins with an app (N) | first day | 30 days | **1 year** | 1 year if L = 50 (before) | 1 year if L = 10 |
|---|---|---|---|---|---|
| 1 | 0.04 % | 0.22 % | **2.2 %** | 5.4 % | 1.1 % |
| 3 | 0.13 % | 0.65 % | **6.5 %** | 15.4 % | 3.3 % |
| 5 | 0.21 % | 1.07 % | **10.5 %** | 24.3 % | 5.4 % |
| 10 | 0.42 % | 2.14 % | **20.0 %** | 42.7 % | 10.5 % |

For comparison, with a name typed (one admin, per-admin ceiling 10) the figure was 1.1 % a year for the admin the guesser aimed at, whatever N was; without a name it is about N times 2.2 % for small N (exactly the formula above). These are the odds of a guesser who never stops for a year; he also sends the admins a "paused" Notice every day, and one more Notice at the half-way point of each cycle, which is what a person should notice long before. Why 20 and not lower: one browser may type 4 wrong codes before its own pause, so the whole sign-in's ceiling must be well above what two honest people mistyping can add up (8) or one careless afternoon pauses every new device; 20 takes five browsers at their own limit. At 10 the yearly odds halve, but two people's typos in a day would pause everyone. An owner with many admins who wants less can lower `SIGNIN_FLEET_WRONG_LIMIT` (one constant in `src/web-remote-access.ts`; the cost is that a shorter run of honest typos pauses new devices) or set up authenticators for fewer admins; an admin with no app keeps the 8-character code, which this does not touch.

## CI supply chain (#2528)

GitHub Actions used by this repository are pinned to full commit SHAs, so a
moved tag cannot change what CI or the npm publish workflows run. A CI job
fails the merge gate if any remote `uses:` is still a tag. Dependabot's
weekly `github-actions` updates rewrite the SHA and the trailing tag
comment together (patch/minor grouped; each major its own PR). See
[CI coverage — GitHub Actions pins](ci.md#github-actions-pins-2528).

CI verifies npm registry signatures of the root and `website/` install trees
(`npm audit signatures --json`). Invalid signatures fail the job; missing-only
findings are reported. See [CI coverage](ci.md#npm-registry-signatures-2528).

Pull requests into `main` and `release/**` run GitHub's dependency review:
high or critical advisories, and licences outside the allow-list, fail the
check. See [CI coverage](ci.md#dependency-review-on-prs-2528).
